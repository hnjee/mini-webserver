## 결정

### D-55. I/O 멀티플렉싱을 동시성 방식으로 선택한다
- 선택: **I/O 멀티플렉싱**으로 여러 연결을 다룬다. 사용할 Linux API와 내부 구조는 설계에서 정한다.
- 이유: 사용자 선택. 대기 중인 연결 때문에 처리 흐름이 묶이는 문제를 먼저 해결하고, 이후 필요하면 스레드 풀을 덧붙일 수 있다.
- 버린 선택지: 연결마다 `fork`하거나 스레드 풀을 먼저 두는 방식은 이번 Step의 우선 학습·구현 방향과 다르다.
- 한계: I/O 준비 알림만으로 파일 작업이나 오래 걸리는 계산까지 논블로킹이 되는 것은 아니다. Step 6의 백엔드 연결·중계 경로는 별도 설계한다.

### D-56. `epoll` 레벨 트리거로 기다리고, 한 차례에 정한 만큼만 처리한다
- 선택: Linux **`epoll` 레벨 트리거**를 쓴다. 듣는 소켓과 연결 소켓을 모두 논블로킹으로 한 `epoll`에 등록하고, 연결마다 기다리는 방향은 읽기·쓰기 중 하나다.
- 한 차례 예산: 소켓 `read` 최대 1번, 파일 조각 채우기 최대 1번, `write`는 **차례를 시작할 때 있던 출력 바이트까지**만. 버퍼 소비·파싱·상태 전이는 외부 I/O가 필요할 때까지 계속한다. `EINTR` 재시도도 예산을 넘지 않는다.
- 내부 실행(B1): 커널 신호 없이 진행할 일이 남았는데 예산이 끝났으면 연결은 **실행 가능**으로 끝나고, 루프는 중복 없는 내부 실행 목록에 넣어 다음 회차에 반드시 다시 부른다. 버퍼 안 바이트만으로 진행할 수 있는 연결은 읽기 대기로 돌아가지 않는다. 예: 버퍼 속 다음 완성 요청, `100` 뒤 버퍼 속 본문, `/echo` 머리 뒤 버퍼 속 본문 조각, 아직 채우지 않은 다음 파일 조각.
- 회차: 내부 실행 목록이 비어 있지 않으면 `epoll_wait`는 기다리지 않는다(0). 한 회차는 반환 배치 처리 → 회차 시작 때 목록에 있던 연결 실행 → 마감 확인 순서다. accept는 한 회차에 **시도 수 상한**까지만 하고, 성공·재시도 오류(D-07)·연결 준비 실패 모두 한 번으로 센다. `EAGAIN`이면 그 회차 accept를 끝낸다.
- 이유·한계: 차례 예산으로 한 연결이 큰 파일·본문을 독점하지 못하고, 준비된 연결과 실행 목록을 **회차마다 순환** 처리한다. 준비 fd가 배치 크기보다 많으면 여러 회차에 걸쳐 처리된다. 실시간 공평성은 보장하지 않으며, 파일 `open`·`read`의 디스크 대기는 남는다(D-55). D-07 밖 accept 오류(`EMFILE` 포함)는 지금처럼 서버를 끝낸다(Step 7). 버린 선택지: `poll`(매번 전체 목록을 넘기고 fd→연결 찾기를 따로 둔다), 엣지 트리거(`EAGAIN`까지 다 읽어야 해 예산과 맞지 않는다).

### D-57. 연결 상태를 구조체로 옮기고, 루프와 연결 처리를 나눈다 (D-46 대체)
- 선택: 새 **루프 모듈**이 `epoll`·accept·연결 목록·내부 실행 목록·마감 확인·끝난 연결 정리를 맡고, `http_conn`은 **연결 하나의 상태 전이**만 맡는다. 차례 결과는 읽기 대기·쓰기 대기·실행 가능·끝 중 하나다.
- 소유: 소켓 fd와 연결 구조체 메모리는 루프가, 파일 fd·남은 전송 길이·버퍼 내용은 `http_conn`이 가진다. 결과(`DONE`·`PEER_CLOSED`·`TIMED_OUT`·`ERROR`)와 오류 번호는 실패한 자리에서 구조체에 저장한다.
- 끝난 연결의 수명(C3): 끝나면 즉시 **끝 표시**하고 내부 실행 목록에서 빼며 다시 실행하지 않는다. `http_conn` 해제(파일 fd 닫기) → 소켓 `close` → 메모리 해제는 **회차 끝**에 한다. 그래서 같은 배치·실행 목록에 남은 포인터가 해제된 메모리나 재사용된 fd를 가리키지 않는다. 생성 실패(메모리·논블로킹 설정·`epoll` 등록)는 만든 자원까지 회수하고 그 소켓만 닫는다. 관심 방향 변경 실패는 그 연결 `ERROR`(원래 오류 저장)다. `epoll` 만들기·기다리기(`EINTR` 제외) 실패와 D-07 밖 accept 오류는 서버를 끝낸다.
- HUP·ERR(C2): 이벤트 플래그는 연결을 **깨우는 정보**일 뿐 종료 판정이 아니다. 남은 입력·출력을 상태대로 처리하고 실제 `read`·`write` 결과로 결과를 기록한다(HUP 뒤에도 저장된 요청을 판정하고 `100` 쓰기 실패는 `EPIPE`로 남김). 이번 구현은 `SO_ERROR`를 따로 읽지 않는다. `EAGAIN`은 정리 상태를 포함해 대기 유지이며, 끝낼지는 마감(D-59)이 정한다.
- 함수 분리·이유: 블로킹 함수의 지역 변수를 구조체 필드로 옮기고 **상태마다 처리 함수 하나**가 다음 상태를 정한다(끝내는 길은 하나). 지역 상태가 차례 사이에도 살아야 하기 때문이다(D-46의 다시 볼 조건). 버린 선택지: 루프가 요청 판정까지 맡기(HTTP 규칙이 두 곳), `http_conn`이 소켓을 닫기(`epoll` 해제와 닫기가 나뉨).
- 영향: 서버 경로에서 `http_conn_serve`는 없어진다. `test_http_conn`은 시험 쪽 `poll` 구동 함수로 바꾸되, 실행 가능·HUP·ERR·마감을 루프와 같은 규칙으로 다룬다.

### D-58. 응답은 연결별 출력 버퍼에 만들고 나눠 보낸다
- 선택: 연결마다 **출력 버퍼** 하나(64KB)를 둔다. `100 Continue`·응답 머리·상태 본문·파일 조각·`/echo` 본문을 여기 넣고 논블로킹 `write`로 보낸다. 출력이 남아 있으면 **소켓에서 새로 읽지 않는다**.
- 부분 송신 수명(C1): 출력이 남은 동안 버퍼 내용과 위치·길이를 바꾸지 않고, **모두 보낸 뒤에만** 다음 내용을 채운다. 한 번에 채우는 것은 머리 묶음(머리 + 상태 본문, 또는 `/echo` 머리 + 입력 버퍼 속 본문, 최대 약 13KB)이거나 파일·`/echo` 조각 하나이며, 조각은 빈 버퍼 용량까지만 읽는다. 입력 버퍼의 다음 요청 바이트와 요청 정보는 앞 응답을 다 보낼 때까지 보존한다.
- 출력을 다 보낸 뒤 동작: `100` → 본문 단계. `/echo`는 머리 + 버퍼 속 본문 → 소켓 조각 읽기·보내기 반복 → 본문과 출력이 모두 끝나면 유지·닫기. 그 밖은 본문을 다 버림 → 판정·최종 응답 → 유지·닫기·정리. 닫는 코드(D-51)는 최종 출력을 다 보낸 뒤 **`shutdown(SHUT_WR)`을 한 번** 하고 정리(D-54)를 시작한다. 정상 `Connection: close`·1.0 닫기와 쓰기 실패는 정리 없이 끝낸다.
- 파일: 원래 크기를 넘게 보내지 않고, 남은 길이가 있는데 파일 끝이면 `EIO`로 `ERROR`다(D-29). 머리를 보낸 뒤 실패는 두 번째 HTTP 응답 없이 연결만 닫는다(D-51).
- 이유·버린 선택지: 블로킹 쓰기를 남기면 받아 가지 않는 클라이언트 하나가 **서버 전체를** 멈춘다. `sendfile`(D-22·D-29의 `read`·`write` 경로가 바뀌고 `/echo`에 못 씀), 응답 전체를 메모리에 만들기(파일 크기만큼 메모리)는 버렸다. `http_response`는 같은 계약(D-52)으로 버퍼에 쓰는 함수를 더하고, 기존 `send_*`는 그 위의 얇은 감싸개로 남긴다.

### D-59. 읽기·쓰기 진행이 없으면 5초 뒤 닫는다 (D-40·D-53의 시간 측정 변경)
- 선택: 논블로킹 연결에서는 `SO_RCVTIMEO`·`SO_SNDTIMEO` 대신 **읽기·쓰기 진행이 없는 기간 5초**를 연결별 단조 시계로 잰다. 결과 구분(D-53)은 유지하고, 요청·응답 전체 마감은 추가하지 않는다.

| 실제 대기 종류 | 마감 시작 | 마감 갱신 | 만료 결과 |
| -------------- | --------- | --------- | --------- |
| 요청 사이 읽기 (버퍼 비어 있음, 출력 없음) | 연결을 받은 때·앞 응답 출력을 다 보낸 때 | 없음 (1바이트 받으면 요청 도중 읽기로) | `DONE` |
| 요청 도중 읽기 (머리·버릴 본문·`/echo` 본문, 출력 없음) | 읽기 대기에 들어간 때 (출력을 다 보낸 때 포함) | 성공한 `read` | `TIMED_OUT` |
| 쓰기 (출력 남음, 논리 상태와 무관) | 출력을 채워 쓰기 대기에 들어간 때 (첫 `write`가 `EAGAIN`이어도) | 성공한 `write` | `ERROR`, 오류 번호 `EAGAIN` |
| 닫기 전 정리 (D-54) | `shutdown(SHUT_WR)` 한 때 | 없음 (고정) | `DONE` |

- 대기 전환(B2): 대기 종류가 바뀔 때마다 **그때부터** 새 마감을 잡는다. `100` 뒤 본문 읽기는 `100`을 다 보낸 때부터, 본문을 다 받은 뒤 최종 응답은 응답을 채운 때부터 잰다. `/echo`·본문 버리기 도중이라도 출력이 남아 있으면 쓰기 대기이므로 만료는 `ERROR`(`EAGAIN`)이고, 출력 없이 입력이 끊기면 `TIMED_OUT`이다.
- 진행이 아닌 것: 준비 알림, 상태 함수 호출, 내부 실행, `EAGAIN`, `EINTR`은 마감을 늘리지 않는다. 실행 가능 연결은 기다리는 중이 아니므로 만료로 닫지 않고 다음 회차에 실행한다. 정리 상태는 `read` 전에 마감을 확인해 마감 뒤 새 `read`를 시작하지 않는다.
- 준비·만료가 겹칠 때(사용자 선택): 한 회차에서 **이번 `epoll_wait`가 돌려준 준비 연결**과 내부 실행을 먼저 처리한 뒤 마감을 확인한다. 5초가 지난 뒤라도 실제 바이트 진행이 있으면 그 연결을 이어서 처리한다. 준비 알림만 있고 진행이 없으면 기존 마감을 유지한다. 이는 도착 시각 판정이 아니며, 배치 밖으로 밀린 연결은 같은 기회를 받지 못할 수 있다. 닫기 전 정리는 D-54의 고정 마감을 먼저 확인한다.
- 영향: Step 4의 호출별 5초(`EINTR`이면 다시 5초)와 달리, 다음 I/O를 기다리는 동안 다른 연결을 처리한 시간도 센다. Step 4에서 쓰기 정체 때 관측된 약 10초(D-53)는 호출별 제한의 결과였고, 새 정책의 종료 시점은 마지막 쓰기 진행 뒤 5초 이후 루프가 확인한 때다. 조금씩이라도 진행하면 계속할 수 있어 총시간 상한은 없다. 정확한 5초 종료는 보장하지 않는다.

## 검토 범위와 남은 한계

| 구분 | 내용 |
| ---- | ---- |
| 변경 전 구조 | `http_conn_serve`·`static_file_send_body`·`http_response_send_*`는 블로킹 `write`로 끝까지 쓰고, 버퍼에 남은 요청을 `read` 전에 처리했다. 응답 머리 버퍼는 512 + `PATH_MAX`였다. |
| OS 문서 근거 | `epoll`은 커널 fd의 준비만 알린다. HUP·ERR는 등록하지 않아도 통지되고 HUP 뒤에도 남은 데이터를 읽을 수 있다. 반환 배치는 최대 개수로 잘린다. 소켓 시간 제한은 `epoll_wait`에 적용되지 않는다(설계 검토의 Linux man-pages 대조). |
| 미검증 가정 | 연결 fd를 `dup`하지 않으므로 마지막 `close`가 `epoll` 등록도 지운다. 마감 확인 지연은 `ab -c 50`에서 5초에 비해 작다. 연결당 메모리 약 82KB가 시험 규모에서 문제없다. |
| 검토 결과 | D-56~D-58은 전체 구현 위임 안의 내부 선택으로 기록한다(사용자의 별도 정책 승인이라는 뜻은 아니다). B1·B2 차단은 설계 한정 재검토에서 해소, C1~C4는 조건부 반영됐다. 이후 문구 2건과 준비 우선 선택의 설계 재검토는 없었지만 구현 영향·필수 기능 시험은 독립 검증을 통과했다. |
