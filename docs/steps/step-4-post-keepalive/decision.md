## 정할 것

모두 정했다. 사용자 선택은 아래와 같다.

- [x] 남은 바이트 처리 (D-39)
- [x] 타임아웃 구현 (D-40, D-41)
- [x] 요청 도중 타임아웃: 408 없이 조용히 닫음 (D-53)
- [x] `Transfer-Encoding`: 처리하지 않고 `chunked`가 마지막이면 501, 아니면 400 (D-48 순서 5)
- [x] `Expect: 100-continue`: 1.1이고 본문이 있으면 검사 통과 뒤 본문 읽기 직전에 `100 Continue` (D-50)
- [x] 요청 사이 빈 줄: 400 후 닫음 (D-48)
- [x] `/echo` `Content-Type`: 항상 `application/octet-stream` (D-50)
- [x] 쓰기 시간 제한: `SO_SNDTIMEO` 5초 (D-53)

## 결정

### D-36. 파일 주소로 온 `POST`와 `GET /echo`는 405로 응답한다 (D-30 대체)
- 선택: `/echo` 밖의 `POST`는 **405 `Allow: GET`**, `GET /echo`는 **405 `Allow: POST`**다. 405여도 본문은 `Content-Length`만큼 읽고 버린다(다음 요청 위치를 찾기 위해).
- 이유: 사용자 선택. 파일은 읽기 전용이라 405가 HTTP 뜻에 맞다.
- 버린 선택지: 파일 응답 유지(D-30), 404.
- 영향: Step 3의 `POST` 파일 응답 시험은 기대값이 405로 바뀐다.

### D-37. 오류 응답 뒤에도 요청의 끝을 알면 연결을 유지한다
- 선택: 기준은 **"다음 요청이 어디서 시작하는지 아는가"**다. 404·403·405·301·500은 유지하고(500은 사용자 확인), 400·413·414·431·501·505는 **응답 뒤 닫는다**(431은 D-42에서 추가). 닫는 응답에는 `Connection: close`를 넣는다.
- 이유: 사용자 선택. 오류 하나(예: `/favicon.ico` 404)마다 끊으면 keep-alive가 비효율적이다.
- 버린 선택지: 오류면 모두 닫기.
- 영향: 머리를 보낸 뒤 본문 전송이 실패하면 연결만 닫는다(D-29).

### D-38. HTTP/1.0도 `Connection: keep-alive`를 보내면 연결을 유지한다
- 선택: 1.1은 `Connection: close`가 없으면 **유지**한다. 1.0은 `Connection: keep-alive`가 있을 때만 유지하고 응답에도 `Connection: keep-alive`를 넣는다. 그 밖에는 닫는다. D-37의 닫는 오류 응답은 버전과 관계없이 닫는다.
- 이유: 사용자 선택. 비용이 작고 `ab -k`로 연결 유지별 처리량을 비교할 수 있다.
- 버린 선택지: 1.0은 항상 닫기.

### D-39. 본문은 모아 두지 않고 조각으로 흘려보낸다
- 선택: `/echo`는 **응답 머리를 먼저** 보내고(`Content-Length` = 요청 본문 길이) 본문을 고정 크기 조각으로 돌려준다. 버릴 본문도 조각으로 읽고 버린다.
- 이유: 사용자 선택. 큰 파일 전송(D-22)과 같은 구조이고 메모리가 본문 크기와 무관하다.
- 버린 선택지: 본문 전체를 모은 뒤 응답.
- 영향: 머리를 보낸 뒤 본문 수신·전송이 실패하면 연결만 닫는다(D-29).

### D-40. 타임아웃은 소켓 옵션 `SO_RCVTIMEO`로 건다
- 선택: 연결을 받으면 `SO_RCVTIMEO`를 한 번 설정하고 `read()`가 시간을 넘기면 연결을 닫는다.
- 이유: 사용자 선택. 기존 `read()` 흐름을 그대로 두는 가장 작은 변경이다.
- 버린 선택지: `read()` 전마다 `poll()`.
- 한계: 시간은 한 번의 기다림 단위라 조금씩 계속 보내는 느린 클라이언트(slowloris)는 막지 못한다.

### D-41. 타임아웃은 5초로 한다
- 선택: `read()` 한 번의 기다림이 **5초**를 넘으면 닫는다(D-40).
- 이유: 사용자 선택. `sleep 1` 시험에 여유가 있고 순차 처리 중 브라우저 대기도 짧다.
- 버린 선택지: 2초, 60초 이상.

### D-42. 요청 머리가 너무 크면 431로 응답한다 (D-09 갱신)
- 선택: 머리가 **8KB를 넘거나 헤더가 100개를 넘으면** 400 대신 **431**로 응답하고 닫는다. 상한은 그대로다.
- 이유: 사용자 선택. "크기 초과는 전용 코드, 형식 오류는 400"으로 정리한다(414·413과 함께).
- 영향: Step 2의 8KB·헤더 100개 초과 시험은 기대값이 431이다.

### D-43. URI가 2KB를 넘으면 414로 응답한다
- 선택: 요청 줄의 대상(쿼리 포함)이 **2048바이트를 넘으면** **414**로 응답하고 닫는다.
- 이유: 사용자 선택. 8KB 머리 상한과 따로 두어야 긴 URI가 항상 414로 거절된다.
- 버린 선택지: 별도 상한 없이 8KB가 넘친 위치로 414·431 구분.
- 영향: Step 3의 "경로가 너무 길면 400"은 방어용으로만 남는다.

### D-44. 본문이 1MB를 넘으면 413으로 응답한다
- 선택: `Content-Length`가 **1048576바이트를 넘으면** 본문을 받기 전에 **413**으로 응답하고 닫는다.
- 이유: 사용자 선택. 폼·`/echo` 시험에 충분하고 `www/large.bin`(4MB)이 413 시험 재료가 된다.
- 버린 선택지: 10MB, 64KB.

### D-45. 연결을 닫는 오류 응답 뒤에는 남은 데이터를 잠깐 받아 버린 뒤 닫는다
- 선택: 닫는 오류 응답(400·413·414·431·501·505) 뒤 **`shutdown`(쓰기 방향)** 하고 들어오는 데이터를 읽어 버리다가 상대가 닫거나 5초가 지나면 닫는다.
- 이유: 사용자 선택. 클라이언트가 아직 보내는 중에 바로 닫으면 RST로 오류 응답을 못 읽을 수 있다.
- 버린 선택지: 바로 닫기(Step 3에서 64KB 이상 본문에 `ECONNRESET` 관찰, D-30).
- 영향: 거절한 연결을 최대 몇 초 더 붙잡는다. 세부는 D-54.

### D-46. 연결 반복은 `http_conn`이 맡고 `main`은 받고 닫기만 한다
- 선택: `http_conn_serve`가 연결 하나의 요청 반복(타임아웃, 버퍼, 판정, 분기, 유지 판단, 닫기 전 정리)을 맡고 `main`은 `accept`·`close`만 한다.
- 결과: `DONE`(요청 사이 상대 닫음·유휴 타임아웃·닫는 응답과 정리 끝), `PEER_CLOSED`(요청 도중 상대 닫음), `TIMED_OUT`(요청 도중 타임아웃), `ERROR`(읽기·쓰기·소켓 설정 실패). `main`은 `ERROR`만 기록한다.
- 이유: 버퍼·유지 여부가 한 함수의 지역 상태라 단순하다.
- 버린 선택지: `main`이 요청 하나 처리 함수를 반복 호출, `/echo` 전용 모듈. Step 5에서 D-57로 대체됐다.

### D-47. 8KB 버퍼 하나를 쓰고 남은 바이트는 앞으로 옮긴다 (D-14 갱신)
- 선택: 연결마다 8KB 버퍼 하나를 두고, 파서를 부를 때 맨 앞은 처리하지 않은 요청의 시작이다. 응답 뒤 남은 바이트(다음 요청 조각)를 맨 앞으로 옮기고 먼저 파서를 부른 뒤 모자랄 때만 `read`한다. 소켓에서는 남은 본문 길이까지만 읽는다.
- 파서: 상태 없는 함수는 그대로이고 입력이 "현재 요청 시작부터 받은 바이트"로 바뀐다. `OK`이면 머리 길이를 `http_request`에 함께 돌려준다.
- 이유: 파서·버퍼 계약을 거의 유지하며 바이트가 섞이는 곳을 머리 읽기 한 군데로 좁힌다. 비용은 요청마다 최대 8KB 복사다.
- 버린 선택지: 시작 위치만 옮기기, 본문용 64KB 버퍼 추가.

### D-48. 요청 판정 순서: 크기 → 형식 → 본문 길이 (D-15 갱신)
- 선택: 아래 순서에서 **첫 번째로 걸린 결과**를 쓴다. 순서 1~3은 머리가 끝나기 전에도 읽을 때마다 본다. 순서 1~7은 모두 응답 뒤 닫는다. 순서 8은 D-51을 따른다.

| 순서 | 검사 | 결과 |
| ---- | ---- | ---- |
| 1 | 대상이 2048바이트 초과 (대상은 첫 SP 다음부터 다음 SP·`\r`·`\n`·NUL 또는 받은 바이트 끝 전까지) | 414 |
| 2 | 줄 바꿈·NUL 오류 (D-19) | 400 |
| 3 | 8KB 안에 종료 빈 줄 없음 | 431 |
| 4 | D-15 표 2~9행 (7행 헤더 101개만 431) | 400·505·501·431 |
| 5 | `Transfer-Encoding` 있음 (마지막 코딩이 `chunked`면 501, 아니면 400) | 501·400 |
| 6 | `Content-Length` 형식 오류 (D-49) | 400 |
| 7 | `Content-Length` > 1048576 | 413 |
| 8 | 경로·메서드 분기 (D-50) | 200·301·400·403·404·405·500 |

- 전송 코딩: 모든 `Transfer-Encoding` 값을 이어 쉼표로 나눠 마지막 요소를 대소문자 없이 `chunked`와 비교한다. 빈 값은 400, `chunked;x=1`은 `chunked`가 아니다. `Content-Length`가 함께 있어도 순서 5가 먼저다.
- 이유: 대상 길이로 바로 414를 내면 도착이 어떻게 나뉘어도 결과가 같고 긴 URI가 항상 414다.
- 영향: 크기를 형식보다 먼저 보므로 `BREW /<3000바이트> HTTP/2.0`은 414다. 헤더 줄 형식 오류와 101번째 헤더는 먼저 만난 쪽이 결과다.
- 요청 앞 빈 줄: 덧붙은 빈 줄도 D-15대로 **400 후 닫는다**. RFC 9112 2.2의 "빈 줄 하나 무시" 권고(SHOULD)는 따르지 않는다(사용자 선택).

### D-49. 본문 길이는 `Content-Length` 숫자 하나로만 정한다
- 선택: `Content-Length`가 **정확히 하나**이고 **숫자로만** 되어 있을 때만 받는다. 빈 값, 부호, 숫자 아닌 글자, 쉼표 목록, 같은 이름 두 번(값이 같아도)은 **400 + 닫기**다. 앞의 0은 허용하고, 1048576을 넘으면 자릿수와 관계없이 413이다.
- 없음: `Content-Length`·`Transfer-Encoding`이 모두 없으면 본문 길이는 0이다(메서드 무관, RFC 9112 6.3). `GET`에 본문이 있어도 길이만큼 읽어 버린다.
- 이유: 길이가 틀리면 다음 요청 위치를 알 수 없어 RFC 9112 6.3이 400과 닫기를 요구한다. 같은 값 중복(MAY 허용)은 D-15처럼 엄격하게 거절한다.

### D-50. `/echo` 판정과 본문 처리 순서
- 선택: 첫 `?` 앞이 **정확히 `/echo`**일 때만 `/echo`다(`/echo/`는 파일 주소). 루트에 `echo` 파일이 있어도 `/echo`가 먼저다.
- 분기: `POST /echo` → 200. `GET /echo` → 405 `Allow: POST`. 그 밖의 `POST` → 파일 시스템을 보지 않고 405 `Allow: GET`(없는 파일도 405). `GET` → 정적 파일(D-28).
- 순서: `/echo`만 머리를 먼저 보낸다(D-39). 나머지는 **본문을 다 읽어 버린 뒤** 판정·응답한다. 버리는 도중 상대가 닫거나 타임아웃이면 응답 없이 닫는다(D-53).
- 이유: 응답 전에 본문을 끝까지 읽으면 "응답을 보냈다 = 다음 요청 위치를 안다"가 되어 유지 판단(D-51)이 단순하다.
- `Expect: 100-continue`: 1.1이고 `Content-Length` > 0이면 D-48 순서 1~7 통과 뒤 본문을 읽기 직전에 `100 Continue`를 보낸다. 1.0·다른 기대 값은 무시한다(사용자 선택, RFC 9110 10.1.1). 100 쓰기 실패는 `ERROR`, 100 뒤 본문 수신 실패는 최종 응답 없이 닫는다. `Expect` 헤더가 여러 개면 첫 값만 본다(사용자 선택).
- `/echo` 응답 `Content-Type`은 항상 `application/octet-stream`이다(사용자 선택).

### D-51. 연결 유지는 응답 전에 한 번 정하고 `Connection` 헤더와 맞춘다
- 선택: `http_conn`이 응답 머리를 쓰기 전에 유지 여부를 한 번 정해 헤더와 동작을 맞춘다.

| 조건 | 연결 | 응답 `Connection` |
| ---- | ---- | ----------------- |
| 닫는 코드(400·413·414·431·501·505) | 닫기 + 정리(D-54) | `close` |
| 1.1, `close` 토큰 없음 | 유지 | 넣지 않음 |
| 1.1, `close` 토큰 있음 | 닫기 | `close` |
| 1.0, `keep-alive` 있고 `close` 없음 | 유지 | `keep-alive` |
| 1.0, 그 밖 | 닫기 | `close` |

- 토큰: `Connection` 값을 쉼표로 나눠 대소문자 없이 비교한다. `close`와 `keep-alive`가 함께 있으면 닫는다.
- 경계: 500과 정적 파일의 400 처리는 D-37·D-48 기준을 따른다(사용자 확인: 500 유지, 정적 400 닫기). 머리를 보낸 뒤 본문 전송·수신 실패는 헤더와 관계없이 연결만 닫는다(D-29, D-39).
- 버린 선택지: 1.1에도 `Connection: keep-alive` 넣기.

### D-52. 응답 함수는 `Allow`·`Connection`을 추가 머리 묶음으로 받는다 (D-27·D-33 갱신)
- 선택: 응답 함수가 추가 머리 묶음(`location`, `allow`, `connection`)을 받고 405·413·414·431을 더한다. `location`은 301에만, `allow`는 405에만 필수이며 어기면 `EINVAL`이다. 머리 순서는 `Date`, `Content-Type`, `Content-Length`, [`Location`], [`Allow`], [`Connection`]이다.
- `100 Continue`: 전용 함수가 `HTTP/1.1 100 Continue\r\n\r\n`만 쓴다. 다른 응답 함수는 100을 거절한다.
- D-33 갱신: `send_head`를 직접 부르는 곳은 파일 응답과 `/echo` 두 곳이다.
- 이유: 선택 머리가 늘 때마다 모든 호출을 바꾸지 않기 위해서다. 유지 판단은 `http_conn`에 둔다.

### D-53. 타임아웃은 연결 시작 때 걸고, 기다린 위치로 결과를 나눈다
- 선택: 시작 때 `SO_RCVTIMEO`와 **`SO_SNDTIMEO`(사용자 선택)**를 각각 5초로 건다. `read`가 `EAGAIN`·`EWOULDBLOCK`이면 타임아웃이고 `EINTR`은 다시 읽는다.

| 기다린 위치 | 동작 | 결과 |
| ----------- | ---- | ---- |
| 요청 사이(버퍼 비어 있음), 상대 닫음·`ECONNRESET` | 응답 없이 닫기 | `DONE` |
| 머리 도중, 버릴 본문 도중 | 응답 없이 닫기 (408 안 보냄, 사용자 선택) | `TIMED_OUT` |
| `/echo` 본문 도중 | 연결만 닫기 | `TIMED_OUT` |
| 닫기 전 정리 (D-54) | 정리 끝 | `DONE` |
| 응답 쓰기가 5초 막힘 | 연결만 닫기 | `ERROR` (`EAGAIN`) |

- 쓰기 제한: 받아 가지 않는 클라이언트가 단일 스레드 서버를 멈추는 것을 막는다(사용자 선택). Linux 실측으로는 일부라도 써지면 남은 쓰기가 다시 5초를 기다려 **약 10초 뒤** 끊긴다. 응답 전체 마감은 두지 않는다(사용자 선택).
- 한계: 시간은 `write` 한 번 단위라 조금씩 받아 가면 오래 붙잡힌다. 본문을 다 보낸 뒤에야 응답을 읽는 클라이언트는 본문이 양쪽 소켓 버퍼 합보다 크면 5초 뒤 끊긴다(`curl`·`nc`는 해당 없음).
- Step 5에서 시간 측정 방식이 D-59로 바뀌었다.

### D-54. 닫기 전 정리는 총 5초까지, 바이트 상한 없이 한다 (D-45 세부)
- 선택: 닫는 응답을 쓴 뒤 `shutdown(SHUT_WR)`하고 **상대가 닫음·읽기 오류·정리 시작부터 총 5초** 중 먼저 오는 때까지 읽어 버린다. **바이트 상한은 두지 않는다**. 남은 시간이 0 이하면 읽지 않고 끝낸다.
- 오류: `setsockopt` 실패, `EAGAIN`·`ECONNRESET`을 포함한 읽기 오류, `shutdown` 실패는 정리를 끝낸다(`DONE`). 응답 쓰기 실패는 정리 없이 `ERROR`다. `Connection: close`·1.0 정상 닫기는 정리 없이 돌아간다.
- 이유: 바이트 상한을 두면 큰 본문을 빠르게 보내는 클라이언트에서 다시 RST가 나 D-45의 목적이 사라진다.
- 버린 선택지: 읽기 한 번 5초만 쓰기, 1MB 바이트 상한.
- 한계: `Connection: close`·1.0 정상 닫기 뒤 클라이언트가 요청을 더 보내면 RST로 마지막 응답이 유실될 수 있다.
