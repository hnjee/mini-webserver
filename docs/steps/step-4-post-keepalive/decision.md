## 결정

### D-36. 파일 주소로 온 `POST`와 `GET /echo`는 405로 응답한다 (D-30 대체)
- 선택: `/echo` 밖으로 온 `POST`는 **405와 `Allow: GET`**, `GET /echo`는 **405와 `Allow: POST`**로 응답한다. 405를 보내더라도 본문은 **`Content-Length`만큼 읽고 버린다**.
- 이유: 사용자 선택. 파일은 읽기만 하는 대상이라 "주소는 있지만 그 방식은 안 받는다"는 405가 HTTP 뜻에 맞다. 본문을 읽는 것은 keep-alive에서 다음 요청의 시작을 찾기 위해서다.
- 버린 선택지: 파일 응답 유지(D-30, 정적 파일에 `POST`가 성공하는 어색한 동작), 404(있는 파일을 없다고 답함).
- 영향: 응답 모듈에 405와 `Allow` 헤더가 더해진다. Step 3의 `POST` 파일 응답 시험은 기대값이 405로 바뀐다.
- 다시 볼 조건: Step 6에서 `/api/*` 라우팅을 앞에 둘 때.

### D-37. 오류 응답 뒤에도 요청의 끝을 알면 연결을 유지한다
- 선택: 기준은 **"다음 요청이 어디서 시작하는지 아는가"**다. 404·403·405·301·500은 유지하고(500은 사용자 확인), 요청이 망가졌거나 본문을 다 읽지 못한 400·413·414·431·501·505는 **응답 뒤 닫는다**(431은 D-42에서 추가).
- 이유: 사용자 선택. 오류 하나(예: 브라우저가 자동으로 요청하는 `/favicon.ico`의 404)마다 연결을 끊으면 keep-alive가 비효율적이다. 코드별 분기는 간단히 처리할 수 있다.
- 버린 선택지: 오류면 모두 닫기(단순하지만 404마다 연결을 다시 맺음).
- 영향: 닫는 응답에는 `Connection: close`를 넣는다. 머리를 보낸 뒤 본문 전송이 실패하면 지금처럼 연결만 닫는다(D-29).
- 다시 볼 조건: ⑤ 크기 상한에서 새 오류 코드(예: 431)를 정할 때 같은 기준으로 분류한다.

### D-38. HTTP/1.0도 `Connection: keep-alive`를 보내면 연결을 유지한다
- 선택: HTTP/1.1은 `Connection: close`가 없으면 **유지**한다. HTTP/1.0은 `Connection: keep-alive`가 있을 때만 유지하고, 응답에도 **`Connection: keep-alive`**를 넣는다. 그 밖에는 응답 뒤 닫는다.
- 이유: 사용자 선택. HTTP/1.0에서도 선택적으로 연결을 유지할 수 있고, 비용이 작다. `ab -k`(HTTP/1.0 + keep-alive)로 연결 유지 여부에 따른 처리량을 비교할 수 있다.
- 버린 선택지: 1.0은 항상 닫기(단순하지만 `ab -k`에서 연결 유지 안 됨).
- 영향: D-37에서 닫기로 한 오류 응답은 버전과 관계없이 닫는다.

### D-39. 본문은 모아 두지 않고 조각으로 흘려보낸다
- 선택: `/echo`는 **응답 머리를 먼저** 보내고(`Content-Length` = 요청 본문 길이), 본문을 **고정 크기 조각**으로 읽는 대로 돌려준다. 405 등에서 버릴 본문도 조각으로 읽고 버린다.
- 이유: 사용자 선택. Step 3 큰 파일 전송(D-22)과 같은 구조여서 일관되고, 본문 크기와 관계없이 메모리가 고정된다.
- 버린 선택지: 본문 전체를 모은 뒤 응답(흐름은 단순하지만 본문 크기만큼 메모리를 쓰고, 동시 연결에서 배로 늘어남).
- 영향: 머리를 보낸 뒤 본문 수신·전송이 실패하면 **연결만 닫는다**(D-29와 같은 규칙). 남은 바이트 보관 방식과 조각 크기는 설계에서 정한다.

### D-40. 타임아웃은 소켓 옵션 `SO_RCVTIMEO`로 건다
- 선택: 연결을 받으면 소켓에 **`SO_RCVTIMEO`**를 한 번 설정한다. `read()`가 그 시간을 넘겨 기다리면 실패로 돌아오고, 서버는 연결을 닫는다.
- 이유: 사용자 선택. 지금 `read()` 반복 흐름을 그대로 두는 가장 작은 변경이다. 필요하면 나중에 바꾼다.
- 버린 선택지: `read()` 전마다 `poll()`로 확인(이벤트 루프와 이어지지만 지금 흐름이 바뀜).
- 영향: 시간은 **한 번의 기다림** 단위로 잰다. 조금씩 계속 보내는 느린 클라이언트(slowloris)는 막지 못하며, 한계로 둔다.
- 다시 볼 조건: Step 5에서 `poll`·`epoll` 기반 이벤트 루프를 고를 때.

### D-41. 타임아웃은 5초로 한다
- 선택: `read()` 한 번의 기다림이 **5초**를 넘으면 연결을 닫는다(D-40).
- 이유: 사용자 선택. 나눠 보내는 시험(TC-2 `sleep 1`)에 여유가 충분하고, Step 5 전 한 번에 하나씩 처리하는 구조에서 브라우저 대기도 짧다.
- 버린 선택지: 2초(`sleep 1` 시험과 여유가 작음), 60초 이상(Step 5 전 브라우저가 오래 멈추고 시험이 길어짐).
- 다시 볼 조건: Step 5에서 동시성을 넣은 뒤.

### D-42. 요청 머리가 너무 크면 431로 응답한다 (D-09 갱신)
- 선택: 요청 머리가 **8KB를 넘거나 헤더가 100개를 넘으면** 400 대신 **431 Request Header Fields Too Large**로 응답하고 닫는다. 8KB·100개 상한은 그대로다.
- 이유: 사용자 선택. Step 4에서 414(URI)·413(본문)을 넣으므로, 크기 초과를 모두 전용 코드로 맞춰 "크기 초과는 전용 코드, 형식 오류는 400"으로 정리한다.
- 버린 선택지: 400 유지(표준 위반은 아니지만 형식 오류와 구분되지 않음).
- 영향: Step 2의 8KB 초과·헤더 100개 초과 시험은 기대값이 431로 바뀐다. D-37에 따라 응답 뒤 닫는다.

### D-43. URI가 2KB를 넘으면 414로 응답한다
- 선택: 요청 줄의 대상(쿼리 포함)이 **2048바이트를 넘으면** **414 URI Too Long**으로 응답하고 닫는다(D-37).
- 이유: 사용자 선택. 8KB 머리 상한과 따로 두어야 긴 URI가 **항상 414**로 일관되게 거절된다. 2KB는 흔히 쓰는 기준이고 헤더 자리(6KB)도 남는다.
- 버린 선택지: 별도 상한 없이 8KB가 넘친 위치로 414·431을 나눔(8KB 안의 긴 URI가 경로 길이 400(D-23)과 섞임).
- 영향: 2KB 안의 경로는 Linux 경로 최대 길이를 넘지 않으므로, Step 3의 "경로가 너무 길면 400"은 방어용으로만 남는다. 요청 줄이 끝나기 전에 2KB를 넘으면 바로 거절할지는 설계에서 정한다.

### D-44. 본문이 1MB를 넘으면 413으로 응답한다
- 선택: `Content-Length`가 **1048576바이트(1MB)를 넘으면** 본문을 받기 전에 **413 Content Too Large**로 응답하고 닫는다(D-37).
- 이유: 사용자 선택. 폼 전송과 `/echo` 시험에 충분하고 여러 조각이 오가 조각 전송(D-39)도 시험된다. 기존 `www/large.bin`(4MB)이 그대로 413 시험 재료가 된다.
- 버린 선택지: 10MB(413 시험용 파일을 따로 만들어야 함), 64KB(조각 전송을 시험하기 어려움).
- 영향: 거절할 때 아직 오는 본문 때문에 생기는 연결 재설정(RST)은 따로 정한다.

### D-45. 연결을 닫는 오류 응답 뒤에는 남은 데이터를 잠깐 받아 버린 뒤 닫는다
- 선택: D-37에서 닫기로 한 오류 응답(400·413·414·431·501·505)을 보낸 뒤 **쓰기 방향만 먼저 닫고(`shutdown`)**, 들어오는 데이터를 읽어 버리다가 상대가 닫거나 **5초 타임아웃(D-41)**이 지나면 닫는다.
- 이유: 사용자 선택. 클라이언트가 아직 보내는 중에 바로 닫으면 연결 재설정(RST)으로 **오류 응답을 못 읽을 수 있다**. 413·414로 거절 이유를 알리려는 목적을 지킨다.
- 버린 선택지: 바로 닫고 한계로 둠(Step 3에서 64KB 이상 본문에 `ECONNRESET` 관찰, D-30).
- 영향: 거절한 연결을 최대 몇 초 더 붙잡으며, Step 5 전에는 그동안 다른 요청이 기다린다. 버릴 바이트 수 상한 같은 세부는 설계에서 정한다.

### D-46. 연결 반복은 `http_conn`이 맡고 `main`은 받고 닫기만 한다
- 선택: `http_conn_serve`가 **연결 하나의 요청 반복**(타임아웃 설정, 버퍼, 판정, 분기, 유지 판단, 닫기 전 정리)을 모두 맡는다. `main`은 지금처럼 `accept`와 `close`만 한다. `/echo`와 본문 읽기·버리기도 `http_conn` 안에 둔다.
- 모듈: `http_parser`는 머리 판정에 본문 길이·`Connection` 토큰을 읽는 **순수 함수**를 더하고, `http_response`는 `Allow`·`Connection` 값을 받는다(D-52). `static_file`·`io`는 바뀌지 않는다.
- 결과: `DONE`(요청 사이에 상대가 닫음, 유휴 타임아웃, 닫는 응답과 정리 끝), `PEER_CLOSED`(요청 도중 상대가 닫음), `TIMED_OUT`(요청 도중 타임아웃), `ERROR`(읽기·쓰기·소켓 설정 실패, `errno` 보존). `main`은 `ERROR`만 기록한다.
- 이유: 버퍼와 유지 여부가 **한 함수의 지역 상태**라 수명이 단순하고, 유지·닫기·정리 정책이 한 곳에 모인다. Step 5에서 스레드·프로세스 방식이면 이 함수를 그대로 쓴다.
- 버린 선택지: `main`이 요청 하나 처리 함수를 반복 호출(버퍼가 `main`에 드러나고 유지 판단이 두 모듈로 나뉨), `/echo` 전용 모듈(본문이 연결 버퍼에 걸쳐 있어 버퍼를 넘겨야 하고 호출자가 하나뿐).
- 다시 볼 조건: Step 5에서 이벤트 루프를 고를 때(연결 상태를 함수 밖 구조체로 옮겨야 함).

### D-47. 8KB 버퍼 하나를 쓰고 남은 바이트는 앞으로 옮긴다 (D-14 갱신)
- 선택: 연결마다 **8KB 버퍼 하나**를 둔다. 파서를 부르는 시점에 버퍼 맨 앞은 **아직 처리하지 않은 요청의 시작**이다. 응답을 마치면 본문 뒤에 남은 바이트(다음 요청 조각)를 **맨 앞으로 옮기고**, 그 바이트로 먼저 파서를 부른 뒤 모자랄 때만 `read`한다.
- 본문: 소켓에서는 **남은 본문 길이까지만** `read`한다. 그래서 다음 요청 바이트가 섞이는 곳은 머리를 읽을 때뿐이다. 두 경우로 나뉜다.
  - 본문 전체가 이미 버퍼에 있음: `read`하지 않는다. 다음 요청은 `머리 길이 + Content-Length` 위치부터이고, 그 뒤 바이트를 맨 앞으로 옮긴다.
  - 본문 일부만 있음: 버퍼 안의 본문 조각을 먼저 돌려주거나 버린 뒤, 이 버퍼를 **조각 버퍼(최대 8KB)**로 다시 쓴다. 이때 버퍼에 다음 요청 바이트는 없다. 요청 정보는 `http_request` 안에 복사되어 있어 버퍼를 다시 써도 망가지지 않는다.
- 파서(D-14): 상태 없는 함수는 그대로다. 입력의 뜻이 "연결에서 받은 전체"에서 **"현재 요청 시작부터 받은 바이트"**로 바뀌고, `OK`이면 종료 빈 줄을 포함한 **머리 길이**를 `http_request`의 필드로 함께 돌려준다(호출 형태는 그대로).
- 이유: 파서·버퍼 계약을 거의 그대로 두면서 바이트가 섞이는 곳을 한 군데로 좁힌다. 옮기는 비용은 요청마다 최대 8KB 복사다.
- 버린 선택지: 시작 위치만 옮기기(복사는 없지만 위치·남은 칸 계산이 늘고 끝에 닿으면 결국 옮겨야 함), 본문용 64KB 버퍼 추가(시스템 콜은 줄지만 연결마다 메모리가 늘어 Step 5에 불리).

### D-48. 요청 판정 순서: 크기 → 형식 → 본문 길이 (D-15 갱신)
- 선택: 아래 순서로 보고 **첫 번째로 걸린 결과**를 쓴다. 순서 1~3은 머리가 끝나기 전에도 읽을 때마다 본다. 순서 1~7의 결과는 **모두 닫는다**(D-37). 순서 8은 D-51 표를 따른다(정적 판정 400만 닫고, 200·301·403·404·405·500은 유지).

| 순서 | 검사 | 결과 |
| ---- | ---- | ---- |
| 1 | 대상이 2048바이트를 넘는다. 대상은 첫 SP 다음 바이트부터 다음 SP·`\r`·`\n`·NUL 또는 받은 바이트 끝 전까지다 (머리 완성 전에도) | 414 |
| 2 | 줄 바꿈·NUL 오류 (D-19) | 400 |
| 3 | 8KB 안에 종료 빈 줄이 없다 (8KB 미만이면 더 읽음) | 431 |
| 4 | D-15 표의 2~9행. 그중 D-15 7행(헤더 101개)만 431 | 400·505·501·431 |
| 5 | `Transfer-Encoding`이 있다 (마지막 코딩이 `chunked`면 501, 아니면 400, 사용자 선택) | 501·400 |
| 6 | `Content-Length` 형식 오류 (D-49) | 400 |
| 7 | `Content-Length` > 1048576 | 413 |
| 8 | 경로·메서드 분기 (D-50) | 200·301·400·403·404·405·500 |

- 전송 코딩 토큰: 모든 `Transfer-Encoding` 헤더 값을 받은 순서로 이어 쉼표로 나누고, 앞뒤 공백을 빼고, 빈 요소는 건너뛴 뒤 마지막 요소를 **대소문자 없이** `chunked`와 비교한다. 요소가 하나도 없으면(빈 값) 400이다. 매개변수가 붙은 `chunked;x=1`은 `chunked`가 아니다. `Content-Length`가 함께 있어도 순서 5가 먼저다.
- 이유: 대상 길이로 **바로** 414를 내면 긴 URI는 8KB가 차기 전에 항상 414가 되어 D-43의 목적을 지킨다. 순서 1은 첫 줄 끝 전까지만 세므로 순서 2의 오류가 더 앞에 있으면 순서 1이 걸릴 수 없어, **도착이 어떻게 나뉘어도 결과가 같다**.
- 영향: 크기를 형식보다 먼저 보므로 `BREW /<3000바이트> HTTP/2.0`은 501·505가 아니라 414다. 대상 뒤 버전 자리가 길면(`GET / HTTP/1.1<긴 글자>`) 대상은 `/`라 414가 아니고 순서 3·4로 간다. 헤더 줄 형식 오류와 101번째 헤더는 줄 순서대로 먼저 만난 쪽이 결과다.
- 버린 선택지: 머리 완성 뒤에만 414 판정(종료 빈 줄 없이 긴 URI가 431이 되어 D-43과 어긋남).
- 요청 앞 빈 줄: `Content-Length` 밖에 덧붙은 빈 줄도 D-15대로 **400 후 닫는다**. RFC 9112 2.2의 "빈 줄 하나 무시" 권고(SHOULD)는 따르지 않는다(사용자 선택, HTTP/1.1 클라이언트는 덧붙이면 안 됨).

### D-49. 본문 길이는 `Content-Length` 숫자 하나로만 정한다
- 선택: `Content-Length`가 **정확히 하나**이고 값이 **숫자로만** 되어 있을 때만 받는다. 빈 값, 부호(`+`·`-`), 숫자 아닌 글자, 쉼표 목록(`5, 5`), 같은 이름 두 번(값이 같아도)은 **400 + 닫기**다. 앞의 0은 허용한다.
- 큰 값: 1048576을 넘는 순간 413이다. 자릿수가 아무리 길어도 넘침 없이 413이 된다.
- 없음: `Content-Length`와 `Transfer-Encoding`이 모두 없으면 본문 길이는 **0**이다(메서드 무관, RFC 9112 6.3). `GET`에 본문이 있어도 길이만큼 읽어 버린다.
- 이유: 길이가 틀리면 다음 요청 위치를 알 수 없어 RFC 9112 6.3이 400과 닫기를 요구한다. 같은 값 중복은 RFC가 받아도 되지만(MAY) D-15처럼 엄격하게 두어 경우를 줄인다.
- 버린 선택지: 같은 값 중복 허용(분기가 늘고 `curl`·브라우저·`ab`는 보내지 않음). 판정은 `http_parser`의 순수 함수에 두어 소켓 없이 시험한다.

### D-50. `/echo` 판정과 본문 처리 순서
- 선택: 대상에서 첫 `?` 앞이 **정확히 `/echo`**일 때만 `/echo`다(`/echo?x=1` 포함, `/echo/`는 파일 주소, D-24와 같은 쿼리 규칙). 루트에 `echo` 파일이 있어도 `/echo`가 먼저다.
- 분기: `POST /echo` → 200. `GET /echo` → 405 `Allow: POST`. 그 밖의 `POST` → 파일 시스템을 보지 않고 405 `Allow: GET`(없는 파일도 405, D-36 문구대로). `GET` → 정적 파일(D-28).
- 순서: `/echo`만 **머리를 먼저** 보내고 본문을 조각으로 돌려준다(D-39). 나머지는 **본문을 다 읽어 버린 뒤** 판정·응답한다. `GET`도 버리기 → `static_file_open` 순서라 버리기가 실패할 때 열린 파일이 없다(D-29). 버리는 도중 상대가 닫거나 타임아웃이면 응답 없이 닫는다(D-53).
- 이유: 응답 전에 본문을 끝까지 읽으면 "응답을 보냈다 = 다음 요청 위치를 안다"가 되어 유지 판단(D-51)이 단순하다. 본문 상한이 1MB라 늦게 알리는 비용도 작다.
- 버린 선택지: 405를 먼저 보내고 버리기(오류를 빨리 알리지만, 버리다 실패하면 이미 보낸 유지 응답과 실제 동작이 어긋남).
- `Expect: 100-continue`: HTTP/1.1 요청에 이 값(대소문자 무시)이 있고 `Content-Length`가 0보다 크면, D-48 순서 1~7을 통과한 뒤 **본문을 읽기 직전**에 D-52의 전용 함수로 `100 Continue`를 보낸다. 1.0 요청과 다른 기대 값은 무시한다(사용자 선택, RFC 9110 10.1.1). 100 쓰기가 실패하면 `ERROR`, 100 뒤 본문 수신이 실패하면 최종 응답 없이 닫는다(D-53).
- `Expect` 값이 여러 개일 때: 첫 `Expect` 헤더 값만 본다. 다른 형태면 100을 보내지 않고, 클라이언트는 잠시 기다린 뒤 본문을 보낸다(사용자 선택, Step 4 구현 검증 후).
- `/echo` 응답의 `Content-Type`은 요청과 관계없이 **`application/octet-stream`**이다(사용자 선택, 시험용 주소라 고정 값이 단순).

### D-51. 연결 유지는 응답 전에 한 번 정하고 `Connection` 헤더와 맞춘다
- 선택: `http_conn`이 응답 머리를 쓰기 **전에** 유지 여부를 한 번 정하고, 그 값으로 `Connection` 헤더와 이후 동작을 함께 정한다.

| 조건 | 연결 | 응답 `Connection` |
| ---- | ---- | ----------------- |
| 닫는 코드(400·413·414·431·501·505) | 닫기 + 정리(D-54) | `close` |
| 1.1, `close` 토큰 없음 | 유지 | 넣지 않음 |
| 1.1, `close` 토큰 있음 | 닫기 | `close` |
| 1.0, `keep-alive` 토큰 있고 `close` 없음 | 유지 | `keep-alive` |
| 1.0, 그 밖 | 닫기 | `close` |

- 토큰: 모든 `Connection` 헤더 값을 쉼표로 나누고 앞뒤 공백을 뺀 뒤 **대소문자 없이** 비교한다(`Keep-Alive, Upgrade`, `CLOSE`). `close`와 `keep-alive`가 함께 있으면 닫는다.
- 경계: 500(파일 열기 실패 등)은 요청 끝을 알므로 D-37 기준대로 **유지**한다(사용자 확인). 정적 파일의 400(`/` 없는 대상, 긴 경로)도 잘못된 요청이므로 코드 목록대로 닫는다(사용자 확인). 머리를 보낸 뒤 본문 전송·수신이 실패하면 헤더 값과 관계없이 **연결만 닫는다**(D-29, D-39).
- 이유: 판단이 한 곳에 있어 헤더와 실제 동작이 어긋날 자리가 없다. 1.1 유지 응답에 헤더를 넣지 않는 것은 그것이 1.1의 기본값이라서다.
- 버린 선택지: 1.1에도 `Connection: keep-alive` 넣기(해는 없지만 기본값 중복).

### D-52. 응답 함수는 `Allow`·`Connection`을 추가 머리 묶음으로 받는다 (D-27·D-33 갱신)
- 선택: `send_head`·`send_status`·`send`가 **추가 머리 묶음**(`location`, `allow`, `connection`) 하나를 인자로 받는다. 상태는 **405·413·414·431**을 더한다. `connection`은 문자열이 아닌 **열거형**(`close`·`keep-alive`·넣지 않음)이다.
- 계약: `location`은 301일 때만, `allow`는 405일 때만 있어야 하고 반드시 있어야 한다. 어기면 아무것도 쓰지 않고 -1(`EINVAL`). `send`는 `location`·`allow`를 받지 않는다(있으면 `EINVAL`, 301·405는 `send_status`로). 머리 순서는 `Date`, `Content-Type`, `Content-Length`, [`Location`], [`Allow`], [`Connection`], 빈 줄이다.
- `100 Continue`: **전용 함수 하나**가 `HTTP/1.1 100 Continue\r\n\r\n`만 쓴다(`Date`·`Content-Length`·본문 없음, RFC 9110 8.6·15.2). `send_head`·`send_status`·`send`는 100을 `EINVAL`로 거절한다. 100 쓰기가 실패하면 `http_conn`은 `ERROR`로 끝낸다.
- D-33 갱신: `send_head`를 직접 부르는 곳은 파일 응답과 `/echo`(본문이 소켓에서 오므로) 두 곳이다. 상태 문구 본문 응답은 여전히 `send_status`만 쓴다.
- 이유 문구: 405 `Method Not Allowed`, 413 `Content Too Large`(RFC 9110), 414 `URI Too Long`, 431 `Request Header Fields Too Large`. 상태 응답 본문·길이는 여전히 `send_status` 하나가 만든다(D-33).
- 이유: 선택 머리가 셋이 되어 인자를 하나씩 붙이면 호출마다 `NULL`이 늘고 다음 머리 때 또 모든 호출이 바뀐다. 유지 판단은 `http_conn`에 두고 응답 모듈은 값만 쓴다.
- 버린 선택지: 인자 세 개 추가(호출이 길어지고 순서 실수 가능), 응답 모듈이 요청을 보고 `Connection`을 정함(유지 판단이 두 곳이 됨).

### D-53. 타임아웃은 연결 시작 때 걸고, 기다린 위치로 결과를 나눈다
- 선택: `http_conn_serve`가 시작할 때 `SO_RCVTIMEO`와 **`SO_SNDTIMEO`(쓰기)** 를 각각 5초로 건다(쓰기는 사용자 선택). 실패하면 응답 없이 `ERROR`로 돌아간다. `read`가 -1이고 `errno`가 `EAGAIN`·`EWOULDBLOCK`이면 **타임아웃**, `EINTR`은 다시 읽는다(기다림이 다시 5초가 됨).

| 기다린 위치 | 동작 | 결과 |
| ----------- | ---- | ---- |
| 요청 사이 (버퍼 비어 있음). 상대가 닫음(0)·`ECONNRESET` 포함 | 응답 없이 닫기 | `DONE` |
| 머리 도중, 버릴 본문 도중 | 응답 없이 닫기 (408 안 보냄, 사용자 선택) | `TIMED_OUT` |
| `/echo` 본문 도중 (머리 보낸 뒤) | 연결만 닫기 | `TIMED_OUT` |
| 닫기 전 정리 (D-54) | 정리 끝 | `DONE` |
| 응답 쓰기(100·머리·본문)가 5초 막힘 | 연결만 닫기 | `ERROR` (`EAGAIN`·`EWOULDBLOCK`, `main`이 기록) |

- 이유: 연결 처리 함수 안에서 걸면 `socketpair` 단위 시험도 같은 시간 제한을 받는다. 결과를 나누면 시험에서 원인을 구분할 수 있다.
- 쓰기 시간 제한: `write`가 5초 넘게 막히면 -1(`EAGAIN`·`EWOULDBLOCK`)이 되고, `io_write_all`은 지금처럼 실패를 돌려준다. 100·머리·본문 어디서 막혀도 **연결만 닫는다**(머리 뒤라면 D-29와 같다). 결과는 `ERROR`다. 응답을 받아 가지 않는 클라이언트 하나가 단일 스레드 서버 전체를 멈추는 일을 막는다(사용자 선택).
- 실측(Linux): 막힌 `write`가 5초 동안 일부라도 썼다면 실패 대신 쓴 바이트 수를 돌려주고, 남은 쓰기가 다시 5초를 기다린 뒤 `EAGAIN`이 난다. 그래서 받아 가지 않는 클라이언트는 **약 10초 뒤** 끊긴다. 응답 전체 마감은 두지 않고 이대로 둔다(사용자 선택, Step 4 구현 후).
- 한계: 시간은 `write` 한 번 단위라 조금씩 받아 가는 클라이언트는 오래 붙잡을 수 있다. `/echo`는 받는 대로 돌려주므로 **본문을 다 보낸 뒤에야 응답을 읽는 클라이언트**는 본문이 양쪽 소켓 버퍼 합보다 크면 5초 뒤 끊긴다. `curl`·`nc`는 보내면서 읽어 해당하지 않는다.
- 시험: 큰 `/echo` 단위 시험은 `fork`해서 보내는 쪽과 읽는 쪽을 나눈다(`socketpair` 버퍼는 수백 KB라 한 프로세스에서 쓰고 읽으면 바로 막힘). 다시 볼 조건: Step 5·7.

### D-54. 닫기 전 정리는 총 5초까지, 바이트 상한 없이 한다 (D-45 세부)
- 선택: 닫는 코드 응답을 다 쓴 뒤 `shutdown(SHUT_WR)`하고, 연결 버퍼로 읽어 버리기를 **상대가 닫음·읽기 오류·정리 시작부터 총 5초** 중 먼저 오는 때까지 한다. 버릴 **바이트 수 상한은 두지 않는다**.
- 시간: 단조 시계로 재고, `read`마다 남은 시간으로 `SO_RCVTIMEO`를 다시 건다. `timeval {0,0}`은 "제한 없음"이므로 **남은 시간이 0 이하면 읽지 않고 끝낸다**. 양수인 남은 시간이 `{0,0}`으로 내려가지 않게 한다(1µs 미만은 1µs로 올린다).
- 정리 중 오류: `setsockopt` 실패는 제한 없는 `read`로 가지 않고 정리를 끝낸다. `EAGAIN`·`EWOULDBLOCK`, `ECONNRESET`을 포함한 모든 읽기 오류도 정리를 끝낸다(`DONE`). `EINTR`은 남은 시간을 다시 계산해 계속한다.
- 실패: `shutdown` 실패(상대가 이미 끊음)는 오류로 보지 않고 정리를 끝낸다(`DONE`). 응답 쓰기가 실패하면 정리 없이 `ERROR`다. `Connection: close`·1.0으로 닫는 정상 응답은 본문을 다 읽었으므로 정리 없이 돌아간다.
- 이유: 시간만으로 붙잡는 길이가 정해진다. 바이트 상한을 두면 큰 본문을 빠르게 보내는 클라이언트(4MB를 `nc`로 보내기)에서 다시 RST가 나 D-45의 목적이 사라진다.
- 버린 선택지: 읽기 한 번 5초만 사용(조금씩 보내는 상대가 정리를 끝없이 늘림), 1MB 바이트 상한(빠른 송신자에 RST).
- 한계: `Connection: close`·1.0 정상 닫기 뒤 클라이언트가 규칙을 어기고 요청을 더 보냈다면, 읽지 않은 데이터 때문에 RST가 나 마지막 응답이 유실될 수 있다.
