## 결정

### D-68. 종료 신호는 핸들러가 표시하고 eventfd로 루프를 깨운다 (채택)
- 선택: `main`이 듣는 소켓을 열기 전에 `sigaction`으로 `SIGINT`·`SIGTERM` 핸들러를 건다. 핸들러는 **errno 저장 → 처음 받은 신호 번호 기록(`volatile sig_atomic_t`) → 공개된 eventfd에 `write` 한 번(결과 무시) → errno 복원**만 한다. 잠금·`malloc`·stdio는 쓰지 않는다.
- 스레드: 워커는 두 신호를 **막은 마스크로 만든다**. 그래서 핸들러는 루프(메인) 스레드에서만 돌고, 루프가 eventfd를 닫는 코드와 겹쳐 실행되지 않는다.
- 깨우기 순서: eventfd 공개 → 회차 맨 앞에서 정지 표시 확인 → `epoll_wait`. 확인 전에 온 신호는 표시로, 확인 뒤 온 신호는 eventfd(또는 `epoll_wait`의 `EINTR`)로 잡힌다. 루프가 시작되기 전에 온 신호도 첫 회차 확인에서 잡힌다.
- 이유: 워커 확장이 이미 쓰는 **완료 eventfd를 그대로** 깨우기 통로로 쓰므로 새 fd·새 등록이 없다. 핸들러가 async-signal-safe 함수(`write`)만 부른다.
- 버린 선택지: `signalfd`(모든 스레드에서 신호를 막아야 하고 핸들러·async-signal-safe 개념을 발표에서 설명할 거리가 사라진다), 표시만 하고 `EINTR`에 기대기(확인과 `epoll_wait` 사이에 온 신호를 놓친다).

### D-69. 정리 시작 때 듣는 소켓을 닫고, 진행 중 요청만 마치고 연결을 닫는다 (채택)
- 선택: 정지 표시를 처음 본 회차에 **듣는 소켓을 닫고**(새 연결은 거부), 바쁘지 않은 연결마다 정지를 적용한다. 바쁜 연결은 회수할 때 적용한다. 연결이 모두 정리되면 워커를 `join`하고 루프가 정상(0)으로 돌아온다.
- 연결별: **이미 시작한 요청만** 기존 5초 무진행 규칙(D-59) 안에서 마친다. 응답 머리를 아직 채우지 않았으면 `Connection: close`로 응답하고, 이미 채웠으면 끝까지 보낸 뒤 닫는다. 요청 사이 대기 또는 이전 응답 뒤 버퍼에 쌓인 **아직 시작하지 않은 다음 요청**은 바이트가 있어도 처리하지 않고 닫는다.
- 요청 경계: `http_conn_run`은 응답을 끝낸 같은 워커 차례에서 다음 요청을 파싱하지 않고 루프에 반환한다. 루프는 `SIGINT`·`SIGTERM`을 잠시 막은 상태에서 최신 정지 표시를 확인하고 다음 요청을 큐에 넣는다. 확인 전에 처리된 신호라면 넣지 않으며, 확인 뒤 도착해 보류된 신호는 요청을 넣은 직후 마스크를 복원해 처리한다. 워커 실행 중 신호를 받아도 다음 요청을 시작하기 전에 반드시 이 경계를 지난다.
- 소유: 듣는 소켓의 소유를 `main`에서 **루프로 옮긴다**. 루프는 정리 시작·서버 실패·시작 실패 모든 경로에서 닫고, `main`은 닫지 않는다.
- 이유: "새 연결 중단 → 처리 중 요청 완료 → 종료"(DESIGN Step 7)를 기존 연결 상태와 마감 위에 얹는다. 유휴 keep-alive가 종료를 막지 않는다.
- 버린 선택지: `epoll` 등록만 지우고 `main`이 끝에 닫기(정리 중 새 클라이언트가 대기열에서 최대 10초 매달린다), 버퍼 속 다음 요청까지 처리(파이프라인 클라이언트가 종료를 계속 늘린다).
- 영향: 응답 머리에 유지를 밝힌 뒤 닫는 경우는 **D-51의 정리 중 예외**다. HTTP는 유지 연결을 서버가 닫는 것을 허용한다.

### D-70. 종료 대기 상한은 10초, 넘으면 남은 연결을 강제로 닫는다 (채택)
- 선택: 정리 시작부터 **10초**가 지나면 바쁘지 않은 연결은 바로, 바쁜 연결은 현재 차례를 회수하는 즉시 닫는다(`ERROR`, `ECANCELED`). 이 뒤에는 어떤 연결도 작업 큐에 넣지 않는다. 시험은 클라이언트 수신 속도만 늦추지 않고 서버에 실제 미송신 데이터가 남은 상태를 관문으로 확인한다.
- 이유: 5초 무진행 마감은 멈춘 연결만 끝낸다. 느리지만 계속 진행하는 전송은 끝이 없으므로 전체 상한이 필요하다. 5초 마감 한 번보다 길어 정상 요청은 거의 마친다.
- 사용자 판단: 10초 안에 마치지 못한 응답은 클라이언트에서 연결이 끊긴 것으로 보인다. 응답 도중 복구할 수 없는 내부 오류가 생기면 연결을 닫는 기존 정책과 결과가 어긋나지 않는다. 다만 종료 시간 상한은 오류가 아니라 운영상 정리 정책이다.
- 버린 선택지: 상한 없음(느린 다운로드 하나가 종료를 무한히 막는다), 5초(마감 상수를 재사용하지만 막 진행을 시작한 요청을 자주 끊는다).
- 다시 볼 조건: 시연에서 10초가 길거나 짧게 느껴질 때.

### D-71. 접근 로그는 상태가 정해진 요청마다 한 줄을 stdout에 남긴다 (채택)
- 선택: 응답 상태가 정해진 요청마다 **정확히 한 줄**. 마지막 바이트를 보내면 `ok`, 그 전에 연결이 끝나면 연결 해제 때 `aborted`로 남긴다. `100 Continue`, 요청 전·머리 도중 끊김은 남기지 않는다.
- 형식: `시각 주소:포트 "메서드 대상 버전" 상태 보낸바이트 걸린ms 결과`. 판정 실패 요청은 요청 자리에 `"-"`를 쓴다.
- 출력: 접근 로그·시작·종료 알림은 **stdout(줄 버퍼)**, 연결 오류·강제 종료는 stderr. 한 줄은 고정 버퍼에 길이를 확인해 만든 뒤 stdio 호출 한 번으로 쓴다. 쓰기 실패는 무시한다.
- 이유: 요청 단위가 시연·디버깅에 가장 읽기 쉽고, 해제 때 한 번 더 확인해 줄이 빠지거나 두 번 나오지 않는다.
- 사용자 판단: 운영 중 요청 결과를 확인하고 문제를 추적하는 데 도움이 된다. 복구 후 재전송을 위한 기록은 아니다.
- 버린 선택지: 연결 단위 한 줄(keep-alive 요청이 보이지 않는다), 루프 스레드만 쓰기(차례 결과에 로그 묶음을 실어야 해 인터페이스가 커진다).

### D-72. 시작 실패와 정상 종료 모두 `main`이 자원을 풀고, 신호 종료는 0으로 끝난다 (채택)
- 선택: `realpath` 뒤 **모든 반환 경로**(설정 실패·소켓 실패·루프 실패·정상 종료)에서 `root`를 해제한다. 신호로 정리를 마치면 종료 코드 0, 시작 실패·서버 실패는 1이다.
- 이유: LSan이 보고한 4097바이트 누수(Step 6 넘김)를 없애고, ASan·valgrind가 정상 종료 경로에서 누수를 검사할 수 있다.
- 사용자 판단: SIGINT·SIGTERM으로 정리를 마친 종료는 정상 종료로 본다. SIGKILL은 이 정리 경로와 별개다.
- 버린 선택지: 신호 번호에 따른 128+N 종료 코드(쉘 관례지만 정리를 마친 정상 종료와 구분하기 어렵다).
