## 결정

### D-01. Linux 단일 실행 환경
- 선택: **Ubuntu 24.04(glibc) Docker 컨테이너**에서 빌드·실행·검증한다. 저장소는 bind mount, 실행 계정은 비root `jungle`이다.
- 이유: 개발·검증 환경을 **Linux 하나**로 통일한다.
- 버린 선택지: macOS·Linux 동시 지원, 매번 도구 설치.
- 영향: macOS에서 만든 실행 파일은 Linux 검증 증거가 아니다.

### D-02. Step 0 실행 인자와 테스트 구성
- 선택: `src/`·`tests/`를 분리하고 **별도 모듈의 POSIX `getopt`**로 `-p`·`-r`을 파싱한다. `-h`는 사용법만 출력하고 정상 종료한다. `-c`는 Step 6에서 추가한다.
- 이유: Step 0은 **설정 수용과 빌드**만 확인한다. 소켓은 Step 1이다. 테스트는 외부 프레임워크 없이 C 실행 파일을 쓴다.
- 버린 선택지: 소켓 없이 대기하는 프로세스, 한 파일에 파서 포함.
- 영향: 프록시 설정은 Step 6 전까지 받지 않는다.

### D-03. 컨테이너 내부의 전용 시험 파일 폴더
- 선택: 시험 파일은 **컨테이너 내부 고정 폴더**에 두고 정해진 파일만 다시 만든다. 경로는 사용자 입력으로 받지 않는다. 코드는 bind mount다.
- 이유: Docker Desktop의 **호스트 공유 폴더는 권한 000이 적용되지 않아** `secret.txt` 시험이 성립하지 않았다.
- 버린 선택지: 실행마다 새 폴더, 호스트 공유 폴더 그대로.
- 영향: `make fixtures`가 출력한 Linux 경로를 `-r`에 전달한다. D-32로 `sub/index.html`·`empty/`가 추가된다.
