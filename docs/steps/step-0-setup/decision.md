## 결정

### D-01. Linux 단일 실행 환경
- 선택: **Ubuntu 24.04(glibc) Docker 컨테이너**에서 빌드·실행·검증한다. 저장소는 bind mount하고 비root 계정 `jungle`로 실행한다.
- 이유: 개발·검증 환경을 **Linux 하나**로 통일한다.
- 버린 선택지: macOS·Linux 동시 지원(환경 차이 관리), 매번 도구 설치(재현 어려움).
- 영향: macOS에서 만든 실행 파일은 Linux 검증 증거가 아니다. 이후 Step도 컨테이너 기준이다.
- 다시 볼 조건: 실행 환경을 여러 OS로 넓힐 때.

### D-02. Step 0 실행 인자와 테스트 구성
- 선택: `src/`·`tests/`를 분리하고 **별도 모듈의 POSIX `getopt`**로 `-p`·`-r`을 파싱한다. `-h`는 사용법만 출력하고 정상 종료하며, `-c`는 Step 6에서 추가한다.
- 이유: Step 0은 **설정 수용과 빌드**만 확인하고 소켓은 Step 1에서 구현한다. 외부 프레임워크 없이 C 테스트 실행 파일을 쓴다.
- 버린 선택지: 소켓 없이 대기하는 프로세스(서버 실행으로 오해), 한 파일에 파서를 넣기(시험·재사용 경계 변경).
- 영향: Step 1에서 설정 파싱 뒤 소켓 루프를 연결한다. 프록시 설정은 Step 6 전까지 받지 않는다.
- 다시 볼 조건: Step 1 또는 Step 6에서 실행 계약을 확장할 때.

### D-03. 컨테이너 내부의 전용 시험 파일 폴더
- 선택: 코드는 bind mount하되 시험 파일은 **컨테이너 내부 고정 폴더**에 준비하고, 정해진 파일만 다시 만든다. 경로는 사용자 입력으로 받지 않는다.
- 이유: Docker Desktop의 **호스트 공유 폴더에서는 권한 000이 적용되지 않아** `secret.txt` 시험이 성립하지 않았다. 단일 개발자 환경이라 전용 폴더를 재사용한다.
- 버린 선택지: 실행마다 새 폴더(반복 시 폴더가 쌓임), 호스트 공유 폴더 그대로(권한 검사 불성립).
- 영향: `make fixtures`가 출력한 Linux 경로를 `-r`에 전달한다. Step 3의 D-32로 `sub/index.html`·`empty/`가 같은 폴더 아래 추가된다.
- 다시 볼 조건: 여러 사용자가 컨테이너를 공유하거나 시험 파일을 영속 관리해야 할 때.
