## 결정

### D-01. Linux 단일 실행 환경

- 상태: 채택
- 선택: Ubuntu 24.04(glibc) Docker 컨테이너에서 빌드·실행·검증한다. 저장소는 bind mount하고, 이미지의 고정 비root 계정 `jungle`로 실행한다. Dockerfile로 빌드 도구를 제공한다.
- 이유: 개발·검증 환경을 Linux 하나로 통일한다.
- 다른 선택지와 버린 이유: macOS와 Linux 동시 지원은 환경 차이를 추가로 관리해야 한다. 매번 도구를 설치하는 방식은 환경 재현이 어렵다.
- 영향: macOS에서 만든 실행 파일은 Linux 검증 증거가 아니다. Step 1 이후의 실행도 Linux 컨테이너 기준으로 한다.
- 다시 볼 조건: 실행 환경을 여러 OS로 넓히기로 결정할 때.

### D-02. Step 0 실행 인자와 테스트 구성

- 상태: 채택
- 선택: `src/`, `tests/`를 분리하고, 별도 모듈의 POSIX `getopt`로 `-p`와 `-r`을 파싱하고, `-h`는 사용법만 출력하고 정상 종료한다. 정상 인자는 설정을 출력하고 종료한다. `-c`는 Step 6에서 추가한다. 외부 프레임워크 없이 C 테스트 실행 파일을 사용하며, Linux/glibc에서 옵션 파서의 반복 호출을 지원한다.
- 이유: Step 0은 설정 수용과 빌드만 확인하고 소켓은 Step 1에서 구현한다.
- 다른 선택지와 버린 이유: 아직 소켓을 열지 않는 대기 프로세스는 서버 실행으로 오해될 수 있다. 한 파일에 파서를 넣거나 반복 호출 계약을 축소하는 방식은 테스트·재사용 경계를 바꾼다.
- 영향: Step 1에서 설정 파싱 뒤 소켓 루프를 연결한다. 프록시 설정은 Step 6 전까지 받지 않는다.
- 다시 볼 조건: Step 1 또는 Step 6에서 실행 계약을 확장할 때.

### D-03. 컨테이너 내부의 전용 시험 파일 폴더

- 상태: 채택 (현재 구현은 독립 검증 통과)
- 선택: 코드는 호스트에서 bind mount하되, 시험 파일은 컨테이너 내부의 고정 전용 폴더에 준비한다. 같은 컨테이너에서는 정해진 7개 시험 파일만 다시 만들고 다른 파일은 건드리지 않는다. 경로는 사용자 입력으로 받지 않고, 큰 파일은 4 MB로 고정한다.
- 이유: Docker Desktop의 호스트 공유 폴더에서는 `secret.txt`의 권한 000이 일반 Linux 파일처럼 적용되지 않았다. 단일 개발자 환경에 맞춰 전용 폴더를 간단히 재사용한다.
- 다른 선택지와 버린 이유: 실행마다 새 폴더를 만들면 안전하지만 같은 컨테이너에서 반복 준비할 때 폴더가 쌓인다. 호스트 공유 폴더를 그대로 쓰면 권한 검사가 성립하지 않는다.
- 영향: `make fixtures` 뒤 출력된 Linux 경로를 `-r`에 전달한다. 새 컨테이너에서는 시험 파일을 다시 준비한다. 호스트 `www/`는 입력 자료로만 사용한다. Step 3의 D-39로 `sub/index.html`과 빈 폴더 `empty/`가 같은 고정 폴더 아래 추가된다(범위 확장, 구현 전).
- 다시 볼 조건: 여러 사용자가 컨테이너를 공유하거나 시험 파일을 영속적으로 관리해야 할 때.
