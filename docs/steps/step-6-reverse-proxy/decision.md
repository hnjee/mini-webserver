## 결정

### D-60. `/api` 접두 경로를 떼고 백엔드에 전달한다
- 선택: `/api/` 요청은 백엔드의 `/`로, `/api/users`는 `/users`로 전달한다.
- 이유: 기본 Python 서버도 별도의 `/api` 폴더 없이 응답할 수 있다.
- 버린 선택지: 주소를 그대로 전달(백엔드에도 `/api` 경로 필요).

### D-61. 라우팅 규칙은 `-c` 설정 파일의 route 줄로 받는다
- 선택: `-c <파일>`은 **선택 인자**이고 없으면 프록시 없이 Step 5와 같다. 한 줄에 `route <접두 경로> <호스트:포트> [<호스트:포트> ...]` 하나이고 `#` 뒤 주석·빈 줄은 무시한다. 예: `route /api/ host.docker.internal:8001 host.docker.internal:8002`
- 검사: 접두 경로는 `/`로 시작·끝, `?`·`#`·공백·제어 문자 불가, 중복 금지. 규칙 1개 이상, 규칙마다 백엔드 1개 이상, 포트 1~65535, 호스트 255바이트 이하. 어기거나 이름 조회·파일 읽기가 실패하면 줄 번호와 함께 **시작할 때 실패**한다(exit 1).
- 주소: 호스트 이름은 시작 때 한 번만 IPv4로 바꾼다(실행 중 블로킹 조회 없음). 서버는 컨테이너, 백엔드는 호스트에서 돌아 `host.docker.internal`이 필요하다.
- 이유: DESIGN 예시를 그대로 적는 가장 작은 문법이다.
- 한계: 설정 다시 읽기, `Host` 헤더 라우팅, IPv6는 지원하지 않는다. 규칙·백엔드 수 상한은 구현에 위임한다.

### D-62. 접두 경로가 바이트 그대로 맞는 가장 긴 규칙을 고른다 (D-60 세부)
- 선택: 요청 대상이 접두 경로로 **바이트 그대로 시작**하면 맞고, 여럿이면 **가장 긴 접두**다. 맞는 규칙이 없으면 `/echo`·정적 파일이다. 전달 주소는 접두를 `/` 하나로 바꾸고 쿼리를 포함한 나머지를 그대로 둔다(`/api/users?x=1` → `/users?x=1`).
- 경계: `/api`·`/api?x`는 규칙 밖이다. 대소문자를 구분하고 퍼센트 디코딩·`.`·`..` 정규화를 하지 않는다(`/api/../a`는 `/../a`로 전달).
- 순서: 파서 결과(400·413·414·431·501·505, `HEAD`의 501)가 먼저이고, 규칙에 맞으면 405 판정(D-36)·정적 판정보다 먼저 프록시로 보낸다. `POST /api/...`도 백엔드로 간다.
- 버린 선택지: 선언 순서 우선, 정규화 뒤 매칭.

### D-63. 라운드 로빈은 규칙마다 카운터 하나이고 실패해도 다른 백엔드로 넘기지 않는다
- 선택: 규칙에 맞을 때마다 그 규칙의 카운터로 백엔드를 고르고 **곧바로 1 늘린다**(성공·실패 무관). 고른 백엔드가 실패하면 502·504로 끝나고 **재시도하지 않는다**.
- 이유: DESIGN의 "연결 실패는 502"와 "8001로 가는 요청에 504"에 맞고 재시도용 본문 보관이 필요 없다.
- 한계: 백엔드 하나만 꺼져도 그 차례의 요청은 502다. 상태 확인은 없다.

### D-64. 백엔드 연결은 요청마다 새로 맺고 HTTP/1.0 요청으로 보낸다
- 선택: 요청마다 새 논블로킹 `connect`를 하고 응답 끝·실패 때 **바로 닫는다**. 클라이언트 연결을 유지해도(D-65) 백엔드 연결은 **재사용하지 않는다**.
- 요청 줄·머리: `메서드 전달주소 HTTP/1.0`. 클라이언트 머리는 순서대로 복사하되 **홉 머리**를 빼고 `Host: <설정의 호스트:포트>`와 `Connection: close`를 붙인다. 홉 머리(요청·응답 공통)는 `Connection`·`Keep-Alive`·`Proxy-Connection`·`TE`·`Upgrade`와 모든 `Connection` 줄의 쉼표 구분 토큰(공백 제거·대소문자 무시)이 가리키는 이름이며, 요청에서는 `Host`·`Expect`도 뺀다.
- 프레이밍: 요청 `Content-Length`는 복사하지 않고 파서가 검증한 값으로 **새로 쓴다**(`Connection: Content-Length`처럼 가리켜도 어긋나지 않음). 요청 `Transfer-Encoding`은 파서가 이미 거절한다(D-48). 본문은 버퍼 속 본문 먼저, 나머지는 남은 길이만큼 조각으로 전달하고(D-39) 다음 요청 바이트는 입력 버퍼에 남긴다(D-47). 업로드 중에도 응답을 지켜본다(D-66).
- `100 Continue`: 유효한 `Expect` 요청이면 연결 성공·실패와 관계없이 본문을 기다리기 **전에** 서버가 보낸다(D-50). 최종 응답 커밋이 아니므로 그 뒤에도 502·504가 가능하다.
- 이유: 백엔드 연결 유지를 다루지 않아도 된다. 백엔드가 RFC 9112 6.1을 어기고 `Transfer-Encoding`으로 답하면 D-65대로 502다. `python3 -m http.server`는 HTTP/1.0과 `Content-Length`로 답한다.
- 한계: 요청마다 handshake 비용이 든다. `X-Forwarded-For` 같은 머리는 넣지 않는다.

### D-65. 백엔드 응답의 끝을 알 수 있으면 클라이언트 연결을 기존 규칙대로 유지한다
- 선택: 사용자 선택. 백엔드 응답 머리를 검증해 **본문 끝**을 정한다. 끝을 알면 클라이언트 연결은 D-51 규칙(D-37·D-38)을 따르고, 모르면 `Connection: close`로 EOF까지 보낸 뒤 닫는다. 모든 응답을 유지하지는 않는다.
- 검증: 아래 중 하나라도 어긋나면 **502**이고, 통과 전에는 클라이언트에 **한 바이트도 쓰지 않는다**.
  - 머리가 첫 `CRLF CRLF`까지 8KB 이내, 줄 바꿈·문자(NUL 없음, LF 앞 CR)가 정상.
  - 상태 줄은 `HTTP/1.0`·`HTTP/1.1` 뒤 공백 하나와 100~599의 숫자 세 자리, 선택적으로 `공백 + 이유 문구`(HTAB·SP·VCHAR·0x80~0xFF)만 허용한다. 1xx는 502다.
  - 머리 줄은 1자 이상 token 이름 바로 뒤 `:`이고, 값은 앞뒤 공백 제거 후 HTAB·SP·VCHAR·0x80~0xFF만 허용한다. obs-fold·이름 앞뒤 공백·머리 101줄 이상은 실패한다.
  - 프레이밍: `Transfer-Encoding` 있음, `Content-Length` 두 줄 이상(값이 같아도)·10진 아님·넘침, `Connection` 토큰이 `Content-Length`·`Transfer-Encoding`을 가리킴. 상태 코드와 무관하다.
- 본문 끝과 `Content-Length`:

| 통과한 응답 | 본문 끝 | 출력 `Content-Length` | 클라이언트 연결 |
| ----------- | ------- | --------------------- | --------------- |
| 204 | 머리 끝 | **뺀다** | D-51 규칙 |
| 304 | 머리 끝 | 있으면 그대로 | D-51 규칙 |
| 그 밖, `Content-Length` 있음 | 그 바이트 수 | 그대로 | D-51 규칙 |
| 그 밖, 없음 | 백엔드 EOF | 없음 | 닫기, `close` |

- 다시 쓰기·커밋: 상태 줄 버전만 `HTTP/1.1`로 바꾸고 홉 머리(D-64)와 204의 `Content-Length`를 빼며 D-51대로 `Connection`을 넣는다. 나머지 머리는 그대로다. 다시 쓴 머리를 출력 버퍼에 채운 순간이 **커밋**이고, 그 뒤에는 502·504로 바꿀 수 없다.
- 길이 있는 응답은 **정확히 그 바이트 수만** 중계하고 넘는 바이트는 버린다(204·304 뒤 바이트도 버림). 길이 전 EOF·읽기 오류는 두 번째 응답 없이 연결만 닫는다(`ERROR`, `EIO`, RFC 9112 6.3). 유지면 남은 요청 본문을 버린 뒤 다음 요청으로 가고, 닫기면 정리 없이 닫는다.
- 버린 선택지: 모두 유지(EOF 응답의 끝을 모름), 모두 닫기(keep-alive 정책과 어긋남), 느슨한 검증(길이 해석 불일치).
- 한계: chunked는 해석하지 않아 `Transfer-Encoding` 응답은 502다. `HEAD`는 파서가 501로 먼저 거절한다(D-35).

### D-66. 응답 머리를 커밋하기 전 실패는 502·504, 커밋 뒤 실패는 연결만 닫는다

| 상황 | 결과 |
| ---- | ---- |
| 소켓 생성·`connect` 즉시 실패, 완료 뒤 `SO_ERROR`(거부 등) | 502 |
| `connect`가 시작부터 5초 안에 안 끝남 (고정) | 504 |
| 업로드 중 요청 쓰기 실패(`EPIPE`·`ECONNRESET`) | 업로드를 멈추고 응답 머리를 계속 기다림. 머리 없이 EOF·오류면 502 |
| 업로드 중 백엔드 쓰기 5초 무진행 | 504 |
| 업로드 중 완전한 응답 머리(조기 응답) | 업로드를 멈추고 그 응답을 D-65대로 중계 |
| 응답 머리 5초 무진행 | 504 |
| 커밋 전 EOF·읽기 오류, D-65 검증 실패 | 502 |
| 커밋 뒤 본문 5초 무진행 | 응답 없이 닫기 (`ERROR`, `ETIMEDOUT`) |
| 커밋 뒤 길이 전 EOF·읽기 오류 | 응답 없이 닫기 (`ERROR`, `EIO`) |
| 길이 없는 응답의 EOF | 정상 끝, 닫기 (D-65) |

- 502·504는 백엔드 소켓을 닫고 남은 요청 본문을 버린 뒤(D-39) 상태 응답(D-33)을 보낸다. 요청 끝을 알므로 D-37·D-51 규칙으로 유지하거나 닫는다. 백엔드 머리 바이트는 클라이언트에 보내지 않는다. 클라이언트 쪽 읽기·쓰기는 D-59 그대로다.
- 조기 응답: 미송신 업로드 바이트를 버리고 응답을 중계한 뒤 유지 규칙이면 남은 본문을 버리고 다음 요청으로 간다. 요청 끝을 확보하지 못하면(클라이언트 끊김·D-59 만료) 유지하지 않는다.
- 한계: 502·504는 본문을 다 버린 뒤 보내므로 실패 시점부터 시간 안에 통보된다는 보장이 없다. 클라이언트가 본문을 5초 넘게 보내지 않으면 최종 응답 없이 닫히고(D-59), 조금씩 진행하면 총시간 상한이 없다. Step 4·5의 채택 동작이며 이번 Step에서 바꾸지 않는다.
- 관련: 연결 시간 초과를 504로 하는 것은 학습 노트([08-proxy](../../study/08-proxy.md) 「백엔드 장애 처리」)와 같다.

### D-67. 연결마다 소켓 하나만 epoll에 등록하고 업로드 중에만 두 소켓을 본다 (D-56·D-57 확장)
- 선택: 기본은 지금 기다리는 소켓 하나만 등록한다. 요청을 백엔드에 올리는 동안에만 조기 응답(D-66)을 보려고 백엔드를 읽기로도 등록한다(백엔드 쓰기 대기는 `IN|OUT`, 클라이언트 본문 대기는 두 소켓 `IN`).
- HUP·ERR: 알림만으로 백엔드를 닫거나 502로 정하지 않는다. 남은 응답을 먼저 읽고, 응답 머리 없이 실제 EOF·읽기 오류면 502, 무진행 마감이면 504다. 준비 알림만으로 마감을 늘리지 않는다.
- 연결 완료: `EINPROGRESS` 뒤에는 현재 세대 백엔드의 쓰기 준비·ERR·HUP 알림을 받은 차례에만 `SO_ERROR`로 판정한다.
- 옛 알림: 백엔드 소켓을 열고 닫을 때마다 세대 번호를 올리고, 루프가 `epoll_wait` 직후 알림의 세대를 복사해 두었다가 달라졌으면 옛 소켓 알림으로 버린다(같은 fd 번호 재사용 대비).
- 마감(D-59 확장): 연결 대기는 시작부터 5초 고정이고 504다. 업로드 중 백엔드 쓰기 무진행은 504, 클라이언트 본문 무진행은 `TIMED_OUT`이다. 응답 머리·본문 중 백엔드 무진행은 커밋 전 504·커밋 뒤 `ERROR`다. 클라이언트 출력 무진행은 `ERROR`, 실패·조기 응답 뒤 본문 버리기 무진행은 `TIMED_OUT`(저장한 502·504는 보내지 않음)이다.
- 소유: 백엔드 소켓은 `http_conn`이 만들고 끝·실패·release 때 닫는다(동시에 최대 하나). 라우팅 표는 `main`이 프로세스 종료까지 빌려준다. 백엔드 송신 버퍼 16KB·머리 버퍼 8KB는 연결 구조체 안에 둔다(연결당 약 24KB 증가).
- 버린 선택지: 항상 두 소켓 등록(헛돎), 업로드 끝까지 응답을 읽지 않기(조기 401·413을 놓침), 요청 본문을 모은 뒤 보내기(D-39 계약 변경), 백엔드 연결을 별도 구조체로 등록(수명이 두 갈래).
