## 결정

### D-60. `/api` 접두 경로를 떼고 백엔드에 전달한다
- 선택: `/api/` 요청은 백엔드의 `/`로, `/api/users`는 `/users`로 전달한다.
- 이유: 기본 Python 서버도 별도의 `/api` 폴더 없이 Step 6 예시 요청에 응답할 수 있다.
- 버린 선택지: 주소를 그대로 전달하면 백엔드에도 `/api` 경로를 마련해야 한다.
- 영향: 경로 경계와 쿼리 처리 등 세부 규칙은 D-62에 정한다.

### D-61. 라우팅 규칙은 `-c` 설정 파일의 route 줄로 받는다
- 선택: `-c <파일>`은 **선택 인자**다. 없으면 프록시 없이 Step 5와 같다. 파일은 한 줄에 `route <접두 경로> <호스트:포트> [<호스트:포트> ...]` 하나만 쓰고, `#` 뒤 주석과 빈 줄은 무시한다. 예: `route /api/ host.docker.internal:8001 host.docker.internal:8002`
- 검사: 접두 경로는 `/`로 시작하고 `/`로 끝나며 `?`·`#`·공백·제어 문자를 넣을 수 없다. 호스트는 255바이트 이하다(D-67의 16KB 버퍼 근거). 이름 조회 실패·파일 읽기 오류도 시작 실패다. 접두 경로 중복 금지, 규칙마다 백엔드 1개 이상, 포트 1~65535, 규칙 1개 이상. 어기면 줄 번호와 함께 **시작할 때 실패**한다(exit 1).
- 주소: 호스트 이름은 시작할 때 **한 번만** IPv4 주소로 바꾼다. 실행 중에는 이름 조회(블로킹)를 하지 않는다. 서버는 컨테이너 안에서, 백엔드는 호스트에서 돌기 때문에 `host.docker.internal` 같은 이름이 필요하다.
- 이유: DESIGN 예시(`/api/*` → 8001, 8002)를 그대로 적을 수 있는 가장 작은 문법이다. 글자를 표로 바꾸는 부분은 순수 함수여서 단위 시험이 쉽다.
- 버린 선택지·한계: INI·JSON 같은 일반 형식은 파서가 커진다. 설정 다시 읽기, `Host` 헤더 라우팅, IPv6는 지원하지 않는다. 규칙 수와 백엔드 수 상한은 구현에 위임한다.

### D-62. 접두 경로가 바이트 그대로 맞는 가장 긴 규칙을 고른다 (D-60 세부)
- 선택: 요청 대상이 규칙의 접두 경로로 **바이트 그대로 시작**하면 그 규칙에 맞는다. 여러 규칙이 맞으면 **가장 긴 접두 경로**를 고른다. 맞는 규칙이 없으면 지금처럼 `/echo`나 정적 파일로 처리한다.
- 전달 주소: 접두 경로를 `/` 하나로 바꾸고 나머지(쿼리 포함)는 그대로 둔다. `/api/` → `/`, `/api/users?x=1` → `/users?x=1`.
- 경계: `/api`와 `/api?x`는 규칙 밖이므로 정적 파일로 처리한다. 대소문자를 구분하고 퍼센트 디코딩과 `.`·`..` 정규화를 하지 않는다(D-24와 같음). `/api/../a`는 백엔드에 `/../a`로 간다.
- 순서: 파서 결과(400·413·414·431·501·505, `HEAD`의 501)가 먼저다. 규칙에 맞으면 405 판정(D-36)과 정적 판정보다 먼저 프록시로 보낸다. 그래서 `POST /api/...`도 백엔드로 간다.
- 이유·버린 선택지: DESIGN의 `/api/*`를 글자 그대로 따르고, 정적 경로와 같은 원칙(디코딩 없음)을 지킨다. 선언 순서 우선은 규칙 순서에 따라 결과가 바뀐다. 정규화한 뒤 매칭하면 정적 처리와 다른 해석이 생긴다.

### D-63. 라운드 로빈은 규칙마다 카운터 하나이고 실패해도 다른 백엔드로 넘기지 않는다
- 선택: 규칙에 맞을 때마다 그 규칙의 카운터로 백엔드를 고르고 **곧바로 1 늘린다**. 연결 성공·실패와 관계없이 늘린다.
- 재시도 없음: 고른 백엔드가 실패하면 그 요청은 502나 504로 끝난다. 다른 백엔드로 다시 보내지 않는다.
- 이유: DESIGN의 "연결 실패는 502"와 완료 기준("8001로 가는 요청에 504")에 그대로 맞는다. 재시도용으로 요청 본문을 보관할 필요도 없다. 루프가 단일 스레드라 잠금이 없다.
- 한계: 백엔드가 하나만 꺼져도 그 백엔드 차례의 요청은 502다. 상태 확인으로 꺼진 백엔드를 빼는 기능은 없다.

### D-64. 백엔드 연결은 요청마다 새로 맺고 HTTP/1.0 요청으로 보낸다
- 선택: 프록시 요청마다 논블로킹 `connect`를 새로 한다. 응답 끝에 닿거나 실패하면 그 백엔드 소켓을 **바로 닫는다**. 클라이언트 연결을 유지해도(D-65) 다음 프록시 요청은 새로 연결하며, 백엔드 연결은 **재사용하지 않는다**.
- 요청 줄·머리: 요청 줄은 `메서드 전달주소 HTTP/1.0`이다. 클라이언트 머리는 받은 순서대로 복사하되(같은 이름 여러 줄도 합치지 않음) 아래 **홉 머리**는 뺀다. 그 뒤 `Host: <설정의 호스트:포트>`와 `Connection: close`를 붙인다.
- 홉 머리 (요청·응답 공통, RFC 9110 7.6.1): `Connection`·`Keep-Alive`·`Proxy-Connection`·`TE`·`Upgrade`, 그리고 모든 `Connection` 줄의 쉼표 구분 토큰(앞뒤 공백 제거, 대소문자 무시)이 가리키는 이름이다. 요청에서는 `Host`·`Expect`도 뺀다.
- 요청 프레이밍: 원래 `Content-Length` 줄은 복사하지 않는다. 원래 요청에 `Content-Length`가 있었으면 파서가 검증한 값으로 **새로 쓴다**. 그래서 `Connection: Content-Length`처럼 길이 머리를 가리켜도 보내는 본문 길이와 머리가 어긋나지 않는다. 요청 `Transfer-Encoding`은 파서가 이미 거절한다(D-48).
- 본문: 버퍼에 있던 본문을 먼저 보내고, 나머지는 클라이언트 소켓에서 남은 길이만큼만 조각으로 읽어 보낸다(D-39). 업로드 중에도 백엔드 응답을 지켜본다(D-66 조기 응답). 본문 뒤에 미리 들어온 다음 요청 바이트는 입력 버퍼에 그대로 남긴다(D-47). 프록시 요청이 끝나기 전에는 입력 버퍼를 백엔드 버퍼로 쓰지 않고, 요청 정보도 덮어쓰지 않는다.
- `100 Continue`: 유효한 `Expect` 요청이면 연결 성공·실패와 관계없이 본문을 기다리기 **전에** 서버가 `100`을 다 보낸다(D-50). `100`은 최종 응답 커밋이 아니므로 그 뒤에도 502·504를 보낼 수 있다.
- 이유: 백엔드 쪽 연결 유지를 다룰 필요가 없다. RFC 9112 6.1은 HTTP/1.1을 표시하지 않은 요청에 `Transfer-Encoding` 응답을 보내지 말라고 **서버에 요구**한다. 하지만 백엔드 구현이 이를 지킨다는 보장은 아니므로, 받으면 D-65대로 502로 처리한다. `python3 -m http.server`(로컬 3.14 소스 확인)는 HTTP/1.0으로 답하고 파일·목록·오류·리다이렉트 응답에 `Content-Length`를 넣는다.
- 버린 선택지·한계: 연결 재사용에는 유휴 연결 관리, 응답 길이 해석, 끊긴 연결 재시도가 필요하다. 대신 요청마다 handshake 비용이 든다. `X-Forwarded-For` 같은 전달 정보 머리는 넣지 않는다.

### D-65. 백엔드 응답의 끝을 알 수 있으면 클라이언트 연결을 기존 규칙대로 유지한다
- 선택: 사용자 선택. 백엔드 응답 머리를 검증한 뒤 **본문 끝**을 정한다. 끝을 알면 클라이언트 연결은 기존 유지 규칙(D-37·D-38·D-51)을 따르고, 끝을 모르면 `Connection: close`를 넣어 EOF까지 보낸 뒤 닫는다. 모든 응답을 유지하는 것은 아니다.
- 판정 순서: 아래 순서로 검사하며 처음 걸린 단계에서 502로 끝낸다. 7단계를 통과하기 전에는 클라이언트에 **한 바이트도 쓰지 않는다**.

| 순서 | 검사 | 실패 |
| ---- | ---- | ---- |
| 1 | 머리 모으기: 첫 `CRLF CRLF`까지 길이 기준으로 8KB 안에서 찾는다 | 8KB 초과 → 502 |
| 2 | 줄 바꿈·문자: NUL 없음, 모든 LF 앞은 CR, CR 뒤는 LF | 502 |
| 3 | 상태 줄: `HTTP/1.0` 또는 `HTTP/1.1`, 공백 하나, 숫자 세 자리(100~599), 그 뒤는 없거나 `공백 + 이유 문구`(HTAB·SP·VCHAR·0x80~0xFF) | 502 |
| 4 | 머리 줄: 이름은 token 1자 이상이고 바로 `:`, 값은 앞뒤 공백을 뺀 뒤 HTAB·SP·VCHAR·0x80~0xFF만 허용. 공백으로 시작하는 줄(obs-fold), 이름 앞뒤 공백, 머리 101줄 이상은 실패 | 502 |
| 5 | 1xx 상태 | 502 |
| 6 | 프레이밍: `Transfer-Encoding` 있음, `Content-Length` 두 줄 이상(값이 같아도)·10진 숫자 아님·넘침, `Connection` 토큰이 `Content-Length`·`Transfer-Encoding`을 가리킴. 상태 코드와 관계없이 검사 | 502 |
| 7 | 본문 끝 정하기 (아래 표) | — |

| 통과한 응답 | 본문 끝 | 출력 `Content-Length` | 클라이언트 연결·응답 `Connection` |
| ----------- | ------- | --------------------- | --------------------------------- |
| 204 | 머리 끝 | **뺀다** | D-51 규칙 |
| 304 | 머리 끝 | 있으면 그대로 둠 (표현 길이, RFC 9110 8.6) | D-51 규칙 |
| 그 밖, `Content-Length` 있음 | 그 바이트 수 | 그대로 | D-51 규칙 |
| 그 밖, `Content-Length` 없음 | 백엔드 EOF | 없음 | 닫기, `close` |

- D-51 규칙: HTTP/1.1은 `close` 토큰이 없으면 유지하고 `Connection` 머리를 넣지 않는다. HTTP/1.0은 `keep-alive` 토큰이 있으면 유지하고 `Connection: keep-alive`를 넣는다. 그 밖에는 닫고 `Connection: close`를 넣는다. 유지 여부는 응답 머리를 쓰기 **전에** 한 번 정한다.
- 다시 쓰기: 상태 줄은 버전만 `HTTP/1.1`로 바꾼다. 홉 머리(D-64)와 204의 `Content-Length`는 빼고, 위 표의 `Connection`을 넣는다. 나머지 머리 줄은 바이트 그대로 둔다.
- 커밋: 다시 쓴 머리를 출력 버퍼에 채운 순간이 **커밋**이다. 그 뒤에는 출력 버퍼를 바꾸지 않으며 502·504로 바꿀 수 없다.
- 길이 있는 응답: **정확히 그 바이트 수만** 중계한다. 머리와 함께 미리 받은 바이트도 포함하고, 넘는 바이트는 버리며, 백엔드에서 남은 길이보다 더 읽지 않는다. 204·304 뒤에 받은 바이트는 내보내지 않는다. 다 보내면 백엔드 소켓을 닫는다. 유지면 남은 요청 본문을 버린 뒤(D-66 조기 응답) 입력 버퍼의 다음 요청부터 처리하고(D-47·D-56), 닫기면 정리 없이 닫는다.
- 조기 끝: 길이를 다 받기 전 EOF·읽기 오류가 나면, 커밋 뒤이므로 두 번째 응답 없이 연결만 닫는다(`ERROR`, `EIO`). 클라이언트는 짧은 본문과 닫힘으로 불완전한 응답임을 안다(RFC 9112 6.3).
- 버린 선택지·한계: 모든 응답을 유지하면 EOF로 끝나는 응답의 끝을 알 수 없다. 모두 닫으면 기존 keep-alive 정책과 어긋난다. 느슨하게 검증해 그대로 넘기면 프록시와 클라이언트가 길이를 다르게 해석할 수 있다(RFC 9112 2.2·4·5). chunked는 해석하지 않으므로 `Transfer-Encoding` 응답은 502다. `HEAD`는 파서가 501로 먼저 거절하므로(D-35) `HEAD` 응답 규칙은 필요 없다.

### D-66. 응답 머리를 커밋하기 전 실패는 502·504, 커밋 뒤 실패는 연결만 닫는다

| 상황 | 시간 제한 | 결과 |
| ---- | --------- | ---- |
| 소켓 생성 실패, `connect` 즉시 실패, 완료 알림 뒤 `SO_ERROR` 실패(거부 등) | — | 502 |
| `connect`가 끝나지 않음 | 시작부터 5초 (고정) | 504 |
| 업로드 중 요청 쓰기 실패 (`EPIPE`·`ECONNRESET`) | — | 업로드를 멈추고 응답 머리를 계속 기다림. 머리 없이 EOF·오류면 502 |
| 업로드 중 백엔드 쓰기 막힘 | 쓰기 진행 없음 5초 | 504 |
| 업로드 중 완전한 응답 머리 도착 (조기 응답) | — | 업로드를 멈추고 그 응답을 D-65대로 중계 |
| 응답 머리 기다림 | 읽기 진행 없음 5초 | 504 |
| 커밋 전 EOF·읽기 오류, D-65 검사 실패 | — | 502 |
| 커밋 뒤 본문 기다림 | 읽기 진행 없음 5초 | 응답 없이 닫기 (`ERROR`, `ETIMEDOUT`) |
| 커밋 뒤 길이 전 EOF·읽기 오류 | — | 응답 없이 닫기 (`ERROR`, `EIO`) |
| 길이 없는 응답의 EOF | — | 정상 끝, 닫기 (D-65) |
| 클라이언트 쪽 읽기·쓰기 | D-59 그대로 | D-59 그대로 |

- 502·504 순서: 백엔드 소켓을 닫는다 → 남은 요청 본문을 다 버린다(D-39) → 상태 응답(D-33)을 보낸다. 요청 끝을 알기 때문에 연결은 D-37 기준에 따라 D-51 규칙으로 유지하거나 닫는다. 백엔드의 머리 바이트는 클라이언트에 보내지 않는다.
- 조기 응답: 백엔드 버퍼에 남은 미송신 바이트는 버린다. 응답을 중계하고, 그 뒤 유지 규칙이면 남은 요청 본문을 버리고 다음 요청으로 간다. 닫기 규칙이면 그대로 닫는다. 요청 끝을 실제로 확보하지 못하면(클라이언트 끊김·D-59 만료) 유지하지 않는다.
- 본문 셈: 이미 백엔드 버퍼로 옮긴 본문은 받은 것으로 센다. 실패하거나 조기 응답이면 미송신 바이트를 버리고, 입력 버퍼에 남은 본문을 먼저 소비한 뒤 소켓에서는 **아직 받지 않은 길이만** 읽어 버린다. 이미 받은 본문을 다시 읽지 않는다.
- 5초는 D-41·D-59의 값을 그대로 쓴다. 연결 시간 초과를 504로 하는 것은 학습 노트([08-proxy](../../study/08-proxy.md) 「백엔드 장애 처리」)의 장애 판단과 같다.
- 기존 정책의 한계: 502·504는 남은 본문을 다 버린 뒤 보내므로, 실패 시점부터 일정 시간 안에 통보된다는 보장이 없다. 클라이언트가 본문을 5초 넘게 보내지 않으면 최종 응답 없이 닫힌다(D-59). 조금씩 진행하면 총시간 상한이 없다. Step 4·5에서 채택한 동작을 그대로 따른 결과이며, 이번 Step에서 바꾸지 않는다.

### D-67. 연결마다 소켓 하나만 epoll에 등록하고 업로드 중에만 두 소켓을 본다 (D-56·D-57 확장)
- 선택: 연결 구조체가 백엔드 상태도 함께 가진다. 차례 결과에 **백엔드 읽기 대기·백엔드 쓰기 대기**를 더한다. 기본은 지금 기다리는 소켓 하나만 등록한다. 대상 fd가 바뀌면 이전 fd를 `DEL`하고 새 fd를 `ADD`하며, 같은 fd면 `MOD`한다. 등록 변경 실패는 그 연결의 `ERROR`다(D-57).
- 업로드 예외: 요청 머리·본문을 백엔드에 보내는 동안에만 조기 응답(D-66)을 보려고 **백엔드를 읽기로도 등록**한다. 백엔드 쓰기를 기다리면 백엔드 하나를 `IN|OUT`으로, 클라이언트 본문을 기다리면 클라이언트 `IN`과 백엔드 `IN` 두 소켓을 등록한다. 업로드가 끝나거나 멈추면 다시 소켓 하나로 돌아간다.
- HUP·ERR 처리: 알림만으로 백엔드를 닫거나 502로 정하지 않는다. 백엔드 읽기 준비·HUP·ERR가 있으면 남은 응답 바이트를 먼저 읽고, 유효한 최종 응답은 D-65·D-66대로 중계한다. 쓰기 실패는 업로드를 멈추고 클라이언트 업로드 등록·미송신 바이트를 정리한 뒤 백엔드 응답 읽기로 전환한다. 응답 머리 없이 실제 EOF·읽기 오류를 확인하면 502, 무진행 마감이면 504다. 머리 완성 뒤 EOF는 D-65의 본문 길이·EOF 규칙으로 판정한다. 읽기 예산이 끝나면 내부 실행 또는 레벨 트리거 등록으로 다음 읽기 기회를 남기고, 준비 알림만으로 마감을 늘리지 않는다. 불필요해진 소켓 등록은 해제한다.
- 깨운 원인 전달: 루프는 `http_conn` 실행에 **깨운 원인**(클라이언트 준비·백엔드 준비와 그 플래그·내부 실행·만료)을 넘긴다. `epoll` 알림은 연결과 소켓 종류(클라이언트·백엔드)를 담고, 루프는 `epoll_wait`가 돌아온 직후 아무것도 실행하기 전에 각 알림의 백엔드 **세대 번호**를 복사해 둔다. 실행할 때 세대가 바뀌었으면 그 백엔드 알림은 옛 소켓 것이므로 버린다.
- 연결 완료: `connect`가 0이면 바로 업로드한다. `EINPROGRESS`면 연결 대기에 들어가고, **현재 세대 백엔드의 쓰기 준비·ERR·HUP 알림**을 받은 차례에만 `SO_ERROR`를 읽어 성공·502를 정한다. 내부 실행·클라이언트 알림·옛 알림으로 실행되면 상태와 마감을 바꾸지 않고 대기로 돌아간다.
- 중복 실행: 내부 실행 목록에서 꺼낸 연결이 그사이 대기로 바뀌었으면 내부 실행은 건너뛴다. 한 회차에 같은 연결이 두 소켓의 알림으로 두 번 실행될 수 있지만, 각 실행은 자기 예산과 깨운 원인만큼만 진행한다.
- 예산: 백엔드 `read`도 차례당 소켓 `read` 1번에 넣고, 백엔드 `write`는 차례당 1번이다.
- 마감 (D-59 확장): 대기 종류가 바뀔 때마다 그때부터 새 마감을 잡는다. 준비 알림·내부 실행만으로는 늘리지 않는다.

| 구간 | 마감 | 만료 결과 |
| ---- | ---- | --------- |
| 연결 대기 | 시작부터 5초 고정 | 504 |
| 업로드, 백엔드 쓰기 남음 | 백엔드 쓰기 진행 없음 5초 | 504 |
| 업로드, 클라이언트 본문 기다림 | 클라이언트 읽기 진행 없음 5초 | `TIMED_OUT` (D-59) |
| 응답 머리·본문, 클라이언트 출력 없음 | 백엔드 읽기 진행 없음 5초 | 커밋 전 504, 커밋 뒤 `ERROR` |
| 클라이언트 출력 남음 | 클라이언트 쓰기 진행 없음 5초 | `ERROR` (D-59) |
| 실패·조기 응답 뒤 본문 버리기 | 클라이언트 읽기 진행 없음 5초 | `TIMED_OUT` (D-59), 저장해 둔 502·504는 보내지 않음 |

- 만료 처리: 만료도 차례 결과를 돌려준다. 커밋 전 백엔드 만료는 백엔드 소켓을 닫고 D-66의 504 순서로 넘어가며 **실행 가능**을 돌려준다. 루프는 이를 끝으로 처리하지 않고 내부 실행 목록에 넣는다. 나머지는 지금처럼 끝낸다.
- 백엔드 소켓 수명: 프록시 요청 하나에 소켓 하나다. `http_conn`이 만들고, 응답 끝·실패 때 직접 닫으며, 남아 있으면 release에서 닫는다. 동시에 최대 하나이고, 연결이 유지되면 수명 동안 여러 개가 차례로 생긴다. `close`가 `epoll` 등록도 지운다(`dup` 없음). `http_conn`은 백엔드 소켓을 열거나 닫을 때마다 세대 번호를 늘린다. 같은 차례 안에서 닫고 새로 연 소켓이 같은 fd 번호를 받을 수 있으므로, 루프는 등록해 둔 백엔드의 세대가 바뀌었으면 `DEL` 없이 새 소켓을 `ADD`한다. 연결 구조체는 지금처럼 회차 끝에 해제한다.
- 그 밖의 소유: 라우팅 표는 `main`이 만들어 프로세스가 끝날 때까지 빌려준다(`root`와 같음). 백엔드로 보낼 버퍼(16KB)와 백엔드 머리 버퍼(8KB)는 연결 구조체 안에 둔다. 16KB는 요청 머리 8KB, 호스트 255바이트 이하(D-61), 덧붙이는 머리를 합친 크기보다 크다. 연결당 약 24KB가 늘지만 새 할당 실패 경로는 없다. 502·504 상태 응답은 `http_response`의 상태 목록에 더하고, 백엔드 머리 다시 쓰기는 상태 응답 함수와 따로 둔다.
- 버린 선택지: 항상 두 소켓을 등록하면 쓰지 않는 쪽 때문에 헛돈다. 업로드가 끝날 때까지 응답을 읽지 않으면 조기 401·413을 놓쳐 504·502로 바뀐다. 요청 본문을 모두 모은 뒤 보내는 방식은 D-39의 조각 전달과 메모리 계약을 바꾼다. 백엔드 연결을 별도 구조체로 루프에 등록하면 정리 순서와 수명이 두 갈래가 된다.
