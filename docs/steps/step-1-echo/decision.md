## 결정

### D-04. 포트 공개와 호스트 접속

- 상태: 채택 · 구현 검증 통과
- 선택: 컨테이너를 `-p 127.0.0.1:8080:8080`으로 실행하고, 호스트에서 `nc localhost 8080`으로 접속한다. 서버는 컨테이너 안에서 모든 주소(`0.0.0.0`)에 연다. 호스트 쪽 공개는 loopback으로 제한한다.
- 이유: DESIGN.md의 완료 기준 명령을 그대로 쓸 수 있고, Step 3의 브라우저 확인까지 같은 방식을 재사용한다. Dockerfile에 `nc`를 추가할 필요가 없다.
- 다른 선택지와 버린 이유: 컨테이너 안에서만 접속하는 방식은 외부 노출이 없지만 Dockerfile 변경이 필요하고, Step 3에서 포트 공개로 다시 바꿔야 한다.
- 영향: 실행 안내(Dockerfile 주석·README)의 `docker run`에 포트 공개가 추가된다. 서버의 바인드 주소는 `0.0.0.0`이다.
- 다시 볼 조건: 호스트 쪽 접속이 불가능한 환경에서 검증해야 할 때.

### D-05. 클라이언트 종료 뒤 쓰기 처리는 Step 1에서 최소한으로 한다

- 상태: 채택 · 구현 검증 통과
- 선택: `SIGPIPE`를 무시하고, 끊어진 연결에 쓰기가 실패하면 그 연결만 닫고 서버는 계속 동작한다.
- 이유: Step 1 요구사항의 "시스템 콜 실패 처리"에 따라 클라이언트 하나 때문에 서버가 종료되지 않아야 한다.
- 다른 선택지와 버린 이유: Step 7로 미루면 Step 1 범위는 가장 작지만, 그때까지 서버가 종료될 수 있다는 한계가 남는다.
- 영향: Step 7에서는 이 처리를 전제로 종료 처리·자원 회수만 다룬다.
- 다시 볼 조건: Step 7 설계에서 `SIGPIPE` 정책을 바꿀 때.

### D-06. `SO_REUSEADDR` 비교 주제는 실험 증거를 남긴다

- 상태: 채택 · 구현 검증 통과
- 선택: `SO_REUSEADDR`을 뺀 경우의 `bind()` 실패를 실제로 재현해 그 결과를 검증 기록에 남긴다. 실험은 본 서버 코드와 분리한다.
- 이유: 발표·질의응답에서 설명뿐 아니라 실제 재현 결과를 근거로 삼을 수 있다.
- 다른 선택지와 버린 이유: 설명만 기록하면 가장 작지만 재현 근거가 없다.
- 영향: 실험용 파일 또는 절차가 하나 추가된다. 구현 방식은 설계에서 정한다.
- 다시 볼 조건: 재현이 환경 때문에 불안정해 근거로 쓰기 어려울 때.
- 실험 결과(독립 검증 2026-11-23, Docker Desktop 컨테이너): 연결을 유지한 채 서버를 `Ctrl+C`로 먼저 끊자 서버 쪽 `:8080`에 `TIME_WAIT` 소켓이 남았다(0.4초 안에 관측, 약 59~61초 뒤 소멸). 이 상태에서 `SO_REUSEADDR` 없이 `bind`하면 `EADDRINUSE`로 실패했고, `SO_REUSEADDR`을 켠 서버는 0.5초 안에 `bind`에 성공했다. 소켓이 모두 사라진 뒤에는 옵션이 없어도 성공했다. 즉 실패 원인은 먼저 연결을 끊은 쪽에 남는 `TIME_WAIT` 소켓이 같은 포트를 점유하는 것이고, `SO_REUSEADDR`은 이를 허용한다. `FIN_WAIT_2`는 관측되지 않았다.

### D-07. 모듈 구성과 `accept` 실패 처리

- 상태: 채택 · 구현 검증 통과
- 선택: `listener`(듣는 소켓 준비)와 `echo`(연결 하나 처리) 모듈로 나누고, `accept` 반복과 연결 소켓 닫기는 `main.c`가 맡는다. `accept`가 `EINTR`·`ECONNABORTED`와, Linux `accept(2)`가 재시도를 권하는 네트워크 오류(`ENETDOWN`, `EPROTO`, `ENOPROTOOPT`, `EHOSTDOWN`, `ENONET`, `EHOSTUNREACH`, `EOPNOTSUPP`, `ENETUNREACH`)로 실패하면 재시도하고, `EMFILE`·`ENFILE`·`ENOMEM`·`ENOBUFS` 등 그 밖의 오류는 메시지를 출력하고 종료한다.
- 이유: Step 0의 옵션 모듈 분리와 같은 방식으로 `echo`만 따로 시험할 수 있고, Step 2에서 `echo` 자리에 HTTP 처리를 넣기 쉽다. 같은 오류를 끝없이 반복하며 CPU를 쓰는 일을 피한다.
- 다른 선택지와 버린 이유: 전부 `main.c`에 넣으면 단위 시험이 불가능하고 Step 2에서 다시 나눠야 한다. 처리 함수를 함수 포인터로 넘기는 구조는 처리 방식이 하나뿐인 지금은 과하다. 모든 `accept` 오류를 무시하고 계속하면 지속되는 오류에서 빈 반복이 생긴다.
- 영향: `Makefile`의 소스·테스트 목록이 바뀐다. 자원 부족이 잠깐 있어도 서버가 내려갈 수 있으나 순차 처리에서는 드물다.
- 다시 볼 조건: Step 5 동시성 설계에서 `accept`와 연결 처리 경계를 바꿀 때.

### D-08. 시험 방식과 `SO_REUSEADDR` 실험 방식

- 상태: 채택 · 구현 검증 통과
- 선택: 수동 `nc` 시험과 `echo`의 단위 테스트(`socketpair`, 외부 프레임워크 없는 C 테스트 실행 파일)를 함께 쓴다. D-06 실험은 `SO_REUSEADDR` 없이 `bind`만 하고 오류를 출력하는 별도의 작은 프로그램으로 하며, 같은 조건에서 서버는 성공하고 실험은 실패하는 결과를 나란히 기록한다.
- 이유: 상대가 끊은 뒤 쓰기(D-05)와 `read()==0`을 수동으로는 매번 같은 결과로 재현하기 어렵다. 별도 프로그램은 서버 소스에 실험용 분기를 넣지 않는다.
- 다른 선택지와 버린 이유: 수동 시험만 하면 D-05를 간접으로만 확인한다. 자동 스크립트는 컨테이너에 `nc`·`python`이 없어 Dockerfile을 바꿔야 하며 Step 1에는 과하다. `-DNO_REUSEADDR` 빌드는 서버 소스에 `#ifdef`가 생긴다. 실행 옵션으로 켜는 방식은 D-02의 실행 인자 계약을 바꾼다.
- 영향: 단위 테스트 파일·실험 프로그램·Makefile 타깃이 추가된다. 소켓 상태는 기본적으로 `/proc/net/tcp`로 기록한다. 서버 재실행과 실험은 같은 컨테이너에서 하고, 소켓 상태가 남아 있는지 먼저 확인한다. 남지 않았으면 전제 불성립(⛔)으로 기록하고 다시 볼 조건으로 넘긴다.
- 다시 볼 조건: 실험 재현이 환경 때문에 불안정할 때.
