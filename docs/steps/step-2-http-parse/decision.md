## 결정

### D-09. 연결별 버퍼는 상한이 있는 가변 크기 버퍼로 한다

- 상태: 대체됨 (D-11)
- 선택: 연결마다 작게 시작해 필요하면 늘리는 버퍼(`realloc`)에 요청을 쌓고, 최대 크기를 둔다. 상한을 넘기면 요청을 거절한다. 상한 값과 초과 시 응답 코드는 아직 정하지 않았다.
- 이유: 사용자 선택. 평소에는 메모리를 적게 쓰고, 큰 요청도 상한까지는 받을 수 있다.
- 다른 선택지와 버린 이유: 고정 크기 배열은 더 단순하지만 크기가 곧 한계가 된다. 한 글자씩 읽기는 시스템 콜이 많아 느리다.
- 영향: 메모리 할당·해제 오류(누수 등)를 설계·검증에서 다뤄야 한다. `\r\n\r\n` 뒤에 남는 바이트의 처리는 Step 4 결정과 이어진다.
- 다시 볼 조건: 메모리 관리 오류가 검증에서 반복될 때.
- 대체 사유: 상한이 8KB(D-10)로 정해져 가변 버퍼가 절약하는 메모리가 작고, 할당 실패·누수 검증 부담이 남는다. 사용자가 고정 버퍼로 되돌리기로 했다.

### D-10. 요청 상한은 8KB, 초과하면 400으로 응답한다

- 상태: 채택 · 구현 검증 통과
- 선택: 요청 라인과 헤더를 합쳐 8KB까지 받는다. `\r\n\r\n`이 나오기 전에 8KB를 넘으면 400 Bad Request로 응답하고 연결을 닫는다. 원인별 코드(414, 431)는 쓰지 않는다.
- 이유: 사용자 선택. 흔한 브라우저 요청이 들어가는 크기이고, 응답 코드를 늘리지 않아 DESIGN.md의 "잘못된 요청은 400"과 맞다. Q-03의 큰 요청 방어에 해당한다.
- 다른 선택지와 버린 이유: 4KB는 정상 요청이 거절될 위험이 있고, 16KB 이상은 방어가 느슨하다. 414/431은 DESIGN.md에 없는 범위이고 시험이 늘어난다.
- 영향: 버퍼 최대 크기가 상수로 고정된다. 상한 초과 시험(TC)이 필요하다. 요청 본문(Step 4)의 크기 제한은 별개로 다룬다.
- 다시 볼 조건: 정상 브라우저 요청이 상한에 걸릴 때, 또는 Step 4 본문 제한과 함께 정리할 때.

### D-11. 연결별 버퍼는 8KB 고정 크기로 한다

- 상태: 채택 · 구현 검증 통과 · D-09 대체
- 선택: 연결마다 8KB 고정 크기 버퍼 하나에 요청을 쌓는다. `\r\n\r\n`이 나오기 전에 가득 차면 D-10대로 400으로 응답하고 연결을 닫는다.
- 이유: 사용자 선택. 상한이 8KB로 정해져 가변 버퍼의 메모리 절약이 작고, 고정 버퍼는 할당 실패·누수 문제가 없어 구현과 검증이 단순하다.
- 다른 선택지와 버린 이유: 상한 있는 가변 버퍼(D-09)는 절약 폭에 비해 메모리 관리 검증 부담이 크다. 한 글자씩 읽기는 시스템 콜이 많아 느리다.
- 영향: 연결마다 8KB를 항상 쓴다. Step 5 동시성에서 연결 수가 늘면 총 메모리를 확인한다. `\r\n\r\n` 뒤에 남는 바이트의 처리는 Step 4 결정과 이어진다. 파싱 결과 구조 선택지에서 원문 위치 참조 방식의 `realloc` 충돌 문제가 사라진다.
- 다시 볼 조건: Step 5에서 연결 수 대비 메모리가 문제될 때, 또는 상한(D-10)을 바꿀 때.

### D-12. 파싱 결과는 값을 복사해 담고 모든 헤더를 목록으로 보관한다

- 상태: 채택 · 구현 검증 통과
- 선택: 파서는 메서드·경로·버전을 복사해 담고, 모든 헤더를 이름·값 쌍의 목록으로 보관한다. 이름으로 헤더를 찾을 수 있게 한다. 원문 버퍼 위치만 가리키는 방식은 쓰지 않는다.
- 이유: 사용자 선택. 복사본은 익숙한 C 문자열 함수를 쓸 수 있고 버퍼 재사용에 영향받지 않아 단순하며, 이후 Step(Content-Length·Connection, 프록시 헤더 전달)이 어떤 헤더든 쓸 수 있다.
- 다른 선택지와 버린 이유: 필요한 헤더 3개만 담는 방식은 Step 6 프록시에서 구조를 고쳐야 할 수 있다. 원문 위치 참조 방식은 길이 관리 실수와 버퍼 수명 문제를 설계·검증에서 더 다뤄야 한다.
- 영향: 헤더 개수 상한과 초과 시 처리는 설계에서 정한다(D-17, 임시). 프록시가 원문 그대로 전달해야 하면 Step 6에서 재조립하거나 원문을 별도 보관한다.
- 다시 볼 조건: 헤더 복사 비용이나 개수 상한이 검증에서 문제될 때.

### D-13. HTTP/1.0과 1.1을 받고, `Host`는 1.1에서만 필수로 한다

- 상태: 채택 · 구현 검증 통과
- 선택: 버전이 HTTP/1.0 또는 HTTP/1.1이면 받는다. 1.1 요청에 `Host`가 없으면 400이고, 1.0 요청은 `Host`가 없어도 허용한다. 그 밖의 버전은 505로 응답한다. 버전 문자열의 정확한 형식 판정 기준(형식 오류를 400과 505 중 무엇으로 볼지 등)은 설계에서 정한다.
- 이유: 사용자 선택. 표준(1.1에서 `Host` 필수)에 맞고, Step 8의 `ab`와 `curl --http1.0`처럼 1.0으로 요청하는 도구도 쓸 수 있다.
- 다른 선택지와 버린 이유: 1.1만 받으면 1.0 요청 도구가 거절된다. `Host` 검사를 하지 않으면 표준과 다르고 `Host` 누락 400 시험이 없어진다.
- 영향: 파서와 시험에 버전별 분기가 생긴다. Step 4 keep-alive에서 1.0과 1.1의 연결 유지 기본값이 다르므로 그때 다시 다룬다.
- 다시 볼 조건: `ab` 측정에서 요청 형식 문제가 확인될 때.

### D-14. 모듈 구성과 연결 처리 경계

- 상태: 채택 · 구현 검증 통과
- 선택: 아래처럼 나누고, `main.c`는 `echo_serve` 자리에 `http_conn_serve`를 부른다. `accept` 반복, `SIGPIPE` 무시, 연결 소켓 닫기는 `main.c`에 그대로 둔다(D-05, D-07 유지).

| 모듈 (파일명은 제안) | 책임 | 하지 않는 것 |
| -------------------- | ---- | ------------ |
| `http_parser` | 받은 바이트를 요청 구조로 바꾸고 결과를 구분한다 (D-15, D-16) | 소켓 I/O, 메모리 할당, 응답 |
| `http_response` | 상태·본문으로 HTTP 응답을 만들어 fd에 끝까지 쓴다 (D-18) | 요청 해석, fd 닫기 |
| `http_conn` | 연결 하나: 8KB 버퍼에 읽기, 파서 호출, 결과를 상태 코드로 바꿔 응답 호출 (D-19) | fd 닫기 |
| `io` | 부분 `write`를 이어 쓰는 `io_write_all` (현재 `echo.c`의 정적 `write_all`을 옮김, D-18) | 버퍼 소유 |

- `echo` 모듈과 `tests/test_echo.c`는 저장소와 `make test`에 남기고, 서버 실행 파일 소스 목록에서는 뺀다(제안). `echo`는 `io_write_all`을 쓰도록 바뀐다.
- 이유: 파서를 소켓 없이 단위 테스트할 수 있다(DESIGN.md Step 2). 응답을 한 곳에서만 만들어 `Content-Length` 일치를 한 함수가 보장한다. 부분 `write` 처리를 응답·에코·이후 프록시가 한 구현으로 공유한다.
- 다른 선택지와 버린 이유: 파서와 연결 처리를 한 모듈에 두면 파서 시험에 소켓이 필요하다. 처리 함수를 함수 포인터로 넘기는 구조는 처리 방식이 하나뿐이라 과하다(D-07과 같은 이유). 이어 쓰기 함수를 응답 모듈에 복사하면 같은 코드가 두 벌 생긴다. `echo`를 지우면 Step 1 단위 시험(TC-1-07~10)을 회귀로 돌릴 수 없다.
- 영향: `Makefile`의 소스·헤더·테스트 목록이 바뀌고, `tests/test_echo` 타깃에 `src/io.c`를 더해야 한다. 검증을 마친 `echo.c`가 `io_write_all` 이동만큼 바뀌므로 `test_echo`(TC-1-07~10) 재실행이 필요하다. 서버가 더 이상 에코하지 않으므로 TC-1-01~06은 Step 1 시점의 시험으로 기록한다(Step 0의 TC-0-02와 같은 처리). Step 2 완료 시 `docs/architecture.md` 모듈 표에 반영한다.
- 다시 볼 조건: Step 3 라우팅이 들어와 `http_conn`의 상태 코드 결정 책임이 커질 때, Step 5에서 연결 처리 경계를 바꿀 때.

### D-15. 파서는 누적된 바이트 전체를 매번 다시 판정하는 상태 없는 함수로 한다

- 상태: 채택 · 구현 검증 통과
- 선택: 인터페이스(헤더 선언 수준, 이름은 제안)

```c
#define HTTP_REQUEST_HEAD_MAX 8192  /* D-10, D-11: 종료 빈 줄 포함 요청 머리 최대 길이 */
#define HTTP_MAX_HEADERS      100   /* D-17 */

typedef enum {
    HTTP_PARSE_INCOMPLETE,           /* 아직 \r\n\r\n 없음, 더 읽어야 함 */
    HTTP_PARSE_OK,
    HTTP_PARSE_BAD_REQUEST,          /* 400: 문법·줄 바꿈 오류, 8KB 초과, 헤더 수 초과, Host 규칙 위반 */
    HTTP_PARSE_NOT_IMPLEMENTED,      /* 501 */
    HTTP_PARSE_VERSION_NOT_SUPPORTED /* 505 */
} http_parse_result;

typedef struct { const char *name; const char *value; } http_header;

typedef struct {
    const char *method, *target, *version; /* storage 안의 복사본 */
    int version_minor;                     /* 0 또는 1 */
    http_header headers[HTTP_MAX_HEADERS]; /* 받은 순서 */
    size_t header_count;
    char storage[HTTP_REQUEST_HEAD_MAX];   /* 모든 복사본이 여기에 들어간다 */
} http_request;

http_parse_result http_parse_request(const char *data, size_t len, http_request *out);
const char *http_request_header(const http_request *req, const char *name);
```

- 계약
  - `data[0..len)`은 그 연결에서 지금까지 받은 바이트 전체다. 파서는 I/O·할당·전역 상태가 없고, 같은 입력에 항상 같은 결과를 낸다.
  - 판정 범위 S는 첫 `min(len, 8192)` 바이트다. 아래 순서로 판정한다.
    1. S 안에 `\r\n\r\n`이 있으면 그 끝까지가 머리다. 머리에 D-16 표 1~9행을 적용한다.
    2. 없으면 S에 NUL, `\r` 없는 `\n`, 다음 바이트가 `\n`이 아닌 `\r`이 있는지 본다. 있으면 `BAD_REQUEST`(D-22). S의 마지막 바이트인 `\r`은 다음 바이트를 기다리므로 오류로 보지 않는다.
    3. 그래도 판정되지 않았으면 `len < 8192`일 때 `INCOMPLETE`, `len >= 8192`일 때 `BAD_REQUEST`(D-10)다.
  - 따라서 종료 빈 줄까지 포함한 머리가 8192바이트 이하면 받아들이고, `INCOMPLETE`는 `len < 8192`에서만 나온다. 2의 "마지막 `\r`은 기다림" 예외도 `len >= 8192`이면 3에서 400이 된다(예: 8192바이트가 `\r\n\r`로 끝남).
  - 종료 빈 줄 뒤의 바이트는 보지 않는다(본문·다음 요청은 Step 4). D-22의 줄 바꿈·NUL 검사도 머리(머리가 아직 끝나지 않았으면 S)에만 적용한다.
  - `out`은 `OK`일 때만 유효하다. 그 밖의 결과에서 `out` 내용은 정해지지 않으며 호출자는 읽지 않는다.
  - 모든 문자열은 `out->storage`에 NUL로 끝나는 복사본이다. 수명은 `out`과 같고 `data` 버퍼를 덮어써도 바뀌지 않는다(D-12). 복사본 합계는 머리 길이를 넘지 않으므로(구분자 자리를 NUL로 쓴다) `storage`가 넘치지 않는다.
  - `http_request`는 값으로 복사하지 않고 포인터로만 넘긴다. 복사하면 포인터가 원본 `storage`를 가리킨다.
  - `http_request_header`는 이름을 대소문자 구분 없이 비교해 첫 번째 값(앞뒤 공백 제거)을 돌려주고, 없으면 `NULL`이다.
- 이유: 8KB 안에서 매번 처음부터 다시 판정해도 비용이 작고, 읽기 사이에 파서가 기억할 상태가 없어 분할 도착(TC-2-02)과 단위 시험이 단순하다. 8KB 초과 판정까지 파서가 하므로 D-10을 소켓 없이 시험할 수 있다.
- 다른 선택지와 버린 이유: 읽은 만큼 이어서 파싱하는 상태 기계는 다시 읽지 않지만 중간 상태가 많아 시험이 늘어난다. 파서가 직접 `read`하는 방식은 단위 시험에 소켓이 필요하다. 필드마다 `malloc`해 복사하면 해제 짝을 검증해야 한다. 포인터 대신 `storage` 안 위치(정수)로 담으면 구조체를 복사해도 안전하지만 쓸 때마다 변환이 필요하다.
- 포기한 것: 읽을 때마다 앞부분을 다시 훑는다(최대 8KB). 구조체 크기가 약 10KB라 호출자가 둘 자리를 정해야 한다.
- 영향: 연결 버퍼 크기와 파서 상한이 같은 상수를 쓴다. Step 4는 머리 길이(소비한 바이트 수)를 돌려받는 출력이 필요하다(그때 추가).
- 다시 볼 조건: Step 4에서 남은 바이트를 넘길 때, Step 5에서 연결마다 구조체를 둘 위치가 문제될 때.

### D-16. 요청 판정 규칙과 오류 우선순위

- 상태: 채택 · 구현 검증 통과
- 선택: 아래 순서로 검사하고 첫 번째로 걸린 결과를 돌려준다. 1행은 머리 완성 전에도 판정 범위 S(D-15)에 적용하고(D-22), 2~9행은 머리가 완성된 뒤 적용한다. 줄 바꿈은 엄격하게 `\r\n`만 인정한다.

| 순서 | 검사 | 실패 결과 | 예 |
| ---- | ---- | --------- | -- |
| 1 | 머리(완성 전이면 판정 범위 S, D-15) 안에 NUL, 뒤에 `\n`이 없는 `\r`, `\r` 없는 `\n`이 없다. S의 마지막 `\r`은 다음 바이트를 기다린다. 머리 완성 전에도 적용 (D-22) | 400 | `GET / HTTP/1.1\nHost: x\n\n`(종료 빈 줄 없이 즉시 400), `GET /\rX` |
| 2 | 요청 줄이 `메서드 SP 대상 SP 버전`이다. 공백은 정확히 하나씩, 세 부분 모두 비어 있지 않다. 메서드는 token 문자(RFC 9110 `tchar`), 대상은 공백·제어 문자가 없다 | 400 | `GET  / HTTP/1.1`, `GET /`, 첫 줄이 빈 줄 |
| 3 | 버전이 정확히 `HTTP/숫자.숫자`(대소문자 구분, 숫자 각 1자리)다 | 400 | `HTTP/1`, `http/1.1`, `HTTP/1.10` |
| 4 | 버전이 `HTTP/1.0` 또는 `HTTP/1.1`이다 | 505 | `HTTP/2.0`, `HTTP/0.9`, `HTTP/1.2` |
| 5 | 메서드가 `GET` 또는 `POST`다(대소문자 구분) | 501 | `BREW`, `HEAD`, `PUT`, `get` |
| 6 | 헤더 줄이 `이름:값`이다. 이름은 `tchar` 1자 이상, 이름과 `:` 사이 공백 없음, 줄 첫 글자가 공백·탭(obs-fold)이 아니다. 값은 앞뒤 공백·탭을 지우고 빈 값도 허용한다 | 400 | `Host x`, `Host : x` |
| 7 | 헤더가 100개 이하다 (D-17) | 400 | |
| 8 | `Host`가 둘 이상이 아니다. 이름은 대소문자 구분 없이 센다(D-15 조회 규칙과 같음). 버전 무관 | 400 | `Host: a` + `host: b` |
| 9 | 1.1 요청에 `Host`가 있다 (D-13). 값 내용은 검사하지 않는다 | 400 | |

- 대상(경로)은 복사만 하고 형식 검사(`/` 시작, `..`)는 Step 3에서 한다.
- 이유: 읽는 순서대로 판정하면 우선순위가 예측 가능하다. 버전을 메서드보다 먼저 보는 것은 버전이 나머지를 해석하는 기준이기 때문이다(`BREW / HTTP/2.0`은 505). 형식이 깨진 버전은 "모르는 버전"이 아니라 문법 오류이므로 400으로 둔다(D-13에서 설계로 넘긴 기준). 이름 뒤 공백과 obs-fold 거절, `Host` 중복 400은 RFC 9112(5.1, 5.2, 3.2)가 요구하는 동작이다.
- 다른 선택지와 버린 이유: RFC가 허용하는 관대한 처리(맨 `\n`, 여러 공백, 앞쪽 빈 줄 무시)는 경우가 늘어나 시험이 커진다. `curl`·브라우저·`ab`는 엄격한 형식을 보내므로 실익이 작다. 형식이 깨진 버전도 505로 보내면 규칙은 하나 줄지만 "문법 오류는 400"과 어긋난다.
- 포기한 것: 앞쪽 빈 줄을 무시하라는 RFC 권고(SHOULD)를 따르지 않는다. `HTTP/1.2`처럼 1.x의 더 높은 부 버전을 1.1로 처리하라는 RFC 9110(2.5) 권고와 달리 D-13대로 505로 응답한다. 값이 잘못된 `Host`도 400으로 거절하라는 RFC 9112(3.2) 요구(MUST)와 달리 `Host` 값 내용은 검사하지 않는다(빈 값은 RFC상 허용).
- 영향: TC-2-04 단위 시험 항목이 이 표를 따른다(D-20). `POST`는 Step 2에서 고정 200을 받고 본문은 읽지 않는다(Step 4).
- 다시 볼 조건: 실제 클라이언트가 400을 받는 사례가 나올 때, Step 4에서 keep-alive 요청 사이 빈 줄을 다룰 때.

### D-17. 헤더는 100개까지 받고, 넘으면 400으로 응답한다

- 상태: 채택 · 구현 검증 통과
- 선택: `http_request`에 헤더 100칸을 고정으로 두고, 101번째 헤더가 나오면 400이다.
- 이유: Apache `LimitRequestFields`의 기본값이 100이다. 흔한 브라우저 요청은 수십 개 이하다. 초과를 400으로 하면 D-10처럼 원인별 코드(431)를 쓰지 않는 규칙과 맞다. 고정 칸이라 할당이 없다.
- 다른 선택지와 버린 이유: 32개는 구조체가 작지만 프록시·도구가 붙이는 헤더에 여유가 적다. 8KB 안에서 가능한 최대(최소 줄 `a:\r\n` 4바이트 기준 약 2000개)는 칸이 수십 KB가 되어 크기 대비 실익이 없다.
- 영향: 헤더 100개/101개 경계 시험이 필요하다(D-20).
- 다시 볼 조건: Step 6 프록시에서 헤더를 덧붙여 상한에 닿을 때.

### D-18. 응답은 함수 하나로 만들고 `Content-Length`는 그 함수가 계산한다

- 상태: 채택 · 구현 검증 통과
- 선택: 인터페이스(이름은 제안)

```c
/* status의 응답 전체를 fd에 끝까지 쓴다. 성공 0, 실패 -1(errno 보존). fd는 닫지 않는다. */
int http_response_send(int fd, int status, const char *content_type,
                       const char *body, size_t body_len);
/* io: 부분 write를 이어서 len 바이트를 모두 쓴다. EINTR은 재시도. 성공 0, 실패 -1(errno 보존). */
int io_write_all(int fd, const void *data, size_t len);
```

- 응답 형식

```text
HTTP/1.1 <코드> <이유 문구>\r\n
Date: <IMF-fixdate, GMT>\r\n
Content-Type: <content_type>\r\n
Content-Length: <body_len>\r\n
Connection: close\r\n
\r\n
<body>
```

- 계약
  - `Content-Length`는 인자로 받지 않고 `body_len`에서 만든다. 본문은 `body_len` 바이트를 그대로 쓴다(NUL 포함 가능).
  - 지원 상태: 200 OK, 400 Bad Request, 501 Not Implemented, 505 HTTP Version Not Supported. 그 밖의 코드는 아무것도 쓰지 않고 -1(`EINVAL`)이다. Step 3에서 403·404·500을 더한다.
  - 상태 줄은 요청 버전과 관계없이 `HTTP/1.1`이다(서버가 지원하는 최고 버전).
  - 이번 Step은 응답 뒤 연결을 닫으므로 `Connection: close`를 항상 보낸다(Step 4에서 인자로 바뀐다).
  - 머리와 본문은 `io_write_all`로 끝까지 쓴다. 머리를 만드는 방식(고정 버퍼 + `snprintf`)과 머리·본문을 한 번에 쓸지(`writev`)는 구현에 맡긴다.
- 본문(제안, 미확정): 200은 `text/plain; charset=utf-8`의 짧은 고정 문장, 오류는 `<코드> <이유 문구>\n`. 요청 대상과 관계없이 같다.
- 이유: 상태 줄·헤더·본문 길이를 한 함수만 만들면 길이 불일치가 생길 자리가 없다(DESIGN.md Step 2). `Date`는 시계가 있는 서버가 2xx·4xx 응답에 보내야 하는 헤더다(RFC 9110 6.6.1).
- 다른 선택지와 버린 이유: 응답을 버퍼에 만드는 함수와 보내는 함수를 나누면 바이트 비교 시험은 쉽지만 호출자가 둘을 짝지어야 한다. `Date`를 빼면 단순하고 응답이 매번 같아 비교 시험이 쉽지만 표준 요구에 어긋난다.
- 영향: 시험은 `Date` 값을 고정 문자열로 비교하지 않고 형식만 본다.
- 다시 볼 조건: Step 3에서 파일 내용을 나눠 보낼 때(본문이 메모리에 다 없을 때), Step 4 keep-alive. Step 3에서 `HEAD`를 다룰 때 `HEAD` 요청에 대한 응답(지금은 501)에 본문을 보내지 않도록 할지 함께 본다(RFC 9112 6.3).

### D-19. 연결 하나는 완성된 요청 하나에 응답하고 돌아간다

- 상태: 채택 · 구현 검증 통과
- 선택: 인터페이스(이름은 제안)

```c
typedef enum {
    HTTP_CONN_RESPONDED = 0,   /* 응답을 끝까지 보냈다 */
    HTTP_CONN_PEER_CLOSED = 1, /* 요청 머리가 완성되기 전에 상대가 닫았다. 응답하지 않았다 */
    HTTP_CONN_ERROR = -1       /* 읽기·쓰기 오류. errno 보존 */
} http_conn_result;
http_conn_result http_conn_serve(int fd);
```

- 흐름: `읽는 중 → (머리 완성 또는 판정 오류) → 응답 중 → 반환`, 또는 `읽는 중 → 반환(상대 종료·오류)`.
  1. 8KB 버퍼와 `http_request`는 `http_conn_serve`의 지역 자원이다. 수명은 연결 하나이고 해제할 것이 없다. 두는 위치(스택·정적)는 구현에 맡긴다.
  2. `read(fd, buf + len, 8192 - len)`. 불변조건: `0 <= len <= 8192`, 읽을 때 남은 칸은 1 이상이다(`INCOMPLETE`는 `len < 8192`에서만 나온다, D-15). 파서가 `len == 8192`에서 `INCOMPLETE`를 돌려주면 0바이트 `read`가 되어 0을 받고 `PEER_CLOSED`로 잘못 끝나므로, 이 불변조건은 파서 계약으로 지킨다.
  3. 읽을 때마다 `http_parse_request(buf, len, &req)`를 부른다. `INCOMPLETE`면 2로 돌아간다.
  4. 결과를 상태로 바꾼다: `OK`→200 고정 응답, `BAD_REQUEST`→400, `NOT_IMPLEMENTED`→501, `VERSION_NOT_SUPPORTED`→505. `http_response_send`를 한 번 부른다.
  5. 반환한다. 연결 소켓은 `main`이 닫는다.

| 상황 | 동작 | 결과 |
| ---- | ---- | ---- |
| `read`가 `EINTR` | 다시 읽는다 | |
| 머리 완성 전 `read == 0` | 응답하지 않는다 | `PEER_CLOSED` |
| `read` 오류 (`ECONNRESET` 등) | 응답하지 않는다 | `ERROR` |
| 응답 쓰기 실패 (`EPIPE` 등, `SIGPIPE` 무시 상태) | 쓰기를 멈춘다 | `ERROR` |
| 머리 뒤에 남은 바이트, `POST` 본문 | 읽지 않고 버린다 | |

- `main`은 `ERROR`면 Step 1과 같은 방식으로 stderr에 한 줄 남기고(Step 1의 로그 유지 여부 선택을 따른다) 연결을 닫고 다음 `accept`로 간다. 서버는 어떤 경우에도 계속 돈다.
- 이유: 이번 Step은 keep-alive가 없어 연결당 요청이 하나다. 머리가 덜 온 채 끊긴 상대에게는 받을 요청이 없으므로 응답하지 않는다.
- 다른 선택지와 버린 이유: 머리가 덜 온 채 끊기면 400을 보내는 방식도 있으나, 상대가 이미 쓰기를 닫았고 판정할 요청이 없다.
- 알려진 한계: 연결만 하고 보내지 않거나 머리를 끝내지 않는 클라이언트가 있으면 서버가 그 연결에서 무한히 기다리고, 순차 처리라 다른 연결도 막힌다(타임아웃은 Step 4, 동시성은 Step 5). 응답 뒤 닫는 방식은 D-21을 따른다.
- 다시 볼 조건: Step 4 keep-alive·타임아웃, Step 5 동시성.

### D-21. 응답을 보낸 뒤 연결은 바로 닫는다

- 상태: 채택 · 구현 검증 통과
- 선택: 응답을 끝까지 보낸 뒤 남은 입력을 읽지 않고 `close`한다(`main`이 닫는다). `shutdown`과 남은 입력 비우기는 하지 않는다.
- 이유: 사용자 선택. 가장 단순하고, 읽기 타임아웃(원래 Step 4 범위)을 Step 2에 들이지 않는다. 요청을 다 읽은 정상 요청에는 영향이 없다.
- 다른 선택지와 버린 이유: 닫기 전에 남은 입력을 비우는 방식(nginx `lingering_close` 방식)은 큰 요청의 400이 안정적으로 전달되지만 읽기 시간 제한과 코드·시험이 늘어난다.
- 영향: 클라이언트가 아직 보내는 중(8KB 초과 요청, `POST` 본문)에 응답하면 운영체제가 연결을 강제로 끊는 신호(RST)를 보내 클라이언트가 응답 대신 "연결 재설정" 오류를 볼 수 있다(RFC 9112 9.6). 알려진 한계로 둔다. TC-2-08은 종료 빈 줄 없이 정확히 8192바이트만 보내 이 현상을 피한다.
- 다시 볼 조건: Step 4 keep-alive·타임아웃 설계, 큰 요청의 400이 실제 클라이언트에서 문제가 될 때.

### D-22. 줄 바꿈 오류는 머리가 끝나기 전에도 바로 400으로 거절한다

- 상태: 채택 · 구현 검증 통과
- 선택: `\r\n\r\n`이 오기 전이라도, 지금까지 받은 바이트에 `\r` 없는 `\n`, 뒤에 `\n`이 없는 `\r`, NUL이 있으면 바로 400으로 응답한다. 받은 바이트의 마지막 `\r`은 다음 바이트를 기다린다. 대상은 요청 머리(머리가 끝나기 전이면 판정 범위)이며 종료 빈 줄 뒤의 본문은 검사하지 않는다(D-15). 파서는 여전히 상태 없는 함수다.
- 이유: 사용자 선택. 설계 검토에서 D-15(종료 `\r\n\r\n` 전에는 판정하지 않음)와 D-16·D-20(`\n`만 쓰는 요청은 400)이 서로 모순임이 지적됐다. 손으로 `nc`에 입력한 요청도 바로 400을 받고, 순차 처리 서버가 무한히 기다리는 경우가 하나 줄어든다.
- 다른 선택지와 버린 이유: 현재 계약을 유지하고 `\n`만 쓰는 요청은 8KB가 차거나 상대가 닫을 때까지 기다리게 하면 파서가 가장 단순하지만, 서버가 멈춘 것처럼 보이는 한계가 남는다.
- 영향: D-15 계약, D-16 표 1행, D-20 TC-2-04를 이에 맞게 고쳤다(반영됨: D-15 계약, D-16 표 1행, D-20 TC-2-04).
- 다시 볼 조건: Step 4 keep-alive에서 요청 사이 빈 줄을 다룰 때.

### D-23. 부분 `write`는 코드 검토로 확인하고 TC-2-06은 전 바이트 도착만 확인한다

- 상태: 채택 · 구현 검증 통과
- 선택: TC-2-06은 소켓 버퍼보다 큰 본문이 전 바이트 도착하는지만 확인한다. `write`가 일부만 쓰고 돌아와 이어 쓰는 분기는 실행했다고 주장하지 않고 코드 검토 항목으로 둔다. 신호로 짧은 쓰기를 유도하는 시험은 추가하지 않는다.
- 이유: 사용자 선택. 설계 검토에서 블로킹 소켓은 `write`가 전부 쓸 때까지 기다려 이어 쓰기 분기가 실행되지 않음이 확인됐다(Linux 컨테이너, 4MB, `write` 1회). 이어 쓰기 코드는 짧은 반복문이라 코드 검토로 충분하고, 흔들릴 수 있는 시험은 비용이 더 크다.
- 다른 선택지와 버린 이유: `SIGALRM`으로 짧은 쓰기를 유도하는 시험은 이어 쓰기 실행 증거가 생기지만 환경에 따라 흔들릴 수 있고 구현·시험이 늘어난다.
- 영향: D-20 TC-2-06의 기대 칸과 이유 문구를 낮췄다(반영됨: D-20 TC-2-06). Step 1의 부분 `write` 처리와 같은 방식이다.
- 다시 볼 조건: 이어 쓰기 분기에 실제 결함이 의심될 때.
