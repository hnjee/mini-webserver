# 2부 4편: 서버에 도착한 쪽지는 어떻게 처리되나 - 소켓으로 보는 웹서버

Nov 21, 2026 · @현지

## 들어가며

"C로 웹서버 만들기" 과제 요구사항을 처음 봤을 때는 한 줄도 읽히지 않았다. socket, bind, listen, accept, keep-alive, Content-Length… 단어는 아는데 서로 이어지지 않았다. 1부에서 길을, 2부에서 짐을 정리하고 나서야 비로소 하나의 그림으로 보였다.

먼저 내 코드의 위치부터 정하자. **웹서버는 응용 계층 프로그램이다.** 그 아래 TCP, IP, 링크는 운영체제가 맡는다.

```
[ 내 C 코드 ]   HTTP 해석, 응답 작성, 파일 서빙, 프록시      ← 응용 계층
       ↕  소켓 API (socket, bind, listen, accept, read, write)
[ 운영체제 ]   TCP (handshake, 순서 맞추기, 재전송), IP, 링크   ← 전송 계층 이하
```

그래서 handshake나 재전송은 직접 짜지 않는다. 내가 할 일은 **TCP가 주는 끊김 없는 흐름에서 HTTP 쪽지를 정확히 잘라 내고, 답장을 HTTP 양식대로 써서 돌려주는 것**이다.

이번 편은 한 사용자의 연결이 태어나서 끝날 때까지를 시간 순서대로 따라간다. 각 단계마다 과제에서 구현해야 할 내용을 함께 적는다.

## 1. 서버가 문을 연다

모든 것은 서버가 손님 받을 준비를 하는 데서 시작한다.

### 소켓: 연결마다 있는 우편함

소켓은 운영체제가 통신을 위해 만들어 주는 **우편함**이다.

- **받은 편지함(수신 버퍼)**: 도착한 데이터가 쌓인다. `read()`로 꺼낸다.
- **보낼 편지함(송신 버퍼)**: `write()`로 넣으면 운영체제가 봉투를 씌워 내보낸다.

프로그램 안에서 소켓은 **숫자 하나(파일 디스크립터, fd)**로 보인다. "4번 우편함에서 꺼내 줘", "4번 우편함에 넣어 줘" 하는 식이다.

### 안내 데스크 차리기: socket → bind → listen

| 함수 | 하는 일 | 식당 비유 |
| --- | --- | --- |
| `socket()` | 소켓 만들기. `SOCK_STREAM`이면 TCP | 안내 데스크 설치 |
| `bind()` | 소켓에 **포트 번호** 붙이기 (예: 8080) | 간판에 "8080번 식당" |
| `listen()` | 손님 받는 상태로 전환, 대기 줄 만들기 | "영업 시작" |

이렇게 만든 소켓을 **listen 소켓**이라고 부른다. 이 소켓은 **주문(HTTP)을 받지 않는다.** 손님이 왔다는 것(연결 요청)만 받는다. 서버가 꺼질 때까지 하나만 열려 있다.

### 과제에서 할 일

- [ ] `socket()` → `bind()` → `listen()` 흐름 구현
- [ ] 포트와 정적 파일 루트를 CLI 인자나 설정 파일로 받기
- [ ] `SO_REUSEADDR` 설정: 서버를 끄고 바로 켜면 `Address already in use`로 `bind()`가 실패한다. 끝난 연결의 기억을 운영체제가 잠시 남겨 두기 때문이다(TIME\_WAIT). 늦게 도착한 패킷이 새 연결에 섞이지 않게 하는 TCP의 안전장치다. 이 옵션을 켜면 그 상태에서도 포트를 다시 쓸 수 있다.
- [ ] 각 함수의 실패(반환값 -1) 처리

## 2. 클라이언트가 연결을 요청한다

브라우저가 처음 보내는 것은 HTTP 요청이 아니라 **"연결하고 싶어요"(SYN)**다. 이때 3-way handshake가 일어난다.

```
브라우저 → 서버:  SYN       "연결하고 싶어요"
서버 → 브라우저:  SYN-ACK   "좋아요, 들리세요?"
브라우저 → 서버:  ACK       "네, 시작할게요"
```

여기서 중요한 점은 **이 인사를 내 프로그램이 아니라 운영체제가 한다**는 것이다. listen 소켓이 열려 있으면 운영체제가 알아서 SYN-ACK을 보내고, 인사가 끝난 연결을 대기 줄에 세워 둔다. 그동안 내 코드는 아무것도 하지 않는다. 그래서 코드에는 handshake가 한 줄도 보이지 않는다.

이 인사는 **요청마다가 아니라 연결마다 한 번**이다. 한 번 연결이 맺어지면 그 안에서는 요청을 여러 번 주고받는다(6번).

### 과제에서 할 일

- [ ] 없음. 운영체제가 한다. 다만 요구사항의 "3-way handshake의 동작 원리"를 설명할 수 있어야 한다. "`listen()` 이후 운영체제가 수행하고, 완성된 연결을 `accept()`가 꺼낸다"가 핵심이다.

## 3. 서버가 연결을 받는다

내 프로그램이 `accept(listen 소켓)`을 부르면, 대기 줄에서 handshake가 끝난 연결 하나를 꺼내 **그 손님 전용 소켓을 새로** 돌려준다. 식당으로 치면 안내 데스크가 손님을 테이블에 앉히는 것이다. 주문을 받고 음식을 내는 것은 이 테이블에서 한다.

| 소켓 | 개수 | 하는 일 |
| --- | --- | --- |
| listen 소켓 (안내 데스크) | 서버에 하나 | 새 연결 요청만 받는다 |
| 손님 소켓 (테이블) | 연결마다 하나 | 실제 HTTP 요청을 읽고 응답을 쓴다 |

### 같은 포트인데 어떻게 구분될까

안내 데스크도 테이블들도 전부 8080번 포트다. 그래도 헷갈리지 않는 이유는 **연결이 네 값으로 구분**되기 때문이다.

| 소켓 | 내 IP : 포트 | 상대 IP : 포트 |
| --- | --- | --- |
| listen 소켓 | 서버 : 8080 | 아직 없음 (누구든) |
| 손님 소켓 A | 서버 : 8080 | 현지 노트북 : 51234 |
| 손님 소켓 B | 서버 : 8080 | 다른 손님 : 49201 |

데이터가 도착하면 운영체제는 상대 IP와 포트까지 보고 맞는 소켓에 넣는다. 아직 맞는 소켓이 없는 새 연결 요청만 listen 소켓으로 간다.

### 과제에서 할 일

- [ ] `accept()`로 손님 소켓(`client_fd`) 받기
- [ ] `read()`, `write()`는 항상 `client_fd`에. listen 소켓에서는 읽지 않는다
- [ ] accept 블로킹 이해: 완성된 연결이 없으면 생길 때까지 기다린다. 이것이 8번 동시성 문제의 출발점이다

## 4. 요청이 도착한다

연결이 맺어지면 브라우저가 드디어 HTTP 요청을 보낸다.

### 운영체제가 봉투를 벗긴다

1. **랜 카드**가 전기·빛 신호를 0과 1로 바꾼다. (1부 1편)
2. **운영체제**가 바깥 봉투부터 벗긴다. MAC을 확인하고, IP가 내 주소인지 확인하고, TCP에서 순서 맞추기와 ACK, 재전송 요청까지 처리한 뒤, 네 값으로 어느 소켓의 데이터인지 찾는다.
3. 봉투를 다 벗긴 **알맹이(HTTP 글자)만** 그 소켓의 수신 버퍼에 순서대로 쌓인다.
4. 내 프로그램이 `read(client_fd)`로 꺼낸다.

그래서 내 프로그램이 받는 것은 이런 글자다. MAC, IP, TCP 칸은 하나도 보이지 않는다.

```
GET /index.html HTTP/1.1\r\n
Host: localhost:8080\r\n
\r\n
```

### 끊김 없는 흐름에서 요청 하나 잘라 내기

TCP는 데이터를 끊김 없는 흐름으로 준다. 그래서 `read()` 한 번에 요청이 딱 하나 들어온다는 보장이 없다. 요청이 **반만** 올 수도 있고, keep-alive면 요청 두 개가 **붙어서** 올 수도 있다. 내가 직접 경계를 찾아야 한다.

1. 받은 데이터를 **버퍼에 계속 쌓는다.**
2. 버퍼에서 **빈 줄**을 찾을 때까지 읽는다. 실제 HTTP에서 줄바꿈은 `\r\n`이라 빈 줄은 `\r\n\r\n`이다. 여기까지가 요청 라인과 헤더다.
3. 첫 줄을 공백으로 나눠 **메서드, URI, 버전**을 얻고, 나머지 줄을 `이름: 값`으로 나눠 헤더를 얻는다.
4. `Content-Length`가 있으면 **그만큼 본문을 더 읽는다.** POST 본문이 여기다.
5. 다 읽고도 버퍼에 **남는 데이터는 다음 요청의 시작**이다. 버리지 않는다.

요구사항의 "요청 라인 / 헤더 / 본문의 경계를 어떻게 식별할 것인가"가 정확히 이것이다.

### 과제에서 할 일

- [ ] 연결마다 수신 버퍼를 두고, `\r\n\r\n`을 찾을 때까지 쌓아 읽기
- [ ] 요청 라인 파싱 (메서드, URI, 버전), 최소 GET과 POST 지원
- [ ] 헤더 파싱 (Host, Content-Length, Connection 등)
- [ ] `Content-Length`만큼 본문 읽기, 남은 데이터는 다음 요청으로
- [ ] 엣지 케이스: 헤더 크기와 URI 길이에 상한을 두고, 넘으면 거절하기 (버퍼 오버플로우 방지). 형식이 잘못되면 400, 지원 안 하는 메서드는 501, 지원 안 하는 버전은 505, 너무 큰 본문은 413, 너무 긴 URI는 414
- [ ] 파서를 단위 테스트하기 쉽게 독립 모듈로 (10번의 프록시에서 응답 파싱에도 재사용)

## 5. 응답을 보낸다

요청을 해석했으면 2부 2편의 응답 양식대로 답장을 쓴다.

```
HTTP/1.1 200 OK\r\n
Content-Type: text/html\r\n
Content-Length: 1234\r\n
Connection: keep-alive\r\n
\r\n
(본문 1234바이트)
```

이걸 `write(client_fd)`에 넣으면 운영체제가 TCP, IP, MAC 봉투를 씌워 내보낸다. 답장 주소를 따로 적을 필요는 없다. **소켓이 이미 누구와의 연결인지 알고 있으니, 같은 소켓에 쓰면 그 사람에게만 간다.**

`Content-Length`는 본문의 바이트 수와 **정확히 같아야** 한다. 틀리면 브라우저는 응답이 덜 왔다고 기다리거나, 다음 응답과 섞어 읽는다. 또 `write()`도 한 번에 전부 보낸다는 보장이 없어서, 돌려준 바이트 수를 확인해 남은 부분을 이어서 써야 한다.

### 정적 파일 서빙

요청의 경로(`/index.html`)를 루트 디렉토리 안의 파일로 바꿔 읽고, 그 내용을 본문에 담는다. `Content-Type`은 확장자로 정한다.

| 확장자 | Content-Type |
| --- | --- |
| .html | text/html |
| .css | text/css |
| .js | application/javascript |
| .png | image/png |
| .jpg | image/jpeg |

### 오류 응답

| 상황 | 상태 코드 |
| --- | --- |
| 파일이 없다 | 404 Not Found |
| 권한이 없거나, 루트 밖으로 나가려는 경로 (`/../../etc/passwd`) | 403 Forbidden |
| 서버 안에서 문제가 났다 | 500 Internal Server Error |

### 동적 요청

요청에 따라 파일을 그대로 주는 게 아니라 프로그램을 실행해서 답을 만드는 것이다. CGI 프로그램을 실행하거나, 10번처럼 백엔드 서버로 요청을 전달하는 방식이 있다. POST 본문을 받아 처리하는 곳도 여기다.

### 과제에서 할 일

- [ ] 상태 라인, 표준 헤더(Content-Type, Content-Length, Connection), 빈 줄, 본문 쓰기
- [ ] `write()`가 일부만 보냈을 때 남은 부분 이어 쓰기
- [ ] 루트 디렉토리에서 파일 읽기, MIME 타입 매핑
- [ ] 경로 탈출 막기 (403)
- [ ] 404 / 403 / 500 오류 응답
- [ ] 동적 요청: CGI 또는 백엔드 전달 중 하나 선택

## 6. 같은 연결로 다음 요청이 온다

웹페이지 하나를 열면 HTML 다음에 CSS, 이미지 요청이 줄줄이 온다. HTTP/1.1은 기본적으로 **연결을 열어 두므로(keep-alive)**, 다음 요청은 handshake 없이 같은 `client_fd`로 온다.

한 사용자의 처음부터 끝까지를 표로 보면 이렇다.

| 순서 | 브라우저 | 서버 운영체제 | 내 프로그램 |
| --- | --- | --- | --- |
| 0 |  |  | `listen()` 후 `accept()`에서 기다림 |
| 1 | SYN | SYN-ACK | (아무것도 안 함) |
| 2 | ACK | 연결 완성, 대기 줄에 세움 | (아무것도 안 함) |
| 3 |  |  | `accept()` 반환 → `client_fd` |
| 4 | `GET /index.html` | 수신 버퍼에 넣음 | `read` → 파싱 → `write` |
| 5 | `GET /style.css` | 같은 소켓에 넣음 | 같은 `client_fd`로 `read` → `write` |
| 6 | (한동안 조용) |  | 타임아웃 → `close(client_fd)` |

연결이 열려 있을 때 다시 오면 4번부터, 연결이 닫힌 뒤 다시 오면 1번부터 시작한다.

### 기억하는 통로, 기억하지 않는 쪽지

TCP 연결은 상대를 기억한다. 운영체제는 `client_fd`가 어느 IP, 어느 포트와의 연결인지, 몇 번까지 주고받았는지를 들고 있다. 하지만 그 위의 **HTTP 요청은 서로를 기억하지 않는다(무상태).** 같은 `client_fd`로 온 두 번째 요청도 첫 번째 요청에 기대지 않고 그 자체로 완전해야 한다.

연결이 기억하는 것은 "어느 컴퓨터의 어느 포트"까지다. "어느 사용자(계정)"는 아니다. NAT 때문에 여러 사람이 같은 IP로 나오고, 연결이 닫히면 새 포트로 다시 온다. 그래서 로그인 정보는 연결에 맡기지 않고 **요청마다 쿠키나 토큰으로** 실린다.

### 과제에서 할 일

- [ ] 한 연결에서 요청을 여러 번 처리하는 반복 만들기
- [ ] `Connection: close`면 응답 후 닫고, 아니면 열어 두기 (HTTP/1.1의 기본은 유지)
- [ ] 응답에도 `Connection` 헤더로 내 결정을 알리기
- [ ] 한동안 요청이 없으면 닫는 타임아웃
- [ ] 요청 처리 코드가 이전 요청의 정보에 기대지 않게 만들기

## 7. 연결이 끝난다

연결은 보통 이럴 때 끝난다.

- 요청에 `Connection: close`가 있을 때
- 한동안 요청이 없어 타임아웃이 났을 때
- **`read()`가 0을 돌려줄 때**: 상대가 연결을 끝낸 것(FIN)이다. 브라우저 탭을 닫았거나 갑자기 끊긴 경우다.

어느 경우든 `close(client_fd)`로 테이블을 치운다. 그러면 운영체제가 끝인사(FIN)를 주고받는다. listen 소켓은 닫지 않는다. 안내 데스크는 계속 다음 손님을 받는다.

### SIGPIPE: 이미 떠난 손님에게 응답하면

응답을 쓰는 도중에 상대가 이미 연결을 끊었으면, 운영체제는 내 프로그램에 SIGPIPE 신호를 보낸다. 기본 동작이 **프로그램 종료**라서, 손님 한 명이 떠났다고 서버 전체가 죽는다. 그래서 SIGPIPE를 무시하도록 설정하고, `write()`의 오류(EPIPE)를 보고 그 연결만 정리한다.

### 과제에서 할 일

- [ ] `read()`가 0이면 연결 정리, 음수면 오류 처리
- [ ] 연결이 끝날 때 그 연결의 버퍼(`malloc`한 것)와 소켓을 빠짐없이 회수
- [ ] SIGPIPE 무시, EPIPE 처리
- [ ] SIGINT / SIGTERM을 받으면 열린 소켓과 메모리를 정리하고 끝내는 안전한 셔다운
- [ ] valgrind 또는 `-fsanitize=address,leak`로 누수 확인

## 8. 여러 사용자가 동시에 오면

1\~7번은 한 사용자의 이야기다. 여러 사용자가 오면 **이 흐름이 사용자마다 하나씩 동시에 돌아간다.**

> 사용자 1명 → 연결 1개 → 소켓 1개 (그 연결 안에서 요청은 여러 개)

현지, B, C가 각자 연결하면 `accept()`가 세 번 돌아와 소켓 fd 4, 5, 6이 생긴다. 세 사람의 요청이 거의 동시에 도착해도 섞이지 않는다. 운영체제가 네 값을 보고 각자의 우편함에 나눠 담기 때문이다. `read(4)`를 하면 현지의 요청만 나오고, `write(4)`에 쓰면 현지에게만 간다.

### 왜 동시성이 필요한가

`accept()`와 `read()`는 기다리는(블로킹) 함수다. 프로그램이 한 줄씩 순서대로만 돌면, fd 4에서 현지가 말을 끝낼 때까지 기다리는 동안 B와 C는 아무 답도 못 받고, 입구에 새 손님이 와도 아무도 안내하지 못한다.

| 방식 | 비유 | 장점 | 단점 |
| --- | --- | --- | --- |
| `fork()` | 손님마다 직원을 새로 뽑음 | 단순하고 서로 격리됨 | 무겁고, 손님이 많으면 한계 |
| 스레드 풀 (pthread) | 직원 몇 명을 미리 두고 나눠 맡김 | 가볍고 효율적 | 공유 데이터에 잠금(mutex) 필요 |
| I/O 멀티플렉싱 (`select`, `poll`, `epoll`, `kqueue`) | 직원 한 명이 "편지 도착한 우편함"만 골라 응대 | 연결 수만 개도 가능 (C10K) | 코드가 가장 복잡, non-blocking 필수 |

어느 방식이든 **사용자를 구분하는 건 운영체제와 소켓이 하고, 내 프로그램은 "어느 소켓을 누가 언제 읽을지"만 정한다.** 이것이 요구사항의 "동시성 모델 선택의 트레이드오프"다.

참고로 `epoll` 같은 이벤트 루프로 가면, 요청이 반만 온 연결을 기다리지 않고 다음 연결로 넘어가야 한다. 그래서 4번의 파싱을 처음부터 **연결별 버퍼 기반**으로 만들어 두면 나중에 편하다.

### 과제에서 할 일

- [ ] 동시성 방식 하나 이상 구현 (추천: 스레드 풀로 먼저 동작시키고, 여유가 있으면 이벤트 루프)
- [ ] 여러 클라이언트 동시 접속 기능 테스트
- [ ] `ab`, `wrk`, `hey` 등으로 동시 요청 수에 따른 처리량 측정, 방식별 비교

## Q&A: 헷갈리기 쉬운 것들

1\~8번을 공부하며 실제로 헷갈렸던 것들이다. 대부분 **"누가 무엇을 알고, 무엇을 해 주나?"**가 섞여 보여서 생긴다.

### A. 소켓과 연결

**Q. listen 소켓에서 요청을 읽나?**

아니다. listen 소켓은 손님(연결 요청)만 받는 안내 데스크다. 읽고 쓰는 것은 `accept()`가 돌려준 손님 소켓(`client_fd`)에서 한다. 둘 다 같은 포트지만 상대 IP와 포트까지 포함한 네 값으로 구분된다.

**Q. 3-way handshake는 요청마다 하나?**

아니다. **연결마다 한 번**이고, 내 코드가 아니라 운영체제가 한다. `accept()`가 돌아온 순간에는 이미 끝난 상태다. 그 뒤 같은 연결에서 오는 요청들은 인사 없이 바로 온다.

**Q. HTTP는 무상태라면서, 연결은 상대를 기억하네?**

계층이 다르다. **통로(TCP 연결)는 기억하고, 그 위의 쪽지(HTTP 요청)는 서로를 기억하지 않는다.** 연결이 기억하는 것은 "어느 컴퓨터의 어느 포트"까지라서, "어느 사용자"인지는 요청마다 쿠키나 토큰으로 실어 보낸다.

### B. 버퍼와 요청의 경계

**Q. read() 한 번에 요청 하나가 오나?**

아니다. TCP가 보장하는 것은 "순서대로, 빠짐없이"까지다. "요청 단위로, 한 번에"는 보장하지 않는다. `read()`는 그 순간 쌓여 있는 만큼만 주므로, 요청이 **덜 올 수도**(큰 POST, 느린 네트워크), **붙어 올 수도**(파이프라이닝) 있다. 실제로는 덜 오는 경우가 훨씬 흔하다.

**Q. 버퍼는 하나인가?**

두 개다.

```
[운영체제의 소켓 수신 버퍼]   ← TCP가 순서 맞추고 빈틈 없이 이어 붙여 둔 곳
        ↓ read()
[내 프로그램의 버퍼]         ← 내가 만든 버퍼. 요청을 잘라 내는 곳
```

**Q. 내 버퍼는 요청별로 만드나?**

아니다. **연결별**이다. `read()`할 때는 어느 요청인지 아직 모르기 때문이다. 연결별 버퍼에 계속 이어 붙이고, 맨 앞부터 빈 줄과 `Content-Length`로 요청 하나를 잘라 낸다. 요청별로 만드는 것은 잘라 낸 뒤의 **해석 결과**(메서드, 경로, 헤더, 본문)다.

```
① [POST /echo ...\r\n\r\nname=hyunjiGET /style.css ...\r\n\r\nPUT /a ...]
    └──── 요청 1 ────┘   → 처리하고 앞에서 떼어 냄
② [GET /style.css ...\r\n\r\nPUT /a ...]
    └─── 요청 2 ───┘     → 처리하고 떼어 냄
③ [PUT /a ...]           → 아직 빈 줄이 없음 = 덜 옴 → read()로 더 받기
```

**Q. Content-Length를 확인하지 않으면?**

본문을 다음 요청으로, 또는 다음 요청을 본문으로 착각한다. 프록시와 백엔드가 경계를 다르게 자르면 요청 하나에 다른 요청을 숨겨 넣는 공격(**HTTP Request Smuggling**)이 가능해진다. 이것을 막는 것은 웹서버의 일이다.

| 상황 | 처리 |
| --- | --- |
| `Content-Length`가 없음 | 본문 길이 0 |
| 숫자가 아니거나 음수, 또는 여러 개인데 값이 다름 | 400 |
| 상한보다 큼 | 413 |
| 지원하지 않는 `Transfer-Encoding` (특히 `Content-Length`와 함께 옴) | 거절 (501 또는 400) |
| 경계가 확실하지 않음 | 응답 후 연결을 닫는다 |

### C. 순서는 누가 지키나

**Q. 소켓 버퍼에서 요청들이 섞일 수 있나?**

없다. TCP 연결 하나는 **한 줄짜리 관**이다. 보내는 쪽은 요청 1을 다 넣은 다음에 요청 2를 넣는다. 운영체제가 줄을 세운 게 아니라, **보내는 쪽에서 이미 줄을 서서 나온다.** 정말 동시에 보내고 싶으면 브라우저는 연결(관)을 여러 개 열고, 서버에는 소켓도 버퍼도 여러 개 생긴다.

**Q. 인터넷에서는 조각이 섞여서 도착하지 않나?**

맞다. 하지만 받는 쪽 운영체제가 TCP 순서 번호로 **다시 맞춘 뒤에** `read()`로 준다. 빈틈이 있으면 뒤 조각은 붙잡아 두고, 재전송으로 빈틈이 메워지면 이어서 내준다.

| 구간 | 상태 |
| --- | --- |
| 보내는 쪽 관 입구 | 순서대로 |
| 인터넷 위 | 섞이고, 없어지고, 중복될 수 있음 |
| 받는 쪽 운영체제 | 순서 번호로 복원, 없어진 건 재전송 |
| `read()`로 받는 내 프로그램 | 다시 순서대로 |

**Q. 파이프라이닝은 요청에 번호를 붙여 순서를 지키나?**

아니다. HTTP/1.1 요청에는 번호가 없다. **TCP의 바이트 번호가 요청 경계를 넘어 죽 이어지기 때문에**, 바이트 순서만 복원하면 요청 순서도 저절로 복원된다. 파이프라이닝의 뜻은 "응답을 기다리지 않는다"이지 "섞어 보낸다"가 아니다. 번호가 없으니 클라이언트는 응답도 순서로만 짝짓는다. 그래서 **서버는 응답을 요청이 온 순서대로** 돌려줘야 한다. (HTTP/2는 요청마다 스트림 ID를 붙여 이 제약을 없앰다.)

**Q. TCP의 ACK는 조각이 빠졌을 때만 보내나?**

아니다. 잘 받았을 때도 **계속** 보낸다. ACK는 "여기까지 다 받았으니 다음은 이 번호"라는 **누적** 확인이다. 보내는 쪽은 ACK가 일정 시간 안 오거나, **같은 ACK가 여러 번 반복되면**(중간 조각이 빠졌다는 신호) 재전송한다. "재전송 요청"이라는 메시지가 따로 있는 것은 아니다.

**Q. "요청 보냈어 → 받았어"는 TCP의 확인인가?**

아니다. 그건 **HTTP의 요청과 응답**이다. 두 층의 주고받기는 따로 있다.

| 층 | 단위 | 무엇을 | 누가 |
| --- | --- | --- | --- |
| HTTP | 요청 | 요청하면 응답한다 | 브라우저와 웹서버 (내 코드) |
| TCP | 바이트 (세그먼트) | 계속 ACK, 안 오면 재전송 | 양쪽 운영체제 |

### 정리: 누가 무엇을 하나

| 누가 | 아는 것 | 하는 일 |
| --- | --- | --- |
| 브라우저 | 요청 단위 | 요청을 하나씩 차례로 관에 넣는다 |
| 운영체제 (TCP) | 바이트 순서만 | handshake, 순서 복원, ACK, 재전송. 요청이 뭔지는 모른다 |
| 웹서버 (내 코드) | 요청 단위 (HTTP 규칙으로 알아냄) | 바이트 흐름을 잘라 처리하고, 순서대로 응답한다 |

그래서 웹서버는 TCP 규칙을 몰라도 된다. 신경 쓸 것은 **"덜 왔으면 더 읽기, 붙어 왔으면 정확히 자르기"** 두 가지뿐이다.

## 9. 흐름을 코드 뼈대로

1\~7번의 흐름을 코드 모양으로 모으면 **이중 반복문**이 된다. (실제 C 코드가 아니라 흐름을 보여 주는 의사 코드다.)

```
SIGPIPE 무시, SIGINT/SIGTERM 처리 등록                    ← 7번

listen_fd = socket(TCP)                                      ← 1번
SO_REUSEADDR 설정
bind(listen_fd, 8080)
listen(listen_fd)

바깥 반복 (연결마다):                    ← 한 바퀴 = handshake 한 번 (2번)
    client_fd = accept(listen_fd)                            ← 3번
    (동시성: 여기서 스레드/프로세스에 넘기거나 epoll에 등록)  ← 8번

    안쪽 반복 (요청마다):                ← 한 바퀴 = HTTP 요청 하나 (6번)
        \r\n\r\n이 나올 때까지 read → 버퍼에 쌓기         ← 4번
        read가 0이면 → 탈출                                  ← 7번
        요청 라인, 헤더 파싱
        Content-Length만큼 본문 읽기
        응답 만들기 (파일 / 오류 / 동적 / 프록시)         ← 5번, 10번
        write로 끝까지 보내기
        Connection: close거나 타임아웃이면 → 탈출         ← 6번
        버퍼에 남은 데이터는 다음 요청으로 넘기기

    close(client_fd), 버퍼 free                           ← 7번
```

- **바깥 반복 한 바퀴 = 연결 하나 = handshake 한 번**
- **안쪽 반복 한 바퀴 = HTTP 요청 하나**

안쪽 반복 없이 요청 하나 처리하고 바로 닫으면 HTTP/1.0처럼 요청마다 handshake를 하게 된다. keep-alive 처리란 결국 이 안쪽 반복을 만드는 것이다.

### 추천 구현 순서

한 번에 다 만들기보다 단계마다 `curl -v`로 확인하며 쌓는다.

1. TCP 에코 서버: 받은 걸 그대로 돌려주기 (1\~3번, 7번)
2. HTTP 파싱 + 고정 응답: `curl -v`로 오가는 쪽지 확인 (4번)
3. 정적 파일, MIME, 오류 응답 (5번)
4. POST 본문과 keep-alive (4번, 6번)
5. 동시성 (8번)
6. Reverse Proxy와 Round-Robin (10번)
7. 엣지 케이스, 단위 테스트, 메모리 검사, 부하 테스트

## 10. 덧붙임: Reverse Proxy, 그리고 과제 요구사항 연결표

### Reverse Proxy: 서버이면서 클라이언트

Reverse Proxy는 1부 5편의 DMZ에 서 있는 서버다. 밖에서는 프록시 하나만 보이고, 뒤의 백엔드가 몇 대인지는 모른다.

```
[클라이언트] → [Reverse Proxy :8080] → [백엔드 :8001, :8002 ...]
                 DMZ에 서 있는 서버        내부망에 숨은 서버
```

프록시는 **서버이면서 동시에 클라이언트**다.

- 클라이언트 쪽: 지금까지처럼 `accept()`로 받는 서버
- 백엔드 쪽: `socket()` + `connect()`로 연결을 거는 클라이언트. 이번에는 내 코드가 3-way handshake를 **시작하는** 쪽이다.

백엔드의 응답을 읽을 때도 똑같은 파싱(빈 줄 + Content-Length)이 필요하다. 그래서 4번의 파서를 요청과 응답 모두에 쓸 수 있게 만들어 두면 좋다.

| 요구사항 | 이어지는 내용 |
| --- | --- |
| 경로 기반 라우팅 (`/api/*` → 8001) | 요청 라인의 경로를 본다. HTTP 쪽지를 열어 보므로 L7 로드밸런서다 (1부 6편) |
| Round-Robin | 백엔드를 번갈아 고른다. 무상태 덕분에 어느 백엔드로 보내도 된다 (2부 2편 REST 원칙 2) |
| 백엔드 응답 없음 | 연결 실패는 502 Bad Gateway, 너무 오래 걸리면 504 Gateway Timeout |

**Forward Proxy**는 반대로 클라이언트를 대신해 밖으로 나간다. 요청 라인이 `GET http://example.com/index.html HTTP/1.1`처럼 전체 주소로 오고, 호스트 이름을 `getaddrinfo()`로 IP로 바꾼다. 1부 3편의 DNS 조회다. 한 줄로 정리하면 **Forward Proxy는 클라이언트를, Reverse Proxy는 서버를 대신한다.**

### 과제 요구사항 연결표

| 요구사항 | 이 글 | 시리즈 |
| --- | --- | --- |
| TCP 소켓 서버 (socket → bind → listen → accept) | 1\~3번 | 2부 3편 TCP |
| 3-way handshake, SO\_REUSEADDR, accept 블로킹 | 1\~3번 | 2부 3편 3번 |
| HTTP 요청 파싱, 경계 식별, Content-Length | 4번 | 2부 2편 HTTP, 2부 3편 4번 |
| HTTP 응답 생성 | 5번 | 2부 2편 4번 |
| 정적 파일, MIME, 404/403/500 | 5번 | 2부 2편 6번 (Content-Type) |
| Connection: keep-alive | 6번 | 2부 3편 4번 |
| 동시 요청 처리, C10K | 8번 |  |

참고로 과제에 적힌 RFC 7230\~7235는 2022년 RFC 9110, 9112 등으로 갱신됐다. 내용은 거의 같다.

## 마치며

이제 "Hello"의 여행이 완성됐다. 1부에서는 길을, 2부 1\~3편에서는 그 길을 달리는 짐을, 이번 편에서는 짐이 서버에 도착한 뒤 프로그램이 어떻게 받고 답하는지를 봤다.

- 운영체제는 봉투를 벗기고 handshake를 하고, 연결마다 **소켓(우편함)**을 만들어 둔다.
- 내 프로그램은 listen 소켓으로 손님을 받고, 손님 소켓에서 **HTTP 글자만 꺼내 읽고 답장을 넣는다.**
- TCP는 끊김 없는 흐름이라, 요청의 경계는 **빈 줄과 Content-Length**로 내가 찾는다.
- **바깥 반복은 연결마다, 안쪽 반복은 요청마다.** 여러 사용자는 이 흐름이 동시에 여러 개 도는 것이다.

구현하다 막히면 "이건 몇 층 문제지?"부터 묻는다. 연결이 안 되면 전송 계층(소켓, 포트), 요청이 이상하게 잘리면 TCP 흐름과 HTTP 경계, 브라우저가 응답을 못 알아들으면 HTTP 양식 문제다.
