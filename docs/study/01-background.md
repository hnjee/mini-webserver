# 1. 웹서버는 왜 등장했나 (역사와 배경)
> - 클라이언트-서버 모델: 요청하는 쪽과 응답하는 쪽
> - 정적 웹 → CGI → 애플리케이션 서버 → 프록시 앞단 구조로의 흐름
> - 각 단계에서 어떤 문제를 해결하려고 다음 단계가 나왔는지

---

## 클라이언트-서버 모델
- **클라이언트** : 통신에서 먼저 말을 거는 쪽
- **서버** : 그 요청을 기다리다 응답하는 쪽
- 통신 구조 : 브라우저에서 `http://example.com/index.html`을 열 때
  ``` plain text
  브라우저(클라이언트)  ──"index.html 줘"──▶  웹서버
  브라우저(클라이언트)  ◀──"여기 내용"────  웹서버
  ```
  - 클라이언트와 서버의 역할은 장치가 아니라 "행동"으로 정해짐. 하나의 장치가 두 역할을 다 하기도 (예 : 프록시)
  - **서버가 대기**(`listen()`) → **클라이언트가 먼저 시작**(`accept()`)하는 구조임

---

## 웹 서버
#### 변천 흐름
``` mermaid
flowchart LR
  subgraph S1["① 정적 웹"]
    direction LR
    a1["요청"] --> a2["웹서버"] --> a3[("디스크 파일")]
    a3 -. "파일 그대로 응답" .-> a1
  end

  subgraph S2["② CGI"]
    direction LR
    b1["요청"] --> b2["웹서버"] -->|"fork + exec"| b3["프로그램<br/>(요청마다 새 프로세스)"]
    b3 -. "출력이 응답" .-> b1
  end

  subgraph S3["③ 애플리케이션 서버"]
    direction LR
    c1["요청"] --> c2["웹서버"] --> c3["상주 앱 코드<br/>(프로세스 재사용)"]
    c3 -. "처리 결과 응답" .-> c1
  end

  subgraph S4["④ 프록시 앞단"]
    direction LR
    d1["요청"] --> d2["프록시"] --> d3["앱 서버 1·2·…"]
    d3 -. "응답 중계" .-> d1
  end

  S1 ==>|"다음 단계 등장"| S2 ==> S3 ==> S4
```
#### 공존 구조
``` mermaid
flowchart LR
  C["클라이언트"] --> P["④ 프록시"]
  P -->|"정적 요청 (/static/*)"| F["① 정적 파일 서빙"]
  P -->|"동적 요청 (/api/*)"| A1["③ 앱 서버 1"]
  P -->|"동적 요청 (/api/*)"| A2["③ 앱 서버 2"]
  A1 -.->|"필요 시"| G["② CGI 방식 프로그램"]
```
- **정적 웹** : 경로 → 파일 읽기를 담당
- **CGI** : 프로그램을 실행하고 출력을 받아 전달하는 역할을 함 (매번 새로운 프로세스 실행 → 응답 후 종료)
- **앱 서버** : 이미 떠 있는 앱에 요청을 넘김 (계속 떠있고, 메모리도 공유됨)
- **프록시** : 요청을 어디로 보낼지 결정하고 중계함 
  - 로드 밸런싱은 프록시가 할 수 있는 여러 일 중 하나일 뿐임.
  - 그 외에 캐싱, 보안, 정적 파일 직접 처리 등도 담당

---

## 변화
#### 정적 웹
- 한계 : 파일 내용이 고정이라, 사용자마다·시점마다 다른 페이지(게시판, 로그인 등)를 못 만든다
- 해결 : 요청 시 프로그램을 실행해서 응답을 만들자 (`CGI`)
#### CGI 
- 한계 : 요청마다 프로세스를 새로 띄워서 느리고(시작비용), 요청이 몰리면 부담이 크다. 상태도 유지되지 않는다.
- 해결 : 프로그램을 계속 띄워 두고 재사용하자 (`앱 서버`)
#### 앱서버
- 한계 : 앱 서버 하나로는 트래픽, 장애, 정적 파일 처리, 보안을 다 감당하기 어렵다. 앱 서버가 여러 대로 늘어나면 "누구에게 보낼지"를 정해야 한다.
- 해결 : 앞에서 요청을 받아 나눠주는 계층을 두자 (`프록시`)
