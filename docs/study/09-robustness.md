# 9. 견고성과 검증
> - 시그널: SIGINT / SIGTERM 안전한 종료, SIGPIPE 무시
> - 자원 회수(fd, 메모리), 버퍼 오버플로 방지
> - 엣지 케이스: 잘못된 요청, 매우 큰 요청, 갑작스러운 연결 종료
> - 검증 도구: 단위 테스트, curl, ab / wrk, valgrind / AddressSanitizer

---

## 시그널과 SIGINT / SIGTERM 안전한 종료
- **시그널(signal)** : 커널이 프로세스에 보내는 짧은 알림
  - 서버가 이 알림을 직접 받아 처리하면, 종료할 때 정리할 시간을 얻음
  - 서버가 이 알림을 직접 받아 처리하지 않으면, 서버는 알림을 받음과 동시에 죽음
  | 시그널 | 알림 주체 | 의미 |
  | --- | --- | --- |
  | `SIGINT` | 터미널에서 Ctrl + C를 누르면 터미널이 보냄 | "중단해 주세요" |
  | `SIGTERM` | `kill <PID>`의 기본값, Docker `stop`, 프로세스 관리자 | "종료해 주세요" |
  | `SIGKILL` | `kill -9` | 잡을 수도 무시할 수도 없음. 커널이 즉시 종료. |
- 시그널의 영향
  - 응답을 쓰던 중이면, 클라이언트는 `Content-Length`보다 적은 바이트만 받고 끊김
  - 서버가 `malloc`한 메모리와 열어둔 fd는 프로세스가 끝나면 커널이 회수함. 누수 문제는 아님.
  - 로그 버퍼를 `fflush`하지 못하고, CGI 자식이 부모 없이 남을 수 있음
#### 시그널 핸들러
- `sigaction` : 시그널이 왔을 때 실행할 함수, 즉 핸들러를 등록하는 시스템 콜
- 핸들러 : 메인 코드가 어디를 실행하고 있든, 그 자리를 끊고 들어옴. 
  - 핸들러 안에서 할 수 있는 일도 제한적임
  - `malloc`·`free`·`printf`는 안전하지 않음 (메인 코드가 `malloc` 내부에서 자료 구조를 고치던 중이라면 핸들러의 malloc과 충돌)
  - 그래서 보통 핸들러는 플래그 하나만 세우고 끝내고, 실제 정리는 메인 루프가 함.
    ``` c
    // 설명용 의사 코드 (프로젝트 구현 아님)
    static volatile sig_atomic_t g_stop = 0;

    static void on_signal(int sig) { g_stop = 1; }   // 핸들러는 이것만

    // main: sigaction(SIGINT, ...), sigaction(SIGTERM, ...) 로 on_signal 등록

    while (!g_stop) {
        n = epoll_wait(...);          // 시그널이 오면 -1, errno==EINTR 로 깨어남
        if (n < 0 && errno == EINTR) continue;   // 루프 맨 위에서 g_stop 재검사
        ...
    }
    // 루프 밖: 정리 단계

    ```
    - `volatile sig_atomic_t` : 핸들러가 바꿀 수 있어서 컴파일러가 최적화로 값을 캐시하면 안 되고, 한 번에 안전하게 읽고 쓸 수 있는 정수형
    - 블로킹 중인 `accept`나 `epoll_wait`는 시그널이 오면 핸들러를 실행한 뒤, -1, errno == EINTR로 돌아옴. 이 때 `g_stop`을 확인

## SIGPIPE 무시
- `SIGPIPE` : 이미 끊어진 연결에 `write`하면 서버가 받는 시그널. 기본 동작은 프로세스 종료.
- `SIGPIPE` 무시 필요 : 클라이언트 하나가 갑자기 끊겼다고 서버 전체가 죽으면 안 됨
  ``` mermaid
  sequenceDiagram
    participant C as 클라이언트
    participant S as 서버 프로세스
    participant K as 서버 커널

    C->>K: close 로 연결 포기
    S->>K: write 1회 (응답 앞부분)
    K->>C: 데이터 전송
    C-->>K: RST (이미 닫힌 소켓)
    S->>K: write 2회 (응답 뒷부분)
    K-->>S: SIGPIPE 전달 + write 가 -1 반환 (EPIPE)
    Note over S: 기본 동작이면 프로세스 종료
  ```
- 핵심 구조 : 시그널은 무시, 오류는 반환값으로 처리
  ``` c
  // 설명용 의사 코드 (프로젝트 구현 아님)
  signal(SIGPIPE, SIG_IGN);      // 시작할 때 한 번. SIG_IGN = 이 시그널을 아예 무시

  n = write(conn_fd, buf, len);
  if (n < 0 && errno == EPIPE) {
      close_conn(conn);          // 이 연결만 정리. 서버는 계속 동작
  }
  ```
- **시그널 무시**와 **반환값 검사**는 한 세트임. 시그널만 무시하고 반환값을 확인하지 않으면 서버는 끊어진 연결을 정리하지 않음
- `SIGPIPE`는 `write`쪽 문제임

## 자원 회수 (fd, 메모리)
- 서버가 오래 살아 있으려면 연결 하나가 끝날 때마다 그 연결을 위해 가져온 자원(fd, 메모리)을 빠짐없이, 정확히 한 번 돌려줘야 함
- 한 번이라도 빠지면 쌓여서 서버가 서서히 죽고, 두 번 돌려주면 엉뚱한 곳이 망가짐
- 핵심 구조 : 끝나는 이유가 다 다르더라도, 정리는 한 곳으로 모여야 함.
  ``` mermaid
  flowchart LR
      A[accept<br/>conn_fd 획득] --> B[conn malloc<br/>epoll 등록]
      B --> C[요청 처리]
      C --> D{끝나는 이유}
      D -->|정상 종료| E[정리]
      D -->|read==0 FIN| E
      D -->|EPIPE / 오류| E
      D -->|타임아웃| E
      E[epoll 해제 + close + free]
  ```
  ``` c
  // 정리 순서
  void close_conn(conn_t *c) {
      if (c == NULL) return;
      epoll_ctl(epfd, EPOLL_CTL_DEL, c->fd, NULL); // 1. 감시 해제
      close(c->fd);                                // 2. fd 닫기
      free(c->inbuf);                              // 3. 버퍼
      free(c);                                     // 4. 구조체 마지막
  }
  ```

## 버퍼 오버플로와 크기 상한
- 클라이언트가 보내는 데이터의 크기는 서버가 정할 수 없음
- 서버는 "얼마까지 받을지" 직접 정해두고, 그 선을 넘으면 거절해야 함 (이 선이 없으면 오버플로 발생)
- 두 가지 문제
  | | 버퍼 오버플로 | 무한 증가 |
  | --- | --- | --- |
  | 버퍼 종류 | 고정 크기 배열 | 늘어나는 버퍼 (`realloc`) |
  | 원인 | 배열보다 많은 바이트 씀 | 상대가 계속 보내면 계속 키움 |
  | 결과 | 옆 메모리를 덮어씀 (크래시, 보안 취약점) | 메모리 고갈 (OOM, 서버 전체 영향) |
  | 방어 | 쓰기 전에 남은 칸 수를 계산 | 늘리기 전에 최대 크기를 확인 | 
- 예시 방어 코드
  ``` c
  // 설명용 (프로젝트 구현 아님)
  char inbuf[4096];
  size_t used = 0;

  // ✗ 위험: 남은 칸을 안 본다
  n = read(fd, inbuf + used, 8192);     // 최대 8192를 4096짜리에 쓸 수 있음
  used += n;

  // ○ 안전: 남은 칸 = 용량 - 사용량 만큼만 요청
  size_t room = sizeof(inbuf) - used;
  if (room == 0) { /* 가득 참 → 상한 초과로 처리 (아래 참조) */ }
  n = read(fd, inbuf + used, room);
  used += n;
  ```
- 상한을 넘은 요청 (진행 중인 읽기, 쓰기 포함) → 더 진행하지 말고 거절 & 연결 종료
  ``` mermaid
  flowchart TD
    A[read로 데이터 수신] --> B{헤더 끝 찾음?}
    B -->|예| C[요청 처리]
    B -->|아니오| D{used가 상한에 도달?}
    D -->|아니오| A
    D -->|예| E[431 응답 후 close_conn]
  ```

## 엣지 케이스
- 서버에는 정상적인 요청만 들어오지 않음. 
  - **잘못된 요청** : 잘못된 요청이라는 판단을 하는 기준이 중요함. (형식이 틀린 것인지, 아직 데이터가 덜 도착한 것인지)
  - **매우 큰 요청** : 크기 상한을 넘지 않는 구조인지 확인 필요.
  - **갑작스러운 연결 종료** : 읽는 중 연결이 끝났다면 미완성 요청을 처리하지 않고 연결 자원 정리.
  - (프록시) **백엔드가 응답하지 않는 경우** : 무한히 기다리지 말고 시간 제한을 둬야 함. 클라이언트 요청이 잘못된 것이 아니라 뒤쪽 서버의 응답을 기다리다 실패한 것이므로, 400과 구별
- 서버는 잘못된 요청에 대해 연결을 적절히 끝내고, 서버 자체는 계속 돌아가야 함.

## 검증 도구
- 단위 테스트 : 이 모듈 하나가 기대대로 동작하나? (테스트 프로그램으로 검사)
- 기능 테스트 : 실제 클라이언트로 연결했을 때 전체가 동작하나? (curl, 브라우저 등으로 확인)
- 부하 테스트 : 요청이 많이 몰려도 처리량이 유지되나? (ab, wrk, hey)
- 메모리 검사 : 누수나 잘못된 메모리 접근이 없나? (valgrind, -fsanitize=address,leak)
