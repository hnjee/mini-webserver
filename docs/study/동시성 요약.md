## 문제 A: `read()`에서 읽을 게 없으면 하나뿐인 스레드가 잠든다

수신 버퍼가 비어 있으면 `read()`는 데이터가 올 때까지 스레드를 재운다(**블로킹 I/O**). 스레드가 하나뿐이면 그동안 다른 손님을 아무도 못 받는다.

**클라이언트 상황**
1. 실제로 요청이 늦게 옴 (느린 네트워크, 큰 업로드)
2. keep-alive: 연결을 안 끊고 다음 요청을 기다림 → 유휴 시간 15초 → `close()`

원인이 **손님**에게 있어서, 서버가 아무리 빨라도 피할 수 없다.

### `read()`에서 잠드는 문제를 푸는 방법 3가지

| 방법 | 동작 | 결과 |
|---|---|---|
| ① 스레드를 늘린다 | 잠드는 건 그대로, 스레드 수로 버팀 | ✗ **스레드 낭비**. 스레드는 무한하지 않고, 손님 수만큼 필요해진다 |
| ② 논블로킹 + while문으로 확인 | `read()`가 안 잠들고 없으면 `EAGAIN`. 웹서버 스레드가 모든 소켓을 계속 물어봄 | ✗ **CPU 낭비**. 아무 일이 없어도 CPU 100% (바쁜 대기) |
| ③ I/O 멀티플렉싱 | 소켓들을 커널에 등록하고 잠들어 있다가, OS가 준비된 걸 알려 주면 그것만 처리 | ✓ 할 일 없으면 CPU 0%, 스레드 하나로 연결 수만 개 |

```c
// ② while문으로 계속 확인 — 웹서버 스레드가 "왔어? 왔어?" 계속 물어봄
while (1) {
    for (fd in 모든_소켓) {
        if (read(fd, ...) == -1 && errno == EAGAIN) continue;
        처리(fd);
    }
}

// ③ I/O 멀티플렉싱 — 커널이 "왔어!" 하고 깨워 줌
while (1) {
    n = epoll_wait(ep, ready, 64, -1);   // 준비된 게 생길 때까지 잠듦
    for (준비된 소켓) 처리;
}
```

> **블로킹은 스레드를 낭비하고, 논블로킹 폴링은 CPU를 낭비해서, 둘 다 안 하려고 I/O 멀티플렉싱이 나왔다.**
> 이게 곧 **연결과 일하는 스레드를 분리**하는 것이다.

### ③ 안에서도 발전이 있었다: select → poll → epoll

| | 기다리는 동안 | 깨어난 뒤 | 감시 목록 |
|---|---|---|---|
| `select` | 잠듦 ✓ | **전부 다시 확인** (O(n)) | 매번 다시 넘김, 보통 1024개 제한 |
| `poll` | 잠듦 ✓ | **전부 다시 확인** (O(n)) | 매번 다시 넘김, 개수 제한 없음 |
| `epoll` | 잠듦 ✓ | **준비된 것만** 받음 | 커널에 남아 있음 (한 번만 등록) |

### epoll: 관심 목록 / 준비 목록

```
[커널의 epoll 객체]
  ├─ 관심 목록: 등록한 소켓들 (수만 개 가능)
  └─ 준비 목록: 데이터가 와서 지금 처리할 수 있는 소켓들
```

데이터가 소켓 수신 버퍼에 들어오는 **그 순간** 커널이 그 소켓을 준비 목록에 올리고 잠든 스레드를 깨운다. 스레드는 준비 목록만 받아서 처리한다.

함께 필요한 것:
- **논블로킹 소켓**: 깨어난 뒤 `read()`가 다시 잠들지 않게
- **연결별 상태 구조체**: 덜 온 요청, 덜 보낸 응답을 기억

## 문제 B: 요청을 처리하는 스레드가 서버 일 때문에 또 잠든다

- 파일 읽기, DB 조회 같은 I/O를 기다리는 시간이 생긴다.
- 그동안 CPU가 논다.

### 해결: 멀티스레드

스레드가 I/O를 기다리면 **OS가 그 스레드를 재워 두고, 다른 스레드에게 CPU를 넘긴다.** 그러니 스레드가 여러 개면, 몇 개가 기다리는 동안 나머지가 일한다. 코어도 여러 개 쓸 수 있다.

### 관리: 스레드 풀 (워커)

요청마다 스레드를 새로 만들면 생성 비용과 메모리가 들고, 손님이 몰리면 끝없이 늘어난다. 그래서

- 정해진 수만큼 **미리 만들어 재사용**하고
- 넘치는 일은 **큐에서 기다리게** 한다.

**고민**: 몇 개 만들까? → CPU 코어 수 + I/O 대기 정도

**해답**:

> 워커 수 ≈ 코어 수 × (1 + 기다리는 시간 ÷ 계산하는 시간)

예: 코어 4개, 요청당 계산 2ms · DB 대기 8ms → 4 × (1 + 8 ÷ 2) = **20개**

### 같은 멀티스레드인데, 왜 A에선 ✗이고 B에선 ✓일까?

| | 문제 A (해결 ①) | 문제 B |
|---|---|---|
| 기다리는 대상 | 손님 (언제 보낼지 모름) | 서버 일 (DB, 파일: 금방 끝남) |
| 스레드는 | **손님에게 붙잡혀** 무한정 잠듦 | 잠깐 잠들었다 곧 돌아옴 |
| 필요한 스레드 수 | 손님 수만큼 → 감당 불가 | 몇 개만 있어도 번갈아 CPU를 채움 |

같은 도구라도 **무엇을 기다리느냐**에 따라 실패도 하고 정답도 된다.

## 우리 서버: epoll + 스레드 풀

- **A**: 조용한 연결은 epoll이 지켜본다.
- **B**: 한 워커가 I/O로 잠들어도 다른 워커가 계속 일한다.
- → epoll과 워커 스레드를 함께 쓴다.

### 두 가지 방식으로 각각 구현했다

**방식 1: 워커 스레드마다 epoll**

```
        [리슨 소켓 (워커들이 공유)]
         ↓       ↓       ↓       ↓
      [워커 1] [워커 2] [워커 3] [워커 4]
      epoll    epoll    epoll    epoll
      연결 여러 개씩
```

받은 워커가 연결을 끝까지 맡아서 **락이 필요 없다.** (nginx와 같은 구조)

**방식 2: epoll 하나 + 작업 큐**

```
[메인 스레드: epoll 1개] → [작업 큐] → [워커 1 … N]
```

메인이 준비된 연결을 큐에 넣고, 워커가 꺼내 처리한다. 큐는 여러 워커가 함께 쓰므로 락으로 보호한다.

## "epoll이 뭐고 왜 쓰나요?" 한 줄 답변

> `read()`는 데이터가 없으면 스레드를 재우는 블로킹 방식이라 연결마다 스레드가 묶이고, 논블로킹으로 바꾸면 언제 왔는지 몰라 계속 확인하느라 CPU를 낭비합니다. 그래서 소켓들을 커널에 등록해 두고 **준비된 것만 알려 받는 I/O 멀티플렉싱**을 쓰고, 리눅스에서 이걸 효율적으로 하는 게 epoll입니다. select/poll은 매번 전부 훑지만 epoll은 준비된 것만 돌려줍니다.

핵심: **블로킹 → 스레드 낭비, 논블로킹 폴링 → CPU 낭비, 그래서 I/O 멀티플렉싱(epoll).**
