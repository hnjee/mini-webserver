# 웹서버 동작 원리 3편: 리버스 프록시와 로드밸런싱

> 정적 파일만 주던 웹서버가 동적 요청까지 처리하게 되는 과정을 따라간다.
> **문제 → 해결책 → 남은 문제 → 다음 해결책** 순서로 간다.
>
> 이전 편: [1편: 요청 하나의 여정](./01-요청-하나의-여정.md) · [2편: 동시성](./02-동시성.md)

```
정적만 처리하던 서버
  → 동적 요청은 API 서버에 맡기기로 함                          (왜? → 2장)
  → 내 서버가 API 서버의 리버스 프록시가 되어 전달·중계        (리버스 프록시 → 3장)
  → API 서버가 감당 못 할 만큼 요청이 많아 복사본을 여러 대 띄우면
     → 그중 누구에게 보낼지 번갈아 고름                       (로드밸런싱 → 4장)
```

---

## 1. 출발점: 정적만 처리하던 서버

1편, 2편의 서버는 이렇게 동작한다.

```
손님 → [내 서버]
        1. accept
        2. read: "GET /index.html"
        3. 디스크에서 index.html 찾기
        4. write: 파일 내용 응답
```

동시성(epoll 또는 스레드풀)까지 붙여서 손님 여러 명을 동시에 받을 수 있다. 그런데 이런 요청이 오면 답할 수 없다.

```
GET /api/users?id=3
```

디스크에 `users`라는 파일이 있는 게 아니다. **DB에서 3번 사용자를 찾아 그때그때 답을 만들어야** 한다.

| | 정적 요청 | 동적 요청 |
|---|---|---|
| 응답 | 디스크에 **이미 있는 파일** 그대로 | 요청마다 **프로그램이 새로 만든** 결과 |
| 예 | `/index.html`, `/logo.png` | `/api/users?id=3`, 로그인, 검색 |
| 필요한 것 | 파일 읽기 | DB 조회, 비즈니스 로직 |

## 2. 동적 요청은 API 서버에 맡긴다: 왜 분리하나

내 웹서버 안에 DB 조회와 로직을 직접 넣을 수도 있다. 그런데 보통은 **답을 만드는 프로그램(API 서버)을 따로 두고**, 웹서버는 그쪽에 맡긴다. 이유는 다음과 같다.

### 2-1. 하는 일의 성격이 완전히 다르다

| | 정적 처리 | 동적 처리 |
|---|---|---|
| 무게 | 가볍고 빠름 (페이지 캐시에서 바로) | 무겁고 느림 (DB 대기, 계산) |
| 기다림 | 거의 없음 | **문제 B** (2편: 서버 쪽 일 때문에 기다림) |
| 잘하는 도구 | C, epoll, `sendfile` | Spring, Django, Express 같은 프레임워크 + DB 드라이버 |

웹서버는 **파일을 빠르게 많이 보내는 일**에 맞춰 만든 프로그램이다. 여기에 로그인, 결제, 검색 로직을 전부 C로 넣으면 웹서버가 비대해지고, 각 일을 잘하는 도구를 쓸 수도 없다.

### 2-2. 섞여 있으면 느린 동적 요청이 정적 요청까지 막는다

2편 6-4에서 본 것처럼, 느린 요청이 워커나 이벤트 루프를 잡으면 가벼운 요청까지 기다린다.

```
한 서버에서 둘 다 처리할 때
DB가 느려짐 → 동적 요청들이 워커를 다 잡음 → logo.png 하나도 못 받음
```

분리해 두면 API 서버가 느려져도 웹서버는 정적 파일을 계속 빠르게 준다. 2편의 **벌크헤드**와 같은 발상이다.

### 2-3. 따로 늘리고, 따로 고치고, 따로 죽는다

- **확장**: 동적 요청만 많아지면 API 서버만 늘리면 된다 (→ 4장).
- **배포**: 앱 로직은 자주 바뀐다. API 서버만 다시 배포하면 되고 웹서버는 그대로 둔다.
- **장애 격리**: 앱에 버그가 있어 API 서버가 죽어도, 웹서버는 살아서 정적 파일을 주고 `502`로 "뒤쪽이 문제다"라고 답할 수 있다.

### 2-4. 웹서버가 API 서버에 맡기는 방법의 변천

| | CGI | FastCGI | 리버스 프록시 |
|---|---|---|---|
| 앱 프로세스 | 요청마다 새로 실행 (`fork` + `exec`) | 미리 띄워 재사용 | 미리 띄워 재사용 (앱이 HTTP 서버) |
| 웹서버 ↔ 앱 | 환경 변수 + stdin/stdout | FastCGI 프로토콜 | **HTTP** |
| 특징 | 단순하지만 요청마다 프로세스 생성이라 비쌈 | PHP-FPM | 이미 만든 HTTP 처리를 그대로 씀 |

지금은 API 서버 자체가 HTTP 서버로 떠 있고(예: 8001번 포트), 웹서버는 HTTP 요청을 그대로 전달하는 **리버스 프록시** 방식이 가장 흔하다.

> **핵심: 웹서버가 동적 처리를 직접 하는 게 아니라, 전달하는 기능을 넣는 것이다.**

## 3. 내 서버가 리버스 프록시가 된다

### 3-1. 갈림길 하나 추가

```
handle(손님 fd):
    요청 = read(손님)                          ← 이미 만든 부분

    if 경로가 /api/ 로 시작:                    ← 새로 추가
        b = connect(127.0.0.1:8001)            ← 이번엔 내 서버가 "손님"이 됨
        write(b, 요청)                          ← 받은 요청을 그대로 전달
        응답 = read(b)                          ← 백엔드의 답 받기
        write(손님, 응답)                        ← 손님에게 전달
    else:
        디스크에서 파일 찾아서 응답               ← 기존 코드 그대로 (정적)
```

```
손님 ──요청──→ [내 서버] ──같은 요청──→ [API 서버 8001]
손님 ←─응답─── [내 서버] ←──응답────── [API 서버 8001]
```

손님은 8001이 있는지도 모른다. 내 서버가 답한 줄 안다.

### 3-2. 프록시 = 받아 주고, 대신 보낸다

```
받아 준다 (서버 역할)   +   대신 보낸다 (클라이언트 역할)
  accept, read             connect, write
```

- **받아 주기만 하면** → 그냥 웹서버 (지금까지의 내 서버)
- **받아 주고 대신 보내면** → 프록시

손님 입장에서는 프록시가 대화 상대, 즉 **연결의 끝**이다. 그래서 대리인이 될 수 있다. 과제의 "프록시는 서버이자 클라이언트다"가 이 뜻이다.

### 3-3. 프록시 안에서 일어나는 일

```
[손님]              [내 서버: OS + 내 프로그램]                    [API 서버 8001]
SYN ─────────→  커널이 handshake → accept 대기열
                accept()  → 손님 소켓 (fd 5)
요청 ────────→  read(5)   → "GET /api/users"
                "/api네 → 8001"
                connect(8001) → 커널이 SYN ─────────────────→ API 서버 커널
                              → 백엔드 소켓 (fd 7)
                write(7, 요청) ─────────────────────────────→ 처리
                read(7)   ←─────────────────────────────────── 응답
응답 ←───────── write(5, 응답)
```

- 손님 쪽은 1편 그대로다. 내 서버의 커널이 handshake를 해 주고 프로그램이 `accept`, `read`.
- 백엔드 쪽은 반대다. 프로그램이 `connect`를 부르면 내 서버의 커널이 **손님 입장이 되어** SYN을 보낸다.
- 소켓이 **두 개**, 각각 수신·송신 버퍼가 따로 있다.
- 백엔드가 같은 컴퓨터(`127.0.0.1`)여도 루프백으로 똑같이 동작한다.

### 3-4. 왜 굳이 연결을 따로 맺나

경로는 handshake가 **끝난 뒤에** 온다.

```
1. SYN → 2. SYN-ACK → 3. ACK → 4. "GET /api/users ..."  ← 경로는 여기서 처음 옴
```

경로를 보고 보낼 곳을 고르려면 **먼저 연결을 받아 주고** 요청을 들어야 한다. 그러면 손님과의 연결은 이미 내 서버와 맺어진 상태이니, 백엔드와는 새로 연결할 수밖에 없다.

덤으로 생기는 것:
- 헤더 고치기 (`X-Forwarded-For`로 진짜 손님 IP 전달)
- 백엔드가 실패해도 손님 연결을 쥐고 있으니 **502, 504로 대신 답하기**
- 요청이 완성될 때까지 받아 두었다가 백엔드에 빠르게 넘기기 (느린 손님 흡수)

### 3-5. 왜 "리버스" 프록시인가

| | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 위치 | 손님 → [프록시] → 인터넷 → 서버 | 손님 → 인터넷 → [프록시] → 서버 |
| 누구 편 | 손님 편 (손님이 알고 설정함) | 서버 편 (손님은 모름) |
| 예 | 회사 프록시, VPN | nginx, 지금 만드는 내 서버 |

### 3-6. 백엔드가 이상할 때

```
connect()가 바로 거부됨 (백엔드가 꺼짐, ECONNREFUSED)      → 502 Bad Gateway
connect()는 됐는데 응답이 안 옴 (nc -l 8001 실험)          → 응답 제한 시간 초과 → 504 Gateway Timeout
```

응답 타임아웃이 없으면 프록시가 영원히 기다린다.

### 3-7. 동시성 서버 위에서 주의할 점

`read(b)`에서 백엔드 응답을 기다리는 건 **2편의 문제 B**다.

- **스레드풀 서버**: 위 코드 그대로 써도 된다. 워커 하나가 기다리는 동안 다른 워커가 일한다.
- **epoll 서버**: 기다리면 루프 전체가 멈춘다(2편 6-3). 백엔드 fd도 epoll에 등록하고, `connect()`도 논블로킹으로(`EINPROGRESS` → `EPOLLOUT`) 한다. 연결별 상태 구조체에 손님 fd ↔ 백엔드 fd 짝과 현재 단계를 기록한다.

## 4. 복사본이 여러 대면 → 로드밸런싱

### 4-1. 왜 같은 API 서버를 여러 대 띄우나

1. **한 대로 감당이 안 돼서**: 요청이 처리량을 넘으면 큐가 끝없이 길어진다. 똑같은 API 서버를 여러 대 띄워 나눠 받는다.
2. **한 대가 죽어도 서비스가 계속되게**: 8001이 죽어도 8002가 받는다.

복사본을 마음대로 늘릴 수 있는 건 API 서버가 **무상태**이기 때문이다. 로그인 세션 같은 상태를 서버 메모리가 아니라 Redis 같은 외부 저장소에 두면, 어느 복사본이 받아도 답이 같다.

### 4-2. 보낼 곳을 고르는 두 단계

프록시가 "대신 보낸다" 직전에 하는 결정이다.

```
1. 받아 준다      accept, read → "GET /api/users"
2-1. 라우팅       "/api/ 니까 → api 그룹 [8001, 8002]"     어느 역할로?
2-2. 로드밸런싱   "지난번엔 8001이었으니 이번엔 → 8002"      같은 역할 중 누구에게?
3. 대신 보낸다    connect, write, read
4. 답을 전한다    write(손님)
```

```
/api/*   → 8001, 8002     같은 역할 2대 중 고르기   → 로드밸런싱
/admin/* → 8003           다른 역할로 보내기        → 라우팅
그 외    → 내가 직접 파일 응답 (정적)
```

후보가 하나뿐이면 2-2는 할 일이 없다. **후보가 둘 이상일 때 그중 하나를 고르는 규칙이 로드밸런싱**이다.

```c
backend = group->servers[group->next];
group->next = (group->next + 1) % group->count;   // 라운드 로빈
```

### 4-3. 고르는 규칙들

| 방식 | 동작 | 맞는 경우 |
|---|---|---|
| **라운드 로빈** | 8001 → 8002 → 8001 … | 요청 무게가 비슷할 때 (과제) |
| 가중치 | 큰 서버에 더 많이 | 서버 사양이 다를 때 |
| 최소 연결 | 처리 중인 게 가장 적은 서버로 | 요청 무게가 들쭉날쭉할 때 |
| 해시 | 같은 손님은 같은 서버로 | 서버에 손님별 데이터가 있을 때 |

### 4-4. 이게 L7 로드밸런서다

| | L4 로드밸런서 | L7 로드밸런서 |
|---|---|---|
| 보는 것 | IP, 포트만 | HTTP 내용 (경로, Host 헤더) |
| 서버를 고르는 때 | 연결이 시작될 때 (SYN) | 요청을 다 읽은 뒤 |
| 프록시인가 | 패킷 주소만 바꾸는 방식은 ❌ (연결 하나) | ✅ (연결 둘) |

내 서버는 `/api/`라는 **경로를 보고** 보낼 곳을 정하니까 L7이다. L4로는 경로를 볼 수 없다.

> **L7 로드밸런서 = 로드밸런싱하는 리버스 프록시.** 지금 만드는 게 바로 이것이다.

### 4-5. 주의: "L7 로드밸런싱"이 곧 라우팅은 아니다

**라우팅**과 **로드밸런싱**은 서로 다른 일이다.

- **라우팅** = **어떤 역할**로 보낼지 정한다 (`/api/` → api 그룹)
- **로드밸런싱** = **같은 역할 중 누구**에게 보낼지 정한다 (api 그룹 중 8002)

헷갈리는 이유는 **"L7 로드밸런서"라는 이름** 때문이다. 이름을 뜯어보면 이렇다.

- **로드밸런서**: 원래 생긴 목적. 여러 서버에 나눠 주려고 만들었다.
- **L7**: 볼 수 있는 범위. HTTP 내용(경로, Host 헤더)까지 본다.

HTTP 내용을 볼 수 있게 되니 **라우팅도 덤으로** 할 수 있게 된 것이다. 그래서 L7 로드밸런서 하나가 두 가지 일을 같이 한다. 이름은 로드밸런싱에서 왔지만, 그렇다고 라우팅이 로드밸런싱이 되는 건 아니다. (스마트폰을 "폰"이라고 부르지만 카메라 기능이 전화가 되는 건 아닌 것처럼.)

| | 라우팅 (어떤 역할로?) | 로드밸런싱 (같은 역할 중 누구?) |
|---|---|---|
| L4 로드밸런서 | ❌ (포트 번호로 나누는 정도만) | ✅ |
| L7 로드밸런서 | ✅ HTTP 내용으로 | ✅ |

```
[L7 로드밸런서] 하나가 하는 일
  ① 라우팅       /api/ → api 그룹          ← L7이라서 가능해진 일
  ② 로드밸런싱   api 그룹 중 8002          ← 이름의 원래 목적
```

> 실무나 클라우드 문서에서 "L7 로드밸런싱"을 "경로 기반 라우팅까지 하는 로드밸런싱"이라는 느슨한 뜻으로 쓰기도 해서 더 헷갈린다. 단어가 나오면 **"지금 하는 일이 역할 고르기인가, 같은 역할 중 고르기인가?"**로 구분한다.

## 5. 정리: 이름은 "역할"을 부르는 말이다

**프록시, 로드밸런서는 하는 일의 이름이다.** 그 일을 전용 장비가 하든, 별도 서버가 하든, 웹서버 안의 기능 하나가 하든 이름은 같다. ("서버"도 원래 "요청에 답하는 역할"이고, 그 일을 하는 기계도 서버라고 부르게 된 것이다.)

| | 보낼 곳 1개 | 보낼 곳 여럿 |
|---|---|---|
| 프록시 ❌ | 그냥 웹서버 (1편, 2편의 내 서버) | 패킷 전달형 L4, DNS 라운드 로빈 |
| 프록시 ✅ | 리버스 프록시 (3장) | **L7 로드밸런서 (4장)** |

- **프록시**는 **방식**: 받아 주고 대신 보낸다.
- **로드밸런싱**은 **목적**: 여러 곳에 나눈다.

### 헷갈릴 때 던질 질문 4개

1. **연결이 하나인가, 둘인가?** → 둘이면 프록시
2. **누구 편인가?** → 손님 편이면 포워드, 서버 편이면 리버스
3. **보낼 곳이 여럿인가?** → 여럿이면 로드밸런싱
4. **HTTP 내용을 읽는가?** → 읽으면 L7

### 한 문장으로

> **동적 요청을 처리하기 위해, 리버스 프록시 방식으로 백엔드에 전달하고, 백엔드가 여럿이면 로드밸런싱한다.**

---

## 6. 그래서 내 서버는 뭐라고 불러야 하나

"동적 요청까지 처리하게 된 내 서버 = 리버스 프록시 서버"라고 해도 될까?

### 요청마다 맡는 역할이 다르다

```
                 ┌─ /index.html  → 직접 파일 응답      ← 이 순간엔 "웹서버"
손님 → [내 서버] ─┤
                 └─ /api/users   → 8001/8002로 전달    ← 이 순간엔 "리버스 프록시"
                                   (+ 라우팅, 라운드 로빈 = L7 로드밸런서)
```

내 서버는 정적 요청에는 **여전히 웹서버**로 직접 답하고, `/api` 요청에만 **리버스 프록시**로 움직인다. 서버 전체가 프록시로 바뀐 게 아니라, **역할이 하나 더 생긴 것**이다.

nginx도 똑같다. 정적 파일 이야기를 할 때는 "웹서버", API 서버 앞에 둔 이야기를 할 때는 "리버스 프록시"라고 부른다. 그래서 맥락이 프록시 기능이면 "리버스 프록시 서버"라고 해도 통하지만, 정적 파일도 직접 주니까 **둘 다 말해 주는 게 정확하다.**

### 이름들의 위치 관계

```
내 서버
 ├─ 웹서버 역할           정적 파일 직접 응답
 └─ 리버스 프록시 역할     /api 요청을 백엔드에 대신 전달
     ├─ 라우팅            /api → api 그룹
     └─ 로드밸런싱         api 그룹 중 라운드 로빈
     → 이 둘을 같이 하니까 "L7 로드밸런서"라고도 부를 수 있음
```

**L7 로드밸런서는 서버 전체의 이름이 아니라, 리버스 프록시 역할을 더 자세히 부르는 이름**이다.

### 소개할 때 쓰는 문장

> **정적 파일은 직접 서빙하고, `/api/*` 요청은 백엔드 서버들로 전달하는 리버스 프록시 기능(경로 기반 라우팅 + 라운드 로빈 로드밸런싱)을 갖춘 웹서버.**

## 부록: 헷갈렸던 것들

- **리버스 프록시는 웹서버와 별개로 따로 만드는 서버인가?** 아니다. 역할이라서 웹서버에 기능으로 넣어도 된다. nginx가 바로 웹서버 + 리버스 프록시다. 큰 서비스에서 프록시만 하는 nginx를 따로 띄우는 경우가 많아서 그렇게 보였을 뿐이다. 별개인 건 뒤쪽 **API 서버(백엔드)**다.
- **로드밸런서는 통신 기계인가?** 기계일 수도 있다(옛날 L4 스위치). 하지만 소프트웨어(nginx, HAProxy), 클라우드 서비스(AWS ELB)일 수도 있다. 이름은 "나누는 일"을 가리킨다.
- **프록시는 "가짜"라는 뜻인가?** "대리인"에 가깝다. 누군가를 대신해서 일한다.
- **프록시의 의미는 "손님 요청을 받아 줬다"는 데 있나?** 그렇다. 손님 입장에서 프록시가 연결의 끝이다. 거기에 "대신 보낸다"가 붙어서 서버이자 클라이언트가 된다.
- **L4 로드밸런서도 대리인 아닌가?** 방식에 따라 다르다. 패킷 주소만 바꾸는 방식은 연결이 하나라서 아니고, 연결을 따로 맺는 TCP 프록시 방식(HAProxy `mode tcp`)은 맞다.
- **L7 로드밸런서가 라우팅을 하니까, 로드밸런싱 = 라우팅인가?** 아니다. 라우팅은 어떤 역할로, 로드밸런싱은 같은 역할 중 누구에게. L7 로드밸런서라는 **한 역할이 두 가지 일을 같이 하는 것**이다. 이름에 "로드밸런서"가 붙어서 로드밸런싱이라는 단어가 흐려졌던 것. L4는 로드밸런싱만 한다(4-5).
- **내 서버는 리버스 프록시 서버인가?** 정적 요청에는 웹서버, `/api` 요청에는 리버스 프록시다. 역할이 하나 더 생긴 것이라 "리버스 프록시 기능을 갖춘 웹서버"가 가장 정확하다(6장).
- **로드밸런싱은 파일로 보내는 것도 포함하나?** 아니다. 따로 떠 있는 별개 서버(같은 컴퓨터의 다른 포트도 포함)로 보내는 것이다.
- **정적 파일도 따로 서버를 두면?** 내 서버는 순수한 리버스 프록시가 된다. 역할은 깔끔해지지만 정적 요청이 한 단계 더 돌아간다. nginx는 보통 직접 주고, 큰 서비스는 CDN으로 보낸다.
- **CGI는?** 요청마다 프로그램을 새로 실행하는 옛날 동적 처리 방식. 환경 변수로 요청 정보를 넘기고 stdout으로 응답을 받는다. 프로세스 생성이 비싸서 FastCGI, 리버스 프록시로 넘어왔다.
