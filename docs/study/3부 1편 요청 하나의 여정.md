## 0. 큰 그림: 네 개의 층

> **한 줄 요약**: 같은 높이끼리 대화한다. 프로그램끼리는 HTTP, OS끼리는 TCP/IP, 세로 방향은 소켓 API.

```
[브라우저]        ←──── HTTP 요청/응답 ────→        [웹서버 프로그램]
    │ socket, connect, send, recv                     │ socket, bind, listen, accept, read, write
    │ (소켓 API = 시스템 콜)                            │
[클라이언트 OS]   ←── TCP/IP (handshake, 순서, 재전송) ──→   [서버 OS]
          └──────────── 라우터 · 스위치 (IP · MAC만 봄) ────────────┘
```

- **프로그램끼리**는 HTTP로 대화한다. 브라우저는 `GET /index.html` 같은 텍스트를 보내고, 웹서버는 그걸 읽고 응답을 만든다. 둘 다 TCP가 어떻게 동작하는지 신경 쓰지 않는다.
- **OS끼리**는 TCP/IP로 대화한다. handshake, 시퀀스 번호, ACK, 재전송은 전부 이 층에서 일어나고, 프로그램은 이 과정을 보지 못한다.
- **프로그램과 OS 사이**를 잇는 것이 소켓 API(시스템 콜)다.
- **라우터와 스위치**는 IP 주소와 MAC 주소만 보고 패킷을 옮길 뿐, 연결이 있다는 사실조차 모른다.

웹서버를 만든다는 건 이 그림의 **오른쪽 위 칸**을 만드는 일이다. 나머지는 OS가 해 준다.

## 1. 데이터가 서버에 도착하면: 역캡슐화

> **한 줄 요약**: 받는 쪽은 아래 계층부터 헤더를 한 겹씩 벗기고, 각 헤더에 적힌 값을 보고 다음에 넘길 곳을 고른다.

### 1-1. 가는 도중에 일어나는 일

- **스위치**: 링크 계층(Ethernet) 헤더의 MAC 주소만 보고 프레임을 전달한다.
- **라우터**: 링크 헤더를 떼고 IP 헤더를 확인한다(목적지 IP로 경로 결정, TTL 1 감소, 체크섬 재계산). 그다음 구간에 맞는 **새 링크 헤더**를 붙여 내보낸다.
- 그래서 **MAC 주소는 구간마다 바뀌지만, IP 주소는 처음부터 끝까지 그대로**다(NAT가 끼면 예외).
- TCP 헤더와 HTTP 데이터는 중간 장비가 원칙적으로 건드리지 않는다.

### 1-2. 서버 컴퓨터 안에서 벗겨지는 순서

```
도착한 프레임:  [Ethernet][IP][TCP][   HTTP 데이터   ][FCS]
① NIC·드라이버:            [IP][TCP][   HTTP 데이터   ]
② IP 계층:                     [TCP][   HTTP 데이터   ]
③ TCP 계층:                         [   HTTP 데이터   ]  → 소켓의 수신 버퍼
──────────────────────────── 커널 / 사용자 공간 경계 ────────────────────────────
④ 웹서버:                           read()로 복사해서 HTTP 파싱
```

| 계층 | 확인하는 것 | 다음 행선지를 고르는 단서 |
|---|---|---|
| ① NIC·드라이버 | 목적지 MAC이 내 것인지, FCS로 오류 검사 | **EtherType** (0x0800 = IPv4, 0x86DD = IPv6, 0x0806 = ARP) |
| ② IP | 목적지 IP가 내 것인지, 헤더 체크섬, 조각 재조립, 방화벽 | **Protocol** (6 = TCP, 17 = UDP) |
| ③ TCP | IP·포트 네 값으로 **어느 연결인지** 찾기, 순서 정렬, 중복 제거, ACK 전송 | 그 연결의 **수신 버퍼** |
| ④ 웹서버 | `read()`로 바이트를 가져와 HTTP 해석 | `\r\n\r\n`, `Content-Length` |

**① NIC와 드라이버**
NIC가 전기·광 신호를 비트로 바꿔 프레임을 만들고, 목적지 MAC이 자기 주소(또는 브로드캐스트)가 아니면 버린다. 통과한 프레임은 DMA로 메모리에 바로 복사되고, 인터럽트로 CPU에 도착을 알린다. 드라이버가 Ethernet 헤더를 떼고 EtherType을 보고 IP 계층에 넘긴다.

**② IP 계층**
목적지 IP가 내 주소인지 확인하고, 조각나서 왔으면 다시 합친다. 방화벽(리눅스라면 netfilter/iptables)도 주로 여기서 검사한다. IP 헤더를 떼고 Protocol 필드를 보고 TCP로 넘긴다.

**③ TCP 계층**
가장 많은 일을 하는 곳이다.
- (출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) 네 값으로 커널의 해시 테이블에서 **이 세그먼트가 속한 연결(소켓)**을 찾는다.
- 시퀀스 번호로 순서를 맞추고, 중복을 버리고, ACK를 보낸다.
- TCP 헤더를 뗀 순수한 HTTP 바이트를 그 소켓의 **수신 버퍼**에 넣는다.

**④ 웹서버 프로그램**
①~③은 전부 커널 안에서 일어난다. 프로그램은 `read()`를 호출해서 수신 버퍼의 바이트를 자기 메모리로 복사해 갈 뿐이다.

### 1-3. 역다중화

EtherType → Protocol → 포트(네 값). 각 헤더에는 "다음에 이 데이터를 누구에게 줄지"가 적혀 있다. 이렇게 갈래를 나눠 넘기는 것을 **역다중화(demultiplexing)**라고 하고, 덕분에 한 컴퓨터에서 여러 프로토콜과 여러 프로그램이 동시에 통신할 수 있다.

## 2. 연결과 소켓

> **한 줄 요약**: 연결은 물리적인 선이 아니라 양쪽 OS가 커널 안에 기억하는 상태(구조체)이고, 소켓은 그 실체와 그걸 가리키는 번호(fd)를 함께 부르는 말이다.

### 2-1. 연결이란

연결은 두 컴퓨터 사이에 전용 통로가 생기는 게 아니다. 패킷은 연결 전이든 후든 똑같이 라우터를 하나씩 거쳐 각자 길을 찾아가고, 라우터들은 연결의 존재를 모른다.

TCP에서 연결이란 **양쪽 OS가 "우리 지금 대화 중"이라는 상태를 각자 기억하기로 합의한 것**이다. 이 상태는 커널 메모리 안의 구조체에 담긴다.

```c
struct tcp_connection {        // 이해를 위한 단순화 (실제 리눅스에서는 tcp_sock)
    // 누구와의 연결인가
    uint32_t local_ip,  remote_ip;
    uint16_t local_port, remote_port;

    // 지금 어떤 상태인가
    int state;                 // SYN_SENT, ESTABLISHED, FIN_WAIT ...

    // 순서 관리
    uint32_t send_next;        // 다음에 보낼 시퀀스 번호
    uint32_t recv_next;        // 다음에 받기를 기대하는 번호
    uint32_t peer_window;      // 상대 수신 버퍼에 남은 공간

    // 데이터
    buffer   send_buf;         // 송신 버퍼
    buffer   recv_buf;         // 수신 버퍼
};
```

### 2-2. 3-way handshake = 이 상태를 합의하는 과정

```
클라이언트 OS                                   서버 OS
     │ ── SYN (내 번호는 1000부터) ──────────────→ │
     │ ←── SYN+ACK (1000 잘 받음, 내 번호는 5000부터) │
     │ ── ACK (5000 잘 받음) ────────────────────→ │
   ESTABLISHED                                ESTABLISHED
```

세 번이 끝나면 양쪽 커널에 구조체가 완성되고, 이 상태를 "연결됐다(ESTABLISHED)"고 부른다.

- **handshake는 OS끼리 한다.** 프로그램은 이 과정에 끼지 않는다.
- **하지만 시작하라고 시키는 건 프로그램이다.** 서버 프로그램이 `listen()`으로 미리 받을 준비를 하고, 클라이언트 프로그램이 `connect()`를 호출해야 handshake가 시작된다.
- UDP는 이런 합의 없이 바로 보낸다. 순서 보장도 재전송도 없다.

### 2-3. 소켓 = 커널의 실체 + 프로그램의 번호

"소켓"이라는 단어는 두 가지를 섞어서 부른다.

| | 무엇인가 | 비유 |
|---|---|---|
| **커널 쪽 소켓** | 커널 메모리 안의 구조체. 연결 정보, 상태, 송신·수신 버퍼, 대기열이 실제로 있는 곳 | 은행 안의 **계좌** |
| **프로그램 쪽 소켓** | 그 구조체를 가리키는 **파일 디스크립터(fd) 번호** (3, 4, 5…) | 손에 쥔 **계좌번호** |

프로그램은 커널 메모리를 직접 만질 수 없다. 그래서 번호를 들고 시스템 콜을 부르면, OS가 안에서 처리하고 결과만 돌려준다.

```
프로그램:  5 (파일 디스크립터)
            ↓
커널:     파일 객체 → socket 구조체 → sock 구조체 (TCP라면 tcp_sock)
                                       └ 연결 정보, 상태, 송신·수신 버퍼
```

`read(5, buf, 4096)`은 "5번이 가리키는 소켓의 수신 버퍼에서 4096바이트까지 꺼내 달라"는 요청이다.

> 리눅스에서는 열린 파일도 소켓도 똑같이 번호로 다루고, 똑같이 `read()`, `write()`, `close()`를 쓴다.
> "소켓"이라는 이름은 벽의 콘센트에서 왔다. 통신의 한쪽 끝(endpoint)에 플러그를 꽂는 구멍이라는 뜻이다.

### 2-4. 대기용 소켓과 연결용 소켓

웹서버에는 소켓이 두 종류 있다.

- **대기용 소켓(listening socket)**: `listen()`을 한 소켓. "80번 포트로 오는 연결은 나한테 줘"라는 **접수 창구**다. 데이터는 주고받지 않고, 연결을 담는 대기열만 가진다. 서버에 하나.
- **연결용 소켓(connected socket)**: handshake가 끝난 연결 하나하나에 대응하는 소켓. 송신·수신 버퍼를 가지고 실제 데이터를 주고받는다. 클라이언트가 100명이면 100개.

식당으로 비유하면 대기용 소켓은 입구의 안내 데스크, 연결용 소켓은 손님마다 배정되는 테이블이다.

### 2-5. 소켓이 생기는 순서

**클라이언트**: 실체와 번호를 먼저 받고, 그다음에 연결한다.

```c
int fd = socket(...);          // 커널에 빈 소켓이 생기고 번호 4를 받음
connect(fd, 서버IP, 80);        // 남는 포트(예: 52341)를 골라 handshake 시작
                               // handshake가 끝나면 connect()가 돌아옴
```

**서버**: 실체가 먼저 생기고, 번호는 나중에 붙는다.

```c
int lfd = socket(...);         // 대기용 소켓, 번호 3
bind(lfd, 80번 포트);
listen(lfd, backlog);          // 대기열 준비

int cfd = accept(lfd, ...);    // 완성된 연결을 하나 꺼내서 번호 5를 붙여 줌
```

서버 쪽 연결 하나는 이런 단계를 거친다.

| 단계 | 커널 안의 모습 | 번호 |
|---|---|---|
| SYN 도착 | SYN 대기열에 **가벼운 메모**(`request_sock`). 아직 소켓이 아니고 버퍼도 없음 | 없음 |
| 마지막 ACK 도착 | **완전한 소켓**(`tcp_sock`)이 만들어지고 버퍼가 붙어 accept 대기열로 | 없음 |
| `accept()` 호출 | 대기열에서 빠져나옴 | **5번이 붙음** |

> SYN 단계를 가볍게 만드는 이유: SYN만 대량으로 보내는 공격(SYN flood)에도 메모리를 덜 쓰기 위해서다.

## 3. 버퍼와 대기열

> **한 줄 요약**: 대기열은 **연결**을 담고, 버퍼는 **데이터**를 담는다. `read()`와 `write()`는 내 메모리와 커널 버퍼 사이의 복사다.

### 3-1. 대기열: 대기용 소켓에 있음

리눅스는 대기용 소켓에 줄을 두 개 둔다.

1. **SYN 대기열**: SYN을 받고 SYN+ACK를 보냈지만 마지막 ACK를 아직 못 받은, 반쯤 열린 연결
2. **accept 대기열**: handshake가 끝나서 `accept()`로 꺼내 가기만 하면 되는 연결

- 연결은 1에서 2로 넘어가고, 프로그램은 2에서만 꺼내 간다.
- `listen(fd, 128)`의 128이 accept 대기열 길이(backlog)다. 실제 길이는 OS 설정 `net.core.somaxconn`과 비교해 작은 쪽이 된다.
- accept 대기열이 가득 차면 리눅스는 새 연결을 기본적으로 **조용히 무시**한다. 클라이언트는 1초, 2초, 4초… 간격으로 SYN을 다시 보내므로, 사용자에게는 "접속이 느려진다"로 보인다.
- 요즘 리눅스는 SYN 쿠키가 기본으로 켜져 있어서 SYN 대기열이 차도 handshake를 계속 받아 준다. 그래서 실제 병목은 주로 accept 대기열이다.

### 3-2. 버퍼: 연결용 소켓마다 있음

연결 하나마다 **양쪽 OS가 각각** 송신 버퍼와 수신 버퍼를 하나씩 가진다. 연결 하나에 버퍼가 총 네 개다.

- **송신 버퍼**: `send()`/`write()`를 호출하면 데이터는 송신 버퍼로 복사되고 함수는 바로 돌아온다. OS가 적당히 잘라 보낸다. **상대의 ACK가 올 때까지 지우지 않는다.** 중간에 사라지면 여기서 꺼내 다시 보내야 하니까.
- **수신 버퍼**: 도착한 데이터를 프로그램이 `read()`로 가져갈 때까지 보관한다. 순서가 뒤바뀌어 도착한 세그먼트를 제자리에 맞추는 것도 여기서 한다.

### 3-3. 흐름 제어

수신 측 OS는 ACK를 보낼 때마다 "내 수신 버퍼에 지금 이만큼 남았다"는 값(**윈도우 크기**)을 함께 보낸다.

```
웹서버가 read()를 안 함 → 수신 버퍼가 참 → 윈도우 = 0
→ 보내는 쪽 OS가 전송을 멈춤 → 보내는 쪽 송신 버퍼가 참
→ 보내는 쪽 프로그램의 send()가 멈춰서 기다림
```

빠른 송신자가 느린 수신자를 압도하지 못하게 막는 장치다.

### 3-4. read()는 무엇을 하나

```c
char buf[4096];                 // 웹서버가 직접 마련한 메모리
int n = read(sock, buf, 4096);  // 커널 수신 버퍼 → buf로 최대 4096바이트 복사
```

버퍼가 두 개 등장한다. 커널 안의 **수신 버퍼**와 프로그램의 **`buf`**. `read()`는 앞에서 뒤로 옮기고, 옮긴 만큼 수신 버퍼가 비워진다. 그 빈자리는 다음 ACK의 윈도우로 상대에게 알려진다.

`read()`의 세 가지 동작은 꼭 기억해 두자.

| 상황 | 결과 |
|---|---|
| 수신 버퍼가 **비어 있음** | 데이터가 올 때까지 **스레드가 잠든다**(블로킹). 논블로킹 소켓이면 바로 `EAGAIN` |
| 데이터가 **요청한 것보다 적게** 있음 | 있는 만큼만 돌려준다. 4096을 달라고 해도 300일 수 있음 |
| 상대가 연결을 **닫음** (FIN) | **0**을 돌려준다 |

> 첫 번째 줄, "수신 버퍼가 비어 있으면 스레드가 잠든다"가 [2편](./02-동시성.md)의 출발점이다.

`write()`는 반대로 내 메모리에서 **송신 버퍼**로 복사한다. 결국 소켓 API는 "내 메모리와 커널 버퍼 사이에서 데이터를 옮겨 달라"는 요청이다.

## 4. 요청 경계 나누기

> **한 줄 요약**: TCP는 순서를 보장하고, 경계는 HTTP와 웹서버가 나눈다.

### 4-1. 섞이지 않는 이유

**다른 연결끼리**: 연결마다 소켓과 수신 버퍼가 따로 있고, 커널이 IP·포트 네 값으로 찾아서 넣어 주므로 절대 섞이지 않는다.

**같은 연결 안에서**: HTTP/1.1 keep-alive에서는 한 연결로 요청을 여러 번 보낼 수 있다. 그래도 섞이지 않는다.

1. **보내는 쪽이 순서대로 넣는다.** 요청 1을 보내고 요청 2를 보내면 송신 버퍼에 `[요청1][요청2]` 순서로 쌓이고, 시퀀스 번호도 그 순서로 매겨진다. 요청 1의 마지막 바이트가 1000번이면, 요청 2의 첫 바이트는 무조건 1001번 이후다.
2. **받는 쪽은 빈틈없이 이어진 부분만 `read()`에 내준다.** 패킷이 뒤바뀌어 요청 2의 조각이 먼저 와도, OS는 빈틈이 메워질 때까지 따로 보관만 한다.

```
도착 순서 (네트워크에서 뒤바뀜):  [요청1 ①][요청1 ②][요청2 ①][요청1 ③]
                                             └ 보관만 함
read()가 보는 순서:               [요청1 ①][요청1 ②][요청1 ③][요청2 ①]...
```

> 중요한 점: **OS는 "요청"이라는 단위를 모른다.** 바이트를 시퀀스 번호 순서대로 넣는다는 규칙 하나만 지킨다.
> 그 결과로 요청들이 보낸 순서대로 줄지어 쌓일 뿐이다.
> "아직 덜 왔는데 `read()`할 수 있다"는 건 **뒷부분이 아직 안 왔다**는 뜻이지, 중간이 비어 있다는 뜻이 아니다.

### 4-2. 그런데 경계는 표시되지 않는다

수신 버퍼에는 바이트가 줄줄이 이어져 있을 뿐이다.

```
GET /a HTTP/1.1\r\nHost: x\r\n\r\nGET /b HTTP/1.1\r\nHost: x\r\n\r\n
└──────────── 요청 1 ────────────┘└──────────── 요청 2 ────────────┘
```

그래서 `read()` 한 번에 이런 일이 생긴다.

- 요청 1의 앞부분만 읽힘 → 나머지가 올 때까지 더 읽어야 함
- 요청 1 전체와 요청 2의 앞부분이 함께 읽힘 → 요청 2의 앞부분을 버리면 안 됨

**"`read()` 한 번 = 요청 하나"라고 가정하면 안 된다.**

### 4-3. 자르는 방법

HTTP가 규칙을 정해 두었다. 헤더는 빈 줄(`\r\n\r\n`)로 끝나고, 본문이 있으면 `Content-Length`에 적힌 바이트 수만큼 이어진다.

웹서버는 읽은 걸 자기 버퍼에 **이어 붙이고**, 완성된 요청만 잘라 내고, **남은 바이트는 다음 요청의 시작으로 보관**한다.

```python
pending = b""                          # 웹서버가 직접 관리하는 누적 버퍼

while True:
    data = sock.recv(4096)             # 커널 수신 버퍼에서 가져오기
    if not data:                       # 0바이트 = 상대가 연결을 닫음
        break
    pending += data                    # 이어 붙이기

    while True:                        # 완성된 요청이 있으면 전부 처리
        end = pending.find(b"\r\n\r\n")
        if end == -1:
            break                      # 헤더가 아직 덜 옴 → 더 읽으러 감
        head = pending[:end]
        body_len = content_length(head)        # Content-Length (없으면 0)
        total = end + 4 + body_len
        if len(pending) < total:
            break                      # 본문이 아직 덜 옴 → 더 읽으러 감
        request = pending[:total]      # 요청 하나 완성
        pending = pending[total:]      # 남은 건 다음 요청의 앞부분이니 보관
        handle(request)
```

### 4-4. 참고: HTTP 버전별 차이

- **HTTP/1.1**: 브라우저는 보통 요청 하나를 보내고 응답을 받은 뒤 다음 요청을 보낸다. 동시에 여러 개를 받으려고 서버 하나에 연결을 여러 개(보통 6개 정도) 연다.
- **HTTP/2**: 한 연결 안에서 여러 요청과 응답을 잘게 쪼개 섞어 보낸다. 대신 조각마다 스트림 ID가 붙어 있어서 받는 쪽이 번호별로 다시 조립한다.

## 5. 연결은 언제 끊기나

> **한 줄 요약**: 보통은 유휴 시간이 지나면 끊긴다. 언제 끊을지는 서버가 정한다.

### 5-1. 끊기는 경우

1. **쉬는 시간이 길어서 (가장 흔함)**: 서버가 정한 유휴 시간 동안 다음 요청이 없으면 닫는다(nginx 기본 75초, Apache 기본 5초). 브라우저나 앱도 자기 기준으로 오래 안 쓴 연결을 닫는다.
2. **`Connection: close`**: 요청이나 응답 헤더에 이게 있으면 그 응답을 끝으로 닫는다. HTTP/1.0은 이게 기본 동작이었다.
3. **요청 횟수 제한**: 연결 하나당 최대 요청 수를 정해 두기도 한다(nginx 기본 1000).
4. **그 밖의 사정**: 탭을 닫거나 앱이 백그라운드로 감, 와이파이↔LTE 전환, 잘못된 요청, 서버 재시작, 공유기·방화벽이 오래 조용한 연결을 정리.

> "페이지를 다 받으면 끊기는 것 같다"는 느낌은, 페이지 로딩이 끝난 뒤 조용해지고 유휴 시간이 지나 끊기기 때문이다. 실제 이유는 1번이다.

### 5-2. 닫는 과정

한쪽 프로그램이 `close()`를 호출하면 OS끼리 FIN과 ACK를 주고받으며 소켓과 버퍼를 해제하고, 번호도 반납된다. 대기용 소켓은 그대로 남아서 다음 연결을 받는다.

### 5-3. 서버 코드에서 끊김을 알아채는 방법

| 상황 | 서버에서 보이는 것 |
|---|---|
| 상대가 정상적으로 닫음 (FIN) | `read()`가 **0** |
| 상대가 갑자기 끊음 (RST) | `read()`가 -1, `errno == ECONNRESET` |
| 이미 닫힌 연결에 `write()` | -1, `errno == EPIPE` + **`SIGPIPE` 신호** |

리눅스에서는 이미 닫힌 소켓에 쓰면 기본적으로 **프로세스 전체가 종료된다.** 손님 한 명이 응답 도중 탭을 닫았다고 서버가 통째로 죽는 것이다. 서버 시작 부분에 반드시 넣자.

```c
signal(SIGPIPE, SIG_IGN);   // 닫힌 소켓에 써도 죽지 않고 EPIPE 에러만 받기
```

## 6. 전체 흐름 한눈에

```
[1] 서버 준비
    웹서버: socket() → bind(80) → listen()
    서버 OS: 대기용 소켓 3번 + SYN 대기열 + accept 대기열

[2] 연결 요청
    브라우저: socket() → 4번 받음 → connect(4, 서버IP, 80)
    클라이언트 OS: 남는 포트 52341 선택, SYN 전송

[3] handshake (OS끼리)
    SYN → SYN+ACK → ACK
    서버 OS: SYN 대기열의 메모 → 완전한 소켓 + 버퍼 → accept 대기열
    클라이언트 OS: ESTABLISHED, connect() 반환

[4] 연결 꺼내기
    웹서버: accept(3) → 5번 받음 (대기용 소켓 3번은 그대로)

[5] 요청 전송 (캡슐화)
    브라우저: send(4) → 클라이언트 송신 버퍼
    클라이언트 OS: TCP → IP → Ethernet 헤더 붙여 전송 (ACK 올 때까지 보관)

[6] 요청 수신 (역캡슐화)
    서버 OS: NIC → IP → TCP → 소켓 5의 수신 버퍼, ACK(+윈도우) 전송

[7] 읽고 처리
    웹서버: read(5) → 내 메모리로 복사 → 경계 찾아 자르기 → HTTP 처리

[8] 응답 (같은 길을 거꾸로)
    웹서버: write(5) → 서버 송신 버퍼 → ... → 클라이언트 수신 버퍼 → 브라우저 recv()

    ※ keep-alive면 [6]~[8]이 같은 연결에서 반복된다.
      다음 요청을 기다리는 동안 웹서버는 read(5)에서 잠들어 있다.

[9] 종료
    close() → FIN/ACK 교환 → 소켓과 버퍼 해제, 상대의 read()는 0
```

**꼭 기억할 네 가지**

1. **연결은 선이 아니라 커널 안의 소켓(구조체)이다.**
2. **대기열은 연결을, 버퍼는 데이터를 담는다.**
3. **소켓 = 커널의 실체 + 프로그램의 번호.** 프로그램은 번호로 시스템 콜을 부르고, read/write는 내 메모리와 커널 버퍼 사이의 복사다.
4. **순서는 TCP, 경계는 HTTP.**

## 7. 헷갈렸던 것들 Q&A

**Q. 역캡슐화 ①~③은 OS가 해 주는 일인가?**
A. 그렇다. NIC·IP·TCP 처리는 전부 커널 안에서 일어나고, 웹서버 프로그램은 `read()`로 결과(HTTP 바이트)만 받는다.

**Q. 연결이 이루어진다는 게 정확히 뭔가?**
A. 양쪽 OS가 커널 메모리에 연결 정보(IP·포트 네 값, 시퀀스 번호, 상태, 버퍼)를 담은 구조체를 만들어 기억하는 것이다. 물리적인 통로가 생기는 게 아니다.

**Q. OS에서 말하는 소켓과 프로그램에서 말하는 소켓은 다른 건가?**
A. 같은 대상을 다른 쪽에서 본 것이다. 커널 쪽은 실체(구조체), 프로그램 쪽은 그걸 가리키는 번호(fd)다. 사람들은 둘 다 "소켓"이라고 부른다. "소켓에 데이터가 쌓인다"는 커널 쪽 이야기고, "`accept()`로 소켓을 받는다"는 번호를 받는다는 이야기다.

**Q. "연결 구조체"와 "소켓"은 다른 건가?**
A. 같은 것이다. 연결용 소켓의 커널 쪽 실체가 연결 구조체다. 단, SYN 대기열의 `request_sock`은 아직 소켓이 아닌 메모이고, accept 대기열의 구조체는 완전한 소켓이지만 아직 번호가 없는 상태다.

**Q. 버퍼는 클라이언트 OS와 서버 OS 모두 연결마다 가지고 있나?**
A. 그렇다. 연결 하나에 양쪽이 송신·수신 버퍼를 하나씩, 총 네 개다.

**Q. 대기열과 버퍼는 뭐가 다른가?**
A. 대기열은 대기용 소켓에 붙어 있고 **연결**을 담는다. 버퍼는 연결용 소켓마다 붙어 있고 **데이터(바이트)**를 담는다.

**Q. 웹서버가 `read()`로 접근하는 건 서버 OS의 수신 버퍼인가?**
A. 그렇다. 정확히는 커널 수신 버퍼의 내용을 프로그램 메모리로 **복사**해 오는 것이다. 프로그램이 커널 버퍼를 직접 들여다보지는 않는다.

**Q. 한 연결의 수신 버퍼에 요청이 여러 개 쌓이면 뒤죽박죽 섞이지 않나?**
A. 섞이지 않는다. 보내는 쪽이 순서대로 번호를 매기고, 받는 쪽은 번호 순서대로 빈틈없이 이어진 부분만 `read()`에 내준다. 단, 경계는 표시되지 않으므로 웹서버가 HTTP 규칙으로 잘라야 한다.

**Q. 요청 1이 덜 온 상태에서 요청 2의 조각이 수신 버퍼 중간에 끼어들 수 있나?**
A. 없다. 요청 2의 바이트는 시퀀스 번호가 전부 요청 1보다 뒤이므로, 요청 1의 마지막 바이트가 들어가기 전에는 `read()`로 보이지 않는다. OS가 "요청이 완성됐는지"를 판단하는 게 아니라, 번호 순서만 지키다 보니 결과적으로 그렇게 된다.

**Q. keep-alive면 handshake를 한 번만 하나?**
A. 그렇다. handshake를 한 번 하고 그 연결로 요청을 여러 번 주고받는다. 응답 후에도 연결을 잠시 열어 두었다가 유휴 시간이 지나면 닫는다.
