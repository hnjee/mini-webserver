# 2부 2편: HTTP는 무엇을 약속했나 - "안녕하세요"가 담기는 쪽지

Nov 20, 2026 · @현지

## 들어가며

전체적인 짐의 구조에서 보면 HTTP는 맨 안쪽 칸이다.

```
[   이더넷 칸  |  IP 칸 |  TCP 칸 | HTTP 쪽지 ]
  바로 다음 기기   컴퓨터   프로그램   무슨 말을 할지
```

앞의 세 칸이 "어디로 가지?"에 답한다면, HTTP는 도착한 뒤 "뭘 하지?"에 답한다.

**HTTP는 배달에 전혀 관심이 없다.** 배달은 앞의 칸들이 다 해 준다. HTTP는 오직 "무슨 말을, 어떤 모양으로 할지"만 정한다. 이번 편에서는 2부 1편에서 본 짐의 맨 안쪽, **"안녕하세요"가 실제로 담기는 HTTP 쪽지**를 열어 본다.

## 1. HTTP는 무엇을 약속했나

한 줄로 말하면, **클라이언트와 서버가 주고받는 쪽지에 무엇을, 어떤 양식으로 쓸지**를 약속했다.

대화 방식도 정해져 있다. **클라이언트가 먼저 요청하고, 서버가 응답한다.** 한 번 묻고 한 번 답하는 구조라서 HTTP 쪽지는 요청과 응답, 두 종류뿐이다.

그리고 **요청끼리는 서로 독립이다.** 서버는 기본적으로 이전 요청을 기억하지 않는다. 이를 무상태(stateless)라고 하며, HTTP 표준 문서에도 무상태 프로토콜이라고 적혀 있다. 전화 통화는 한번 연결되면 "아까 말한 그거"가 통하지만, HTTP는 돛단배에 쪽지를 띄우듯 매번 새 쪽지를 보낸다.

이 대화 방식에는 **아래의 TCP 연결을 어떻게 쓸지**도 들어 있다. 응답마다 연결을 닫을지(HTTP/1.0), 열어 두고 여러 요청을 이어 보낼지(HTTP/1.1), 연결 하나에 여러 쪽지를 동시에 보낼지(HTTP/2)를 HTTP가 정한다. HTTP는 쪽지 양식과 함께, 그 쪽지를 TCP라는 통로로 어떻게 주고받을지도 약속하는 셈이다. (2부 1편 5번 "위층은 아래층을 통로로 쓴다")

## 2. "안녕하세요"만 보내면 안 되는 이유

HTTP 쪽지에 딱 "안녕하세요"만 적어서 보내고 이 쪽지가 서버에 도착했다고 하자. 서버는 이런 질문들에 막힌다.

| 서버의 질문 | 답해주는 곳 |
| --- | --- |
| 이걸로 뭘 하라는 거지? (보관? 검색? 삭제?) | 시작줄의 메서드 (`POST`) |
| 무엇에 대해서지? (채팅? 프로필? 몇 번 대화방?) | 시작줄의 경로 (`/chat`) |
| 어느 사이트에 온 거지? (서버 한 대가 여러 사이트를 맡기도 한다) | `Host` 헤더 |
| 이걸 어떻게 읽지? (글자? JSON? 사진?) | `Content-Type` 헤더 |
| 어디까지가 메시지지? | `Content-Length` 헤더 |
| 누가 보낸 거지? | 로그인 정보 헤더 (`Cookie` 등) |

"안녕하세요"는 **내용**일 뿐이고, 나머지는 서버가 그 내용을 **무엇을, 어디에, 누구를 위해, 어떻게** 처리할지 알려주는 설명서다. 택배 상자 위에 "선물이에요, 거실에 놔주세요, 깨지기 쉬움, 보낸 사람 현지"라고 붙이는 메모와 같다.

이것은 2부 1편의 원리와 같다. 0과 1만 오면 읽을 수 없듯, 내용만 오면 처리할 수 없다. 그래서 약속이 필요하다.&#32;

### 그래서 매번 다 담는다

HTTP는 무상태라서 이 정보들은 한 번 보내고 끝이 아니다. 받는 쪽이 앞 쪽지를 기억 못 하니, 쪽지마다 "저 현지예요, 3번 대화방이에요, 이거 보내요"를 다시 적는다.

- **로그인 정보(쿠키, 토큰)를 매번 보낸다.** 서버가 "아까 로그인한 사람"을 기억하지 못하기 때문이다.
- **보통 채팅 서비스는 대화방 번호를 매번 함께 보낸다.** 그래야 서버가 이 메시지를 어느 대화에 붙일지 안다.

## 3. 요청 쪽지 양식

"안녕하세요"를 보낼 때 브라우저가 쓰는 요청 쪽지를 단순하게 그리면 이렇다. (실제 클로드가 쓰는 주소나 칸 이름과는 다른 설명용 예시다.)&#32;

2부 1편에서 아래 칸들은 "몇 번째 자리부터 몇 자리"로 자른다고 했다. HTTP는 조금 다르다. **글자로 쓰고, 줄바꿈과 콜론(:)과 빈 줄로 칸을 나눈다.** 첫 줄까지가 시작줄, 빈 줄까지가 헤더, 그 뒤가 본문이다. 그래서 사람이 읽어도 바로 이해된다. 최신 버전인 HTTP/2와 HTTP/3은 속도를 위해 0과 1의 이진 양식을 쓰지만, 담는 내용과 뜻은 같다.

```
POST /chat HTTP/1.1                ← 시작줄
Host: claude.ai                    ← 헤더
Content-Type: application/json
Content-Length: 30
                                   ← 빈 줄
{"message": "안녕하세요"}           ← 본문
```

| 부분 | 적는 것 | 예시에서는 |
| --- | --- | --- |
| 시작줄 | 무엇을 할지 + 무엇에 대해 + HTTP 버전 | /chat에 데이터를 보낼게요(POST), HTTP/1.1 |
| 헤더 | 내용을 해석하고 처리하는 데 필요한 부가 정보, `이름: 값` | 어느 사이트, 본문 형식, 본문 길이 |
| 빈 줄 | "헤더 끝, 이제 본문" 표시 |  |
| 본문 | 실제로 전하려는 내용 | "안녕하세요" |

시작줄의 경로(`/chat`)는 요청이 출발한 곳이 아니라 **요청의 대상**이다. 그래서 "어디에서"가 아니라 "무엇에 대해"라고 읽는다.

## 4. 응답 쪽지 양식

서버의 답장도 거의 같은 모양이다. 다른 점은 첫 줄뿐이다.

```
HTTP/1.1 200 OK                    ← 상태줄
Content-Type: application/json     ← 헤더
Content-Length: 52
                                   ← 빈 줄
{"reply": "안녕하세요, 현지님!"}    ← 본문
```

**상태줄**은 "요청이 어떻게 됐는지"를 숫자(상태 코드)로 알려준다. 앞자리만 봐도 대충 알 수 있다.

| 앞자리 | 뜻 | 자주 보는 코드 |
| --- | --- | --- |
| 2xx | 성공 | 200 성공 |
| 4xx | 요청한 쪽 문제 | 401·403 권한 없음, 404 그런 것 없음 |
| 5xx | 서버 쪽 문제 | 500 서버 오류 |

## 5. 메서드: 경로는 대상, 메서드는 행동

`/chat`에서 무엇을 할지 서버가 이미 알 텐데 왜 `POST`를 따로 보낼까? **같은 대상에도 할 수 있는 일이 여러 개**이기 때문이다. (설명용 예시)

| 요청 | 뜻 |
| --- | --- |
| `GET /chat/3` | 3번 대화 내용을 가져와 주세요 |
| `POST /chat/3` | 3번 대화에 새 메시지를 받아 주세요 |
| `DELETE /chat/3` | 3번 대화를 지워 주세요 |

문장으로 치면 **경로는 명사, 메서드는 동사**다. 자주 쓰는 메서드는 `GET`(가져오기), `POST`(보내기), `PUT`·`PATCH`(바꾸기), `DELETE`(지우기)다.

### 중간 장비도 메서드를 본다

메서드에는 HTTP가 약속해 둔 성격이 있어서, 서버뿐 아니라 브라우저와 중간 장비도 이걸 보고 행동을 정한다.

- **GET은 보기만 하는 요청**이다. 서버의 내용을 바꾸지 않으므로, 브라우저는 결과를 저장해 두었다 다시 쓰거나(캐시) 실패하면 다시 보낸다.
- **POST는 무언가를 바꾸는 요청**이다. 두 번 보내면 메시지가 두 번 올라가거나 결제가 두 번 될 수 있다.

새로고침을 눌렀을 때 뜨는 **"양식을 다시 제출하시겠습니까?"** 경고창이 바로 이것이다. 브라우저가 방금 요청이 POST였다는 걸 보고, 다시 보내도 되는지 묻는 것이다.

## 6. 본문: 형식은 Content-Type, 키 이름은 서비스의 약속

본문을 키:값으로 쓰라는 것은 HTTP의 약속이 아니다. HTTP는 본문에 대해 딱 하나만 약속한다. **"본문이 어떤 형식인지는 `Content-Type` 헤더에 적어라."**

| Content-Type | 본문 |
| --- | --- |
| `text/plain` | 그냥 글자. `안녕하세요`만 적어도 된다 |
| `application/json` | 키:값 형식 |
| `text/html` | 웹페이지 |
| `image/png` | 사진 파일의 0과 1 그대로 |

채팅 같은 서비스가 키:값(JSON)을 많이 쓰는 이유는 보낼 정보가 **여러 개**이기 때문이다. 메시지만이 아니라 어느 대화방인지도 함께 간다. 어느 게 무엇인지 구분하려면 이름표(키)가 필요하다. 0과 1에 칸을 나누던 것과 같은 원리다.

```json
{
  "conversation_id": 3,
  "message": "안녕하세요"
}
```

이 키 이름들은 HTTP도 국제 표준도 아니고, **그 서비스가 직접 정한 약속**이다. 이런 약속을 적어 둔 문서를 **API 명세**라고 한다. 약속은 층층이 있는 셈이다.

| 약속 | 정하는 곳 | 정하는 것 |
| --- | --- | --- |
| 이더넷, IP, TCP | 국제 표준 | 배달 |
| HTTP | 국제 표준 | 쪽지 양식 |
| 본문의 키 이름 | 각 서비스 (API 명세) | 내용의 구성 |

## 7. HTTPS

**HTTPS**는 HTTP 쪽지를 암호화해서 보내는 것이다. 쪽지 양식은 그대로인데 봉투를 잠가서, 중간의 라우터들은 내용을 읽지 못한다. 1부 2편의 443번 포트가 HTTPS였다. "안녕하세요"도 이렇게 잠긴 채로 간다.

## 8. 덧붙임: 이 약속 위의 설계, REST

지금까지가 HTTP의 약속이었다. REST는 HTTP의 약속이 아니라, **그 약속을 잘 활용해 서비스를 설계하는 방식**이다. 2000년 로이 필딩이 박사 논문에서 정리했고, 그는 HTTP/1.1 표준을 만든 저자 중 한 명이기도 하다.

### 원칙 1: 자원은 경로로, 행동은 메서드로

`get_chat`, `write_chat`처럼 행동을 이름에 넣는 대신, 경로에는 자원(`/chats/3`)을 쓰고 행동은 HTTP가 이미 약속해 둔 메서드로 표현한다. 그러면 서버뿐 아니라 브라우저와 중간 장비까지 요청의 뜻을 알아듣는다. 반대로 `POST /sendMessage`처럼 행동을 이름에 넣는 방식은 RPC 방식이라고 부르며, 둘 다 실제로 쓰인다.

### 원칙 2: 서비스도 무상태로

HTTP 쪽지가 무상태라고 해서 그 위의 서비스까지 무상태인 것은 아니다. 로그인하면 서버 A가 자기 메모리에 "이 쿠키 = 현지, 지금 3번 대화방"이라고 기억해 두는 설계도 가능하다. 그러면 다음 요청이 서버 B로 가면 B는 그 기억이 없어서, 로드밸런서는 요청을 계속 서버 A로만 보내야 한다. 서버 A가 꺼지면 상태도 같이 사라진다.

REST는 이렇게 하지 말자고 한다. **서버가 대화 상태를 기억하는 데 기대지 말고, 요청마다 처리에 필요한 맥락을 다 담아라.** 그러면 1부 6편의 로드밸런서가 가장 한가한 서버로 그냥 보내도 되고, 서버를 몇 대든 늘리기 쉽다.

| 구분 | 무상태의 뜻 |
| --- | --- |
| HTTP | 쪽지 약속 자체가 요청끼리 연결하지 않는다 (프로토콜의 특징) |
| REST | 서비스도 서버의 기억에 기대지 않게 만든다 (설계 원칙) |

## 마치며

- HTTP는 배달이 아니라 **쪽지에 무엇을, 어떤 양식으로 쓸지**를 약속한다.
- 쪽지는 **시작줄(응답은 상태줄) / 헤더 / 빈 줄 / 본문**으로 나뉜다.
- **경로는 대상, 메서드는 행동**이고, 중간 장비도 메서드를 참고한다.
- **요청마다 맥락을 다 담는다(무상태).** 그래서 반복되는 정보도 매번 담는다. 이 성질과 메서드를 살려 서비스를 설계하는 방식이 REST다.
- 본문 형식은 `Content-Type`에 적고, 키 이름은 **서비스가 정한 약속(API 명세)**이다.

다음 편에서는 HTTP 쪽지를 감싸는 바로 다음 칸, **TCP**를 열어 본다. 포트가 적히는 곳이자, 인터넷이라는 엉성한 길 위에서 쪽지를 빠짐없이, 순서대로 전달하는 약속이다.
