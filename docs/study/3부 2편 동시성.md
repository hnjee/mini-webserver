# 웹서버 동작 원리 2편: 동시성

> 요청 여러 개를 동시에 처리하려면 어떻게 해야 하나.
> **문제 → 해결책 → 남은 문제 → 다음 해결책** 순서로 따라간다.
>
> 이전 편: [1편: 요청 하나의 여정](./01-요청-하나의-여정.md)

---

## 1. 문제의 출발점

1편의 서버는 스레드 하나로 이렇게 돌았다.

```c
while (1) {
    int fd = accept(lfd, ...);
    handle(fd);          // 안에서 read() → 처리 → write()
}
```

**`read()`는 수신 버퍼가 비어 있으면 스레드를 재운다.** 스레드가 하나뿐이면 그동안 아무도 다른 손님을 받지 못한다. 다른 손님의 handshake는 커널이 끝내 두지만, `accept()`할 스레드가 자고 있으니 accept 대기열에서 계속 기다린다.

---

## 2. 문제 A: 손님을 기다리느라 스레드가 묶인다

출발점의 문제를 정확히 말하면, **서버는 할 일이 없는데 손님 쪽 사정 때문에 스레드가 기다리는 것**이다. 이걸 문제 A라고 부르자. 이런 경우들이 다 여기에 들어간다.

- **요청이 천천히 도착함**: 느린 모바일 네트워크, 큰 파일 업로드. keep-alive와 상관없이 생긴다.
- **keep-alive로 쉬는 중**: 요청 하나를 끝내고 다음 요청이 아직 안 옴. (HTTP/1.0은 응답 후 닫는 게 기본이라 원래는 없던 상황이다. 1.0의 비공식 확장 `Connection: keep-alive`가 널리 쓰이면서 HTTP/1.1에서 연결 유지가 기본값이 되었다. 대신 1.0 방식은 요청마다 handshake를 다시 한다.)
- **연결만 하고 첫 요청을 아직 안 보냄**: 브라우저는 연결을 미리 열어 두기도 한다.
- **일부러 천천히 보내는 공격**: 헤더를 몇 초에 한 글자씩 보내는 slowloris.
- **손님이 응답을 천천히 받음**: 손님의 수신 버퍼가 차면 서버의 송신 버퍼도 차서, 블로킹 `write()`가 스레드를 재운다(1편 3-3 흐름 제어).

모두 원인이 **손님**에게 있다. 서버가 아무리 빨라도 피할 수 없다.

---

## 3. 해결 방향 두 가지

1. **스레드 자체를 여러 개 둔다** → 한 스레드가 잠들어도 다른 스레드가 일한다. (스레드풀)
2. **연결과 스레드를 분리한다** → 스레드가 특정 연결에 잠들지 않게 한다. 기다리는 일은 커널에 맡긴다. (epoll)

---

## 4. 해결 1: 스레드를 여러 개 — 스레드풀

```
[메인 스레드] accept() → [작업 큐: fd 번호] → [워커 스레드 N개] read → 처리 → write
```

- 워커 스레드는 서버 시작 때 미리 N개 만들어 두고 계속 재사용한다.
- 작업 큐에 서는 건 **fd 번호(일의 이름표)**일 뿐이다. 번호가 스레드가 되는 게 아니라, 워커가 번호를 집어 들고 그 소켓으로 일한다.
- 큐는 뮤텍스 + 조건 변수로 보호한다.

**좋아진 점**: 한 워커가 잠들어도 다른 워커가 다른 손님을 받는다.

**한계**: 문제 A를 **해결한 게 아니라 버티는 것**이다. 워커가 여전히 연결에 붙어서 `read()`로 기다린다.

```
워커 8개, keep-alive 유휴 제한 5초
0.01초  손님 1~8 응답 끝 → 워커 8개 모두 "다음 요청 오나?" 하고 잠듦
0.02초  손님 9 도착 → 처리할 워커 없음
5.01초  워커들이 제한 시간 끝나고 풀려남 → 그제야 손님 9 처리 (0.01초면 될 일)
```

손님 쪽 사정이 워커를 붙잡으니, 사실상 **워커 수 = 동시에 받을 수 있는 손님 수**가 되어 버린다.

## 5. 해결 2: 연결과 스레드를 분리 — epoll

**아이디어**: 소켓 하나에 잠들지 말고, "등록한 소켓 **아무거나** 준비되면 깨워 줘"라고 잠든다.

- `read(5)` → "5번에 데이터 오면 깨워 줘"
- `epoll_wait()` → "등록한 소켓 중 아무거나 읽을 게 생기거나(`EPOLLIN`) 쓸 자리가 생기면(`EPOLLOUT`) 깨워 줘"

### epoll은 어떻게 동작하나

1편의 OS 구조는 그대로이고, 커널에 **epoll 객체** 하나가 추가된다(이것도 fd로 다룸).

```
[epoll 객체]
  ├─ 감시 목록: 등록한 소켓들 (수만 개 가능)
  └─ 준비 목록: 지금 처리할 수 있는 소켓들
```

TCP가 데이터를 소켓의 수신 버퍼에 넣는 **바로 그 순간**, 등록할 때 걸어 둔 콜백이 그 소켓을 준비 목록에 올리고 잠든 스레드를 깨운다. 스레드는 준비 목록만 받아서 처리한다.

> **poll·select와의 차이**: 둘 다 자는 동안은 CPU를 안 쓰고 같은 커널 알림으로 깨어난다. 하지만 poll은 어느 소켓 때문에 깼는지 기록하지 않고, 호출 사이에 목록도 기억하지 않아서 **매번 전부 다시 확인**한다. epoll은 준비된 소켓을 기록해 두므로 **준비된 것만** 본다. poll은 함수일 뿐이고, epoll은 커널에 객체가 남는다.

### 이벤트 루프

```c
while (1) {
    n = epoll_wait(ep, ready, 64, -1);
    for (준비된 소켓) {
        if (대기용 소켓) accept → 논블로킹 설정 → epoll에 등록
        else             있는 만큼 read → 요청이 완성되면 처리 → 쓸 수 있는 만큼 write
    }
}
```

필요한 것:
- **논블로킹 소켓**: `read()`/`write()`가 절대 잠들지 않고, 없으면 `EAGAIN`을 돌려준다.
- **연결별 상태 구조체**: 덜 온 요청, 덜 보낸 응답을 기억해 둔다. 스레드가 연결을 들고 있지 않으니 지역 변수로는 안 된다.

**좋아진 점**: 문제 A 해결. 쉬는 연결은 커널 소켓과 epoll 감시 목록이 들고 있고, 스레드는 준비된 일만 한다. 스레드 하나로 연결 수만 개를 받는다.

- **연결 수** = 열려 있는 소켓 수 (수만 개)
- **스레드가 바쁜 정도** = 지금 실제로 처리 중인 일

### CPU를 다 쓰려면: 루프를 코어 수만큼

루프 하나는 코어 하나만 쓴다. 코어가 4개면 루프를 4개 띄운다.

- 루프마다 자기 epoll 객체, 자기 대기용 소켓(`SO_REUSEPORT`), 자기 연결들을 가진다.
- 연결 하나는 처음 받은 루프가 끝까지 맡으므로, 루프끼리 공유하는 게 없어 뮤텍스가 필요 없다.
- **이게 nginx의 구조다.**

## 6. 또 다른 문제 B: 서버 쪽 일 때문에 기다린다

여기까지는 **손님 때문에 기다리는 문제(A)** 를 풀었다. 그런데 스레드가 멈추는 이유가 하나 더 있다. **요청은 다 왔는데, 서버가 답을 만드는 동안 기다리는 경우**다. 이걸 문제 B라고 부르자.

- **B-1. 무언가를 기다림 (I/O 대기)**: DB 조회, 외부 API 호출, 파일 읽기. 스레드는 일을 안 하는데 자리를 차지한다. **웹서버에서 가장 흔하고 핵심적인 경우다.**
- **B-2. 계산 자체가 오래 걸림**: 이미지 변환, 암호화, 큰 데이터 처리. 스레드가 실제로 CPU를 쓰며 일한다.

### 6-1. 해결 원리: 멀티스레드 + OS 스케줄러

스레드가 I/O를 기다리면 **OS가 그 스레드를 blocked 상태로 빼 두고, 실행 가능한 다른 스레드에게 CPU를 넘긴다.** 그러니 스레드를 여러 개 두면, 몇 개가 기다리는 동안 나머지가 CPU를 쓴다. 문제 B-1을 푸는 본체는 이것이다.

**스레드풀은 그 스레드들을 관리하는 방법**이다. 요청마다 스레드를 만들면 생성 비용·메모리·문맥 전환이 커지고 손님이 몰리면 끝없이 늘어나니,

- 정해진 수만큼 미리 만들어 **재사용**하고
- 그 수를 **CPU가 놀지 않을 만큼** 정하고
- 넘치는 일은 **큐에서 기다리게** 한다.

**워커 수 정하기**

> 워커 수 ≈ 코어 수 × (1 + 기다리는 시간 ÷ 계산하는 시간)

- 코어 4개, 요청당 계산 2ms·DB 대기 8ms → 워커 하나가 10ms 중 2ms만 CPU를 쓰니 5개가 번갈아야 코어 하나가 찬다 → 4 × 5 = **20개**
- 계산만 하는 일(B-2)이면 → **코어 수** 정도. 코어보다 늘려도 동시에 계산할 수 있는 수는 그대로다.
- 상한도 있다: **DB 연결 수**(DB가 20개만 받으면 워커 100개 중 80개는 줄만 선다), 그리고 **실제로 쓸 수 있는 코어 수**(같은 컴퓨터의 다른 프로그램, 컨테이너 CPU 제한).
- 마지막엔 `wrk`로 측정해서 정한다.

> 코어를 프로그램들에 나눠 주는 것도 OS 스케줄러다. 기본은 칸막이 없이 모든 스레드가 모든 코어를 두고 경쟁하고, 필요하면 우선순위(`nice`), CPU 고정(affinity), 사용량 제한(cgroups, 컨테이너)으로 규칙을 준다.

### 6-2. 두 문제를 나란히 보면

| | 문제 A: 손님 때문에 기다림 | 문제 B: 서버 쪽 일 때문에 기다림 |
|---|---|---|
| 예 | 느린 네트워크, keep-alive 유휴, 느린 수신 | DB 조회, 파일 읽기, 외부 API (+ 무거운 계산) |
| 해결 원리 | 기다리는 일을 **커널(epoll)에 맡겨** 스레드가 묶이지 않게 | 기다리는 스레드는 **OS가 재워 두고** 다른 스레드가 CPU를 쓰게 (멀티스레드) |
| 구현 방법 | 이벤트 루프 | 스레드풀 |

둘 다 **"기다림은 OS에게 맡긴다"**는 같은 발상이다.

> 참고: DB와 외부 API도 결국 네트워크 소켓이라, B-1도 **비동기 I/O**로 바꾸면 epoll에 맡길 수 있다(Node.js, Netty, Spring WebFlux). 그러면 기다리는 동안 스레드를 놓아준다. 대신 코드가 복잡해진다. 일반 파일 읽기는 epoll로 기다릴 수 없고, 계산(B-2)은 기다림이 아니라서 결국 스레드가 필요하다.

### 6-3. epoll 루프 + 스레드풀

epoll 루프는 처리까지 직접 한다. 그래서 문제 B가 생기면 루프 자체가 멈춘다.

```
루프 1이 연결 1만 개를 맡고 있음
0.000초  손님 A 요청 처리 → DB 조회 200ms (루프가 이 줄에서 멈춤)
0.001초  손님 B, C, D... 데이터 도착 → 준비 목록에 쌓이지만 아무도 처리 못 함
0.200초  A 끝 → 그제야 B, C, D... 처리
```

epoll은 손님을 기다리는 문제만 풀어 준다. 그래서 **역할을 나눈다.**

```
[이벤트 루프]  accept, read, write만. 요청이 완성되면 작업 큐에 넣고 바로 다음 소켓으로
       ↓ 작업 큐
[워커 스레드풀] 오래 걸리는 일 처리 (DB를 기다리는 건 워커)
       ↓ "다 됐어" (eventfd를 epoll에 등록해 두고 알림)
[이벤트 루프]  응답 쓰기
```

- 루프는 절대 멈추지 않고, 기다림이 있는 일은 워커가 맡는다.
- 같은 연결을 루프와 워커가 동시에 건드리지 않게 주의한다.

> 4장의 스레드풀과의 차이: 4장의 워커는 **손님도 기다렸다**(문제 A까지 떠안음). 여기서의 워커는 **서버 쪽 일만 한다**(문제 B만 맡음).

### 6-4. 스레드풀의 주의점: 워커는 요청이 끝날 때까지 잡힌다

```
[작업 큐]  →  [워커 8개]  →  [코어 n개]
 프로그램이     프로그램이      OS가
 관리          관리           나눠 줌
```

- **워커 ↔ 요청**: 요청 하나가 워커를 잡으면 응답을 보내고 끝날 때까지 놓지 않는다.
- **워커 ↔ 코어**: 그동안 워커 스레드는 DB를 기다리거나 시간이 쪼개지면서 코어에 올라갔다 내려왔다 한다. 그래도 워커는 계속 그 요청 전용이다.
- 그래서 **동시에 처리 중인 요청 수 = 워커 수**이고, 나머지는 큐에서 기다린다.

**느린 요청이 워커를 전부 잡으면?** 예를 들어 외부 결제 API가 10초씩 걸리기 시작하면, 그 요청 8개가 워커를 다 잡고 가벼운 요청들까지 큐에서 10초씩 기다린다. 그래서 함께 쓰는 방법들:

- **타임아웃**: DB·외부 API 호출에 제한 시간을 둔다. 가장 기본.
- **벌크헤드(bulkhead)**: 느릴 수 있는 일과 빠른 일의 워커 묶음을 따로 둔다. 한쪽이 막혀도 다른 쪽은 돈다.
- **큐 길이 제한 + 빠른 거절**: 큐가 너무 길면 `503`으로 바로 돌려보낸다.
- **비동기 I/O**: 기다리는 동안 스레드를 놓아주게 바꾼다.
- **모니터링**: 큐 대기 시간과 워커 사용률을 지켜본다.

> 직접 실험: `/slow` 경로만 `sleep(5)` 하게 만들고 워커 수만큼 요청한 뒤 일반 경로를 요청해 본다. 일반 요청도 5초씩 기다린다. `/slow`용 워커 묶음을 따로 두면 다시 빨라진다.

## 7. 구현 순서

| 단계 | 만들 것 | 해결되는 것 | 확인 실험 |
|---|---|---|---|
| 0 (지나온 길) | 스레드풀 + `read()` | 문제 A를 워커 수만큼 버팀 | `nc`로 연결만 워커 수만큼 열어 두면 서버가 멈춤 |
| 1 | 싱글 스레드 epoll 루프 | **문제 A** | 같은 `nc` 실험에도 바로 응답 · `wrk -c1000` |
| 2 | epoll 루프 × 코어 수 (`SO_REUSEPORT`) | CPU 전부 활용 | 1단계와 `wrk` 처리량 비교 |
| 3 | epoll 루프 + 워커 스레드풀 | **문제 B** | 처리에 `usleep(200000)` 넣고, 다른 연결이 안 느려지는지 |

덤: 1단계 이후 **유휴 연결 타임아웃**(마지막 활동 시각 기록 + `epoll_wait`의 대기 시간 활용)을 넣으면 nginx의 `keepalive_timeout`과 같아진다.

## 8. 실제 서버들은 어디쯤인가

| 서버 | 구조 | 문제 A | 문제 B |
|---|---|---|---|
| Apache prefork (예전) | 프로세스 풀 + 블로킹 | 버팀 | 버팀 |
| Node.js | epoll 루프 1개 | 해결 | 루프가 멈춤 |
| nginx | epoll 루프 × 코어 수 (워커 프로세스) | 해결 | 직접 안 하고 뒤쪽 서버로 넘김 |
| Tomcat | Acceptor + Poller(epoll) + 워커 스레드풀 | 해결 | 해결 |
| Apache event | 자식 프로세스마다 리스너(epoll, accept 겸) + 워커 스레드들 | 해결 | 해결 |

실제 서비스에서 흔한 조합:

```
손님들 → [nginx: 문제 A 담당, 연결 수만 개] → [애플리케이션 서버: 스레드풀, 문제 B 담당]
```

---

## 9. 핵심 요약

1. `read()`는 수신 버퍼가 비면 스레드를 재운다. 손님 때문에 스레드가 묶이는 **문제 A**가 출발점이다.
2. **스레드를 여러 개**(스레드풀) 두면 버틸 수는 있지만, 손님이 스레드를 붙잡는 건 그대로다.
3. **연결과 스레드를 분리**(epoll)하면 문제 A가 풀린다. 기다림은 커널이 맡고 스레드는 준비된 일만 한다.
4. 그런데 스레드가 멈추는 이유가 하나 더 있다. DB·파일·외부 API 같은 서버 쪽 일을 기다리는 **문제 B**다.
5. 문제 B를 푸는 원리는 **멀티스레드 + OS 스케줄러**(기다리는 스레드는 재우고 다른 스레드가 CPU를 씀)이고, **스레드풀**은 그 스레드를 몇 개 두고 어떻게 재사용할지 정하는 관리 방법이다.
6. 그래서 **epoll로 손님을 받고, 스레드풀로 서버 쪽 일을 처리한다.** 두 경우 모두 "기다림은 OS에게 맡긴다."
7. 스레드풀의 워커는 요청이 끝날 때까지 잡히므로, 느린 일에는 타임아웃·벌크헤드·빠른 거절을 함께 쓴다.

## 부록: 헷갈렸던 것들

- **fd 번호가 워커를 받으면 스레드가 되나?** 아니다. 스레드는 미리 만든 수만큼 계속 살아 있고, fd는 끝까지 일의 이름표다.
- **워커 수 = 사용자 수?** 아니다. 사용자가 화면을 보는 동안은 요청이 없다. 단, 워커가 연결을 붙잡고 기다리는 구조(4장)에서는 실제로 그렇게 되어 버린다.
- **epoll을 쓰면 OS 구조가 바뀌나?** 아니다. 소켓·버퍼·대기열은 그대로이고 epoll 객체만 추가된다.
- **poll()은 누가 호출하나?** 웹서버 스레드가 호출한다. 그러면 커널이 각 소켓에 "데이터 있니?"라고 묻는다.
- **nginx 워커들은 같은 수신 버퍼를 두고 어떻게 동기화하나?** 공유하지 않는다. 연결 하나는 받은 워커가 끝까지 맡고, 워커마다 epoll 객체도 따로다. 함께 쓰는 대기용 소켓은 OS가 연결 하나를 한 워커에게만 주도록 보장한다.
- **운영 숫자**: accept 대기열 = min(`listen()` backlog, `somaxconn`), fd 한도 = `ulimit -n`(기본 1024인 환경이 많음), 확인은 `ss -lnt`.
