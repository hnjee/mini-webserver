# 2부 3편: TCP와 UDP - 프로그램 사이의 전달을 책임지는 전송 계층

Nov 21, 2026 · @현지

## 들어가며

처음에는 TCP가 "포트를 실어 보내는 칸"인 줄 알았다. 짐에 실리는 정보만 보면 그렇게 보인다. 하지만 2부 1편에서 본 것처럼 계층은 역할로 나뉜다. 전송 계층은 **프로그램과 프로그램 사이의 전송 전체**를 책임진다. 누구에게 줄지뿐 아니라, 잘 도착했는지까지.

이번 편에서는 HTTP 쪽지를 바로 감싸는 칸, TCP를 열어 본다. 그리고 같은 전송 계층의 다른 선택지, UDP도 함께 본다.

## 1. TCP는 무엇을 약속했나

한 줄로 말하면, **양 끝의 프로그램 사이에서 데이터를 빠짐없이 순서대로 전달해 주겠다**는 약속이다. 브라우저는 "이거 보내 줘" 하고 넘기기만 하면 된다. 받는 쪽 프로그램은 보낸 그대로, 빠진 것 없이, 순서대로 받는다.

그래서 TCP가 하는 일은 두 가지다.

1. **누구에게**: 포트로 어느 프로그램인지 알려준다.
2. **확실하게**: 없어지거나 순서가 바뀐 데이터를 수습한다.

### 인터넷이라는 길에서 생기는 일

아래 계층의 IP는 도착을 보장하지 않는다. 그래서 이런 일이 생긴다.

- **없어짐**: 라우터가 너무 바쁘면 패킷을 버리기도 한다.
- **순서 뒤바뀜**: 패킷마다 다른 길로 갈 수 있어서 뒤에 보낸 게 먼저 도착하기도 한다.
- **중복**: 같은 패킷이 두 번 도착하기도 한다.

### 왜 하필 TCP가 맡나

- **IP가 아닌 이유**: IP 칸은 라우터가 읽는다. 라우터가 수많은 대화의 도착 여부까지 챙기면 느려진다. 그래서 IP는 일부러 최선형 전달로 설계됐다.
- **HTTP가 아닌 이유**: HTTP가 맡으면 메일, 원격 접속 같은 다른 서비스도 같은 기능을 따로 만들어야 한다.
- **그래서 TCP**: TCP 칸은 양 끝 컴퓨터만 읽는다. 무엇을 보냈는지는 보낸 쪽이, 무엇을 받았는지는 받은 쪽이 안다. 게다가 운영체제가 처리해서 모든 프로그램이 함께 쓴다.

참고로 처음에는 TCP와 IP가 하나의 약속이었다. 1970년대 후반, 확실한 전달이 필요 없는 프로그램도 IP를 쓸 수 있도록 둘로 나뉜었다.

## 2. TCP의 세 도구

### 도구 1: 순서 번호

TCP는 보내는 데이터에 번호를 매긴다. 받는 쪽은 번호를 보고 순서를 다시 맞추고, 같은 번호가 두 번 오면 하나는 버린다. (실제로는 조각 번호가 아니라 "몇 번째 바이트부터인지"로 매기지만 원리는 같다.)

```
보낸 순서:  [1번] [2번] [3번]
도착 순서:  [1번] [3번] [2번]   → 번호대로 다시 맞춤
```

### 도구 2: 확인 응답 (ACK)

받는 쪽은 "여기까지 받았어요, 다음 거 주세요"라고 답한다. 이것을 ACK(Acknowledgement)라고 한다. 조각마다 답을 기다렸다 다음 걸 보내는 것이 아니라, 여러 조각을 한꺼번에 보내 놓고 "3번까지 다 받았어요"처럼 한 번에 답할 수도 있다.

### 도구 3: 재전송

보내는 쪽은 보낸 조각을 ACK가 올 때까지 들고 있다. 일정 시간이 지나도 ACK가 없으면 없어졌다고 보고 다시 보낸다.

### 세 도구를 합치면

```
보내는 쪽 → 1번 →              받는 쪽: "1번 받았어요, 2번 주세요"
보내는 쪽 → 2번 → (중간에 없어짐)
보내는 쪽 → 3번 →              받는 쪽: "아직 2번 주세요" (3번은 보관)
보내는 쪽: "2번 답이 없네" → 2번 다시 보냄
                                    받는 쪽: "3번까지 다 받았어요!"
```

## 3. "연결한다"는 것

데이터를 보내기 전에 양쪽이 인사를 세 번 주고받는다. 이것을 **3-way handshake**라고 한다.

```
1. 브라우저 → 서버:  "대화하고 싶어요. 제 번호는 100부터예요"      (SYN)
2. 서버 → 브라우저:  "좋아요. 100번 잘 들었고, 제 번호는 500부터예요" (SYN-ACK)
3. 브라우저 → 서버:  "500번 잘 들었어요. 시작할게요!"              (ACK)
```

전화로 치면 "여보세요?" → "네, 들려요. 제 말도 들리세요?" → "네, 들려요!"다. 이 인사로 두 가지를 확인한다.

- 서로 **말이 통하는지** (양방향으로 다 닿는지)
- 서로 **몇 번부터 셸지** (순서 번호의 시작점)

### 연결의 정체

**연결은 진짜 선이 이어지는 것이 아니다.** 양쪽 컴퓨터가 각자 "나는 지금 저 컴퓨터의 저 포트와 대화 중이고, 몇 번까지 보냈고 몇 번까지 받았다"를 **기억하는 상태**를 연결이라고 부른다. 대화가 끝나면 "이제 끝낼게요"(FIN)를 주고받고 그 기억을 지운다.

연결 하나는 네 가지 값으로 구분된다.

> 출발지 IP + 출발지 포트 + 목적지 IP + 목적지 포트

그래서 노트북을 와이파이에서 랜선으로 바꾸면 연결이 끊길 수 있다. 출발지 IP가 바뀌면 서버 입장에서는 완전히 다른 상대가 되기 때문이다. 그러면 브라우저가 알아서 새로 연결을 맺는다.

### TCP는 기억하고, HTTP는 기억하지 않는다

HTTP는 요청끼리 독립인 무상태인데, 그 아래 TCP는 연결이라는 상태를 기억한다. 배달을 확실히 하려면 "몇 번까지 받았나"를 기억해야 하기 때문이다. 역할이 다르니 성격도 다르다.

## 4. 연결은 얼마나 쓰나

### 인사는 연결당 한 번

3-way handshake는 조각마다 하는 것이 아니다. **연결을 처음 맺을 때 한 번**만 한다. 그 뒤로는 데이터를 바로 보내고, 조각마다 오가는 것은 ACK뿐이다.

```
[처음 한 번]  SYN → SYN-ACK → ACK         (인사)
[그다음]      1번, 2번, 3번 조각           (그냥 보냄)
              ← "3번까지 받았어요" (ACK)
```

### 연결은 여러 요청에 걸쳐 재사용된다

인사가 한 번 왕복하는 동안에는 데이터를 못 보내므로 handshake는 비싸다. 그래서 요청 하나마다 연결하지 않고, 같은 서버와 주고받는 여러 요청에 연결을 재사용한다. 웹페이지 하나만 열어도 HTML, CSS, 이미지 등 수십 개의 요청이 오가기 때문에 이 차이가 크다.

연결은 보통 이럴 때 닫힌다.

- **한동안 조용할 때**: 일정 시간 요청이 없으면 서버나 브라우저가 닫는다. 이 시간은 설정마다 다르다.
- **어느 한쪽이 끝낼 때**: 탭을 닫거나 서버가 재시작할 때.
- **네트워크가 바뀜 때**: 출발지 IP가 바뀌면 네 값이 달라져 다른 연결이 된다.

### 연결을 어떻게 쓸지는 HTTP가 정한다

TCP는 그 연결로 쪽지를 한 장 보내든 백 장 보내든 상관하지 않는다. 통로를 어떻게 쓸지는 그 위의 HTTP가 정한다.

| HTTP 버전 | 연결 사용 방식 |
| --- | --- |
| HTTP/1.0 | 응답을 다 보내면 연결을 닫는다. 브라우저는 연결이 닫히는 걸 보고 응답의 끝을 안다 |
| HTTP/1.1 | 연결을 열어 둔다. 그래서 응답의 끝을 `Content-Length`로 알려야 한다 |
| HTTP/2 | 쪽지를 조각내 꼬리표를 붙이고, 연결 하나에 여러 쪽지를 섞어 보낸다 |
| HTTP/3 | TCP 대신 UDP 위의 QUIC를 쓴다. 인사와 암호화 준비를 한 번에 한다 |

TCP는 데이터를 **끊김 없는 흐름**처럼 전달해서, "여기서 메시지 하나 끝"을 알려주지 않는다. 연결을 열어 두면 "연결이 닫히면 끝"이라는 신호도 쓸 수 없다. 그래서 HTTP/1.1부터 `Content-Length`가 중요해졌다.

연결이 열려 있다고 HTTP가 기억하는 것은 아니다. **TCP 통로는 그대로 두고, 그 위로 독립된 HTTP 쪽지를 여러 장 보내는 것이다.** 그래서 로그인 정보는 여전히 매번 간다.

## 5. TCP 칸의 생김새

2부 1편에서 "다른 정보들"이라고 넘어갔던 부분을 이제 채울 수 있다. (주요한 것만 추렸다.)

```
[ 출발지 포트 | 목적지 포트 | 순서 번호 | 확인 응답 번호 | 표시 | 받을 수 있는 양 | … ]
```

| 칸 | 하는 일 |
| --- | --- |
| 출발지 포트, 목적지 포트 | 어느 프로그램에서 어느 프로그램으로 |
| 순서 번호 | 이 데이터가 몇 번째인지 |
| 확인 응답 번호 | "여기까지 받았으니 다음은 이 번호 주세요" |
| 표시 | 인사(SYN)인지, 확인(ACK)인지, 끝인사(FIN)인지 |
| 받을 수 있는 양 | "답을 안 기다리고 한 번에 이만큼까지 보내도 돼요." 받는 쪽이 넘치지 않게 속도를 조절한다 |

칸 하나하나가 1번의 두 가지 일과 이어진다. 포트는 **누구에게**, 나머지는 **확실하게**를 위한 칸이다.

## 6. UDP: 포트만 붙여 주는 약속

UDP는 같은 전송 계층의 약속이지만, TCP의 두 가지 일 중 **누구에게**만 한다. 연결 인사도, 순서 번호도, "받았어요"도 없다. 보내는 쪽은 그냥 던지고 잊는다. 빠르기 위한 기술이 따로 있는 것이 아니라, **할 일을 최소한으로 줄였더니 결과적으로 빠른 것**이다.

```
UDP 칸: [ 출발지 포트 | 목적지 포트 | 길이 | 검사값 ]
```

검사값으로 데이터가 깨졌는지는 확인하지만, 깨졌으면 버리기만 한다. 또 TCP가 끊김 없는 흐름인 것과 달리, UDP는 **한 번 보낸 덩어리가 그대로 한 덩어리로** 도착한다(도착한다면).

### 언제 쓰나

- **영상 통화, 게임**: 조금 전 화면을 다시 받는 것보다 지금 화면을 빨리 받는 게 중요하다.
- **DNS 질문**: 한 번 묻고 한 번 답하면 끝이라 인사부터 하는 게 낭비다. 답이 안 오면 다시 물으면 된다.

### UDP 위에 다시 만든 확실함: QUIC

확실한 전달이 필요한데 TCP는 쓰고 싶지 않다면, UDP 위에 직접 그 기능을 만들면 된다. HTTP/3가 쓰는 **QUIC**가 그렇다. UDP를 바닥에 깔고 순서 맞추기, 재전송, 암호화를 새로 만들었다. TCP는 운영체제에 들어 있어 고치기 어렵지만, UDP 위에 프로그램으로 만들면 마음대로 개선할 수 있다. QUIC는 IP가 바뀌어도 연결을 이어 갈 수 있게 설계됐다.

## 마치며

전송 계층에는 두 가지 선택지가 있다. **TCP는 "확실한 전달까지 다 해 줄게"**, **UDP는 "포트만 붙여 줄 테니 나머지는 알아서 해"**다.

| 구분 | TCP | UDP |
| --- | --- | --- |
| 포트 | 있음 | 있음 |
| 연결 인사 | 있음 (3-way handshake) | 없음, 바로 보냄 |
| 순서 맞추기, 재전송 | 있음 | 없음 |
| 데이터 모양 | 끊김 없는 흐름 | 보낸 덩어리 그대로 |
| 성격 | 확실하지만 조금 느림 | 빠르지만 보장 없음 |
| 쓰는 곳 | 웹, 메일, 파일 전송 | 영상 통화, 게임, DNS |

### 같은 영상인데 왜 다를까: 유튜브와 영상 통화

유튜브는 웹이다. 영상을 몇 초짜리 조각으로 잘라 두고, 플레이어가 HTTP로 "다음 조각 주세요"를 계속 요청한다. 인터넷이 느려지면 화질 낮은 조각을 요청하기도 한다.

같은 영상인데 유튜브는 확실한 전달을, 영상 통화는 UDP를 고르는 이유는 **기다릴 수 있느냐**다.

- **유튜브**: 지금 장면보다 수십 초 앞을 미리 받아 둔다(버퍼링). 조각 하나를 다시 받느라 조금 늦어도 화면은 멈추지 않는다.
- **영상 통화**: 지금 말하는 얼굴을 바로 보내야 해서 미리 받아 둘 수 없다. 없어진 걸 기다리면 대화가 끊기므로, 보통 UDP 위의 실시간 전용 약속을 쓴다.

다음 편에서는 TCP와 UDP를 감싸는 바로 다음 칸, 모래시계의 가운데인 **IP**를 열어 본다.
