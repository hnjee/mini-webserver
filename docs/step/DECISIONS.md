# 결정 기록

이 문서를 읽으면 모든 Step에서 정한 것과 그 이유를 한곳에서 볼 수 있어요. 각 Step의 자세한 과정은 같은 폴더의 `STEPn.md`에 있어요.

## Step 0. 공통 준비

| # | 결정 | 이유 |
| - | ---- | ---- |
| 0-1 | 실행 인자는 `-p` 포트, `-r` 루트, `-c` 라우팅 설정 파일로 받는다. | 팀원 모두 같은 명령어로 완료 기준을 확인하기 위해서예요. (DESIGN.md 제안과 같음) |
| 0-2 | 인자 파싱은 `getopt()`로 한다. | POSIX 표준이라 과제에서 허용되고, 순서 무관 처리와 기본 에러 검사를 해줘요. |
| 0-3 | 포트는 `strtol()`로 바꾸고 1~65535 정수만 받는다. | `atoi()`는 `"abc"`나 `"80abc"` 같은 잘못된 입력을 알아챌 수 없어요. |
| 0-4 | `-p`와 `-r`은 필수, `-c`는 선택으로 한다. 루트는 디렉터리인지, `-c`는 파일인지 시작할 때 검사한다. | `-c`는 Step 6부터 써요. 잘못된 경로는 요청을 받기 전에 알려주는 게 원인을 찾기 쉬워요. |
| 0-5 | 잘못된 인자는 에러와 사용법을 `stderr`에 출력하고 종료 코드 2로 끝낸다. `-h`는 사용법을 `stdout`에 출력하고 0으로 끝낸다. | 종료 코드 2는 "사용법 오류"를 뜻하는 관례예요. |

| 0-7 | 컴파일 옵션은 `-std=c11 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic`로 한다. | 표준 C와 POSIX만 쓰는지 컴파일러가 확인해줘요. `getopt()`, `stat()` 같은 POSIX 함수를 쓰려면 `_POSIX_C_SOURCE`가 필요해요. |
| 0-8 | 소스는 `src/`에 두고, 설정 읽기는 `config.c`/`config.h`로 분리한다. | `main.c`는 흐름만 담고, Step마다 기능을 모듈로 붙이기 위해서예요. |
| 0-9 | `www/`에 `index.html`, `style.css`, `app.js`, `image.png`, `photo.jpg`, `large.bin`, `secret.txt`를 둔다. | 정적 파일, MIME, 큰 파일, 403 테스트에 같은 재료를 쓰기 위해서예요. (DESIGN.md 제안과 같음) |
| 0-10 | `large.bin`과 `secret.txt`는 `make www`로 만들고 git에 올리지 않는다. | `large.bin`은 5MB라 저장소에 넣기엔 커요. git은 권한 000을 저장하지 못해서 `secret.txt`는 받은 뒤 직접 만들어야 해요. |
| 0-11 | 빌드·실행·테스트는 Docker의 Ubuntu 24.04 컨테이너에서 한다. 편집은 Mac에서 한다. | `epoll`과 valgrind를 쓸 수 있고, 팀원과 같은 환경에서 결과를 비교할 수 있어요. |
| 0-12 | `compose.yaml`로 프로젝트 폴더를 컨테이너의 `/app`에 마운트하고, 8080 포트를 Mac에 연다. | Mac에서 고친 파일이 바로 컨테이너에 보여요. Step 3에서 Mac 브라우저로 확인할 수 있어요. |

## Step 1. TCP 에코 서버

| # | 결정 | 이유 |
| - | ---- | ---- |
| 1-1 | `socket()` → `setsockopt(SO_REUSEADDR)` → `bind()` → `listen()` → `accept()` 반복 흐름으로 만든다. | 과제의 필수 구현 흐름이에요. (DESIGN.md 제안과 같음) |
| 1-2 | `SO_REUSEADDR`는 `bind()` 전에 켠다. | 켜지 않으면 재시작할 때 `TIME_WAIT` 때문에 `bind()`가 실패해요. (DESIGN.md 제안과 같음) |
| 1-3 | IPv4(`AF_INET`)로, 모든 네트워크 주소(`INADDR_ANY`)에서 연결을 받는다. 포트는 `htons(cfg.port)`로 넣는다. | 과제 테스트는 IPv4로 충분해요. `127.0.0.1`에만 묶으면 Docker 포트 연결로 들어오는 Mac의 요청을 못 받아요. 소켓 주소는 네트워크 바이트 순서(빅 엔디언)여야 해서 `htons()`로 바꿔요. |
| 1-4 | `listen()`의 대기열 길이는 `SOMAXCONN`으로 한다. | OS가 허용하는 최대값이라, 순간적으로 연결이 몰려도 대기열에서 거절될 일이 적어요. |
| 1-5 | 한 번에 연결 하나만 처리하는 반복 서버로 만든다. | Step 1은 통로 확인이 목적이에요. 동시 처리는 Step 5에서 방식을 골라 붙여요. |
| 1-6 | `read()`가 양수면 그 바이트만 돌려주고, 0이면 연결을 닫고, -1이면 `EINTR`은 다시 읽고 나머지는 연결을 닫는다. | 반환값의 뜻을 그대로 따르는 처리예요. (DESIGN.md 제안과 같음) |
| 1-7 | 쓰기는 `write_all()`로 `n`바이트를 끝까지 보낸다. | `write()`는 요청한 것보다 적게 쓰고 돌아올 수 있어요. Step 2의 응답 전송에도 그대로 써요. |
| 1-8 | 서버 준비 단계(`socket`, `setsockopt`, `bind`, `listen`)가 실패하면 `perror()`를 출력하고 종료 코드 1로 끝낸다. `accept()` 실패는 출력만 하고 다음 연결을 기다린다. 연결 하나의 에러는 그 연결만 닫는다. | 준비가 안 되면 서버를 돌릴 수 없지만, 연결 하나의 문제로 서버 전체가 멈추면 안 돼요. |
| 1-9 | 읽기 버퍼는 4096바이트 지역 배열로 한다. | 에코는 받은 만큼 바로 돌려주니 크게 잡을 필요가 없고, `malloc()`·`free()`를 맞출 필요도 없어요. |
| 1-10 | 연결을 받거나 닫을 때 클라이언트 IP와 포트를 `stdout`에 출력한다. | 터미널 두 개로 접속할 때 어느 연결이 처리 중인지 눈으로 확인할 수 있어요. |
| 1-11 | 소켓 코드는 `server.c`/`server.h`로 분리하고, `main.c`는 설정을 읽은 뒤 서버 함수를 부르기만 한다. | Step 2부터 에코 대신 HTTP 처리 함수로 바꿔 끼우기 쉬워요. |
| 1-12 | `SIGPIPE` 처리는 Step 7로 미룬다. | 클라이언트가 끊긴 뒤 `write()`하면 서버가 종료될 수 있다는 걸 알고 넘어가요. R-09는 Step 7 요구사항이에요. |

## Step 2. HTTP 요청 파싱 + 고정 응답

| # | 결정 | 이유 |
| - | ---- | ---- |
| 2-1 | 연결마다 8KB(8192바이트) 고정 크기 버퍼에 이어 붙이고, `\r\n\r\n`이 나올 때까지 `read()`를 반복한다. | TCP는 메시지 경계를 몰라서 한 번의 `read()`로 다 온다고 가정할 수 없어요. (DESIGN.md 제안과 같음) 정상 요청 헤더는 8KB 안에 들어오고, 늘어나는 버퍼도 상한은 필요해서 고정 배열이 단순해요. |
| 2-2 | 버퍼가 가득 찼는데 `\r\n\r\n`이 없으면 431을 보내고 연결을 닫는다. | 431은 "헤더가 너무 크다"는 전용 코드라 400보다 원인이 분명해요. 요청 끝을 모르니 남은 바이트를 믿을 수 없어요. |
| 2-3 | 헤더가 끝나기 전에 `read()`가 0이면 응답 없이 연결을 닫는다. -1이면 `EINTR`은 다시 읽고 나머지는 연결을 닫는다. | 상대가 요청을 다 보내지 않고 끊었으니 응답할 대상이 없어요. 1-6의 `read()` 처리를 그대로 따라요. |
| 2-4 | `\r\n\r\n` 뒤에 딸려 온 바이트는 Step 2에서는 버린다. | Step 2는 응답 하나를 보내고 연결을 닫아요. 남은 바이트를 앞으로 당겨 다음 요청이나 본문으로 쓰는 건 Step 4에서 만들어요. |
| 2-5 | 파싱 결과는 버퍼 안을 가리키는 포인터로 struct에 담는다. 구분자 자리에 `'\0'`을 써 넣는다. 요청 처리가 끝나기 전에는 버퍼를 다시 채우거나 당기지 않는다. | 복사가 없고, 길이 검사가 버퍼 크기 하나로 끝나요. 요청 하나를 한 흐름 안에서 끝내는 구조라 버퍼가 바뀔 때 struct를 쓰고 있을 일이 없어요. |
| 2-6 | struct에는 `method`, `uri`, `version`, `host`, `content_length`, `connection`을 담는다. 그 밖의 헤더는 형식만 검사하고 버린다. 헤더 이름은 대소문자를 구분하지 않는다. | R-02가 요구하는 항목이에요. `Content-Length`와 `Connection`은 Step 4에서 써요. HTTP 헤더 이름은 대소문자를 구분하지 않아서 `host:`도 받아야 해요. |
| 2-7 | 지원 메서드는 `GET`, `POST`다. 그 밖의 메서드는 501이다. 메서드는 대소문자를 구분한다. | POST 본문은 Step 4에서 읽지만 아는 메서드로는 지금부터 인정해요. HTTP 메서드는 대소문자를 구분해요. |
| 2-8 | 지원 버전은 `HTTP/1.0`, `HTTP/1.1`이다. `HTTP/`로 시작하는 다른 버전은 505, `HTTP/`로 시작하지 않으면 400이다. | 형식이 맞는 다른 버전과 아예 틀린 형식을 구분해요. |
| 2-9 | 400 조건: 요청 라인이 세 조각이 아님, URI가 `/`로 시작하지 않음, 헤더 줄에 `:`가 없음, `Content-Length`가 0 이상의 정수가 아님, `HTTP/1.1`인데 `Host`가 없음. | 형식이 틀린 요청이에요. `HTTP/1.1`의 `Host` 필수는 RFC 9112 규칙이에요. |
| 2-10 | 판정 순서는 형식(400) → 메서드(501) → 버전(505)이다. | 형식이 틀렸으면 메서드나 버전을 따질 의미가 없어요. |
| 2-11 | Step 2는 모든 응답 뒤에 연결을 닫고, 응답에 `Connection: close`를 넣는다. | keep-alive는 Step 4에서 만들어요. 에러 뒤에는 남은 바이트를 믿을 수 없어서 Step 4에서도 닫아요. |
| 2-12 | 응답은 `send_response(fd, status, content_type, body, body_len)` 하나로 보낸다. `Content-Length`는 함수가 `body_len`으로 쓴다. | 본문 길이와 `Content-Length`가 어긋날 수 없어요. (DESIGN.md 제안과 같음) |
| 2-13 | 응답 헤더는 `Date`, `Content-Type`, `Content-Length`, `Connection`을 넣는다. | R-03의 표준 헤더예요. `Date`는 RFC 9110이 시계가 있는 서버는 보내라고 정했어요. |
| 2-14 | 헤더는 512바이트 지역 배열에 `snprintf()`로 만들고, `write_all()`로 헤더 → 본문 순서로 보낸다. | 헤더는 짧아서 작은 배열로 충분해요. 부분 `write()`는 1-7의 `write_all()`이 처리해요. |
| 2-15 | 정상 요청에는 URI와 상관없이 `text/html` 고정 본문 `<h1>Hello, world!</h1>`로 200을 보낸다. 에러에는 `text/plain`으로 `400 Bad Request`처럼 상태 줄과 같은 글자를 보낸다. | 파일 서빙은 Step 3이에요. 에러 본문이 있으면 `curl`로 볼 때 원인을 바로 알 수 있어요. |
| 2-16 | 파서는 `request.c`/`request.h`, 응답은 `response.c`/`response.h`로 나눈다. 파서는 소켓을 쓰지 않는다. `write_all()`은 `server.c`에서 `response.c`로 옮긴다. | 파서를 분리된 모듈로 만들어 단위 테스트해요. (DESIGN.md 제안과 같음) `write_all()`은 이제 응답을 보낼 때 써요. |
| 2-17 | 단위 테스트는 `tests/test_request.c`에 직접 만든 `CHECK` 매크로로 쓰고, `make test`로 빌드하고 실행한다. | C + POSIX만 쓰는 조건이라 외부 테스트 라이브러리를 쓰지 않아요. 실패하면 줄 번호를 출력하고 종료 코드로 알려줘요. |
| 2-18 | 요청마다 메서드, URI, 응답 코드를 `stdout`에 한 줄 출력한다. | 1-10의 연결 로그와 함께 보면 어떤 요청이 어떤 코드로 끝났는지 바로 확인할 수 있어요. |

## Step 3. 정적 파일 서빙

| # | 결정 | 이유 |
| - | ---- | ---- |
| 3-1 | 파일 경로는 루트의 절대 경로 + URI로 만든다. URI의 `?` 뒤(쿼리 문자열)는 뗀다. | 쿼리 문자열은 파일 이름이 아니에요. |
| 3-2 | URI의 `%XX`는 디코딩하지 않는다. | 테스트 파일 이름에 필요 없어요. 디코딩하면 `%2e%2e`가 `..`이 되어 경로 탈출 검사를 디코딩 뒤에 해야 하는 함정이 생겨요. |
| 3-3 | 디렉터리를 요청하면 그 안의 `index.html`을 보낸다. 없으면 404다. 디렉터리 목록은 보여 주지 않는다. | 디렉터리 요청에 `index.html`을 보내는 건 과제 요구사항이에요. (DESIGN.md 제안과 같음) 목록 기능은 요구사항에 없어요. |
| 3-4 | 경로 탈출은 `realpath()`로 실제 위치를 구한 뒤 루트와 같거나 루트 + `/`로 시작하는지로 막는다. 밖이면 403이다. | `..`, `//`, 심볼릭 링크를 모두 풀어서 실제로 가리키는 곳을 봐요. `/app/www2`가 `/app/www` 안으로 잘못 판정되지 않게 `/`까지 확인해요. |
| 3-5 | 루트의 `realpath()`는 서버 시작할 때 한 번 구한다. 실패하면 `perror()`를 출력하고 종료 코드 1로 끝낸다. | 요청마다 구할 필요가 없어요. 1-8처럼 준비 단계 실패는 서버를 켜지 않아요. |
| 3-6 | 디렉터리에 `index.html`을 붙인 뒤에는 `realpath()`부터 같은 검사를 한 번 더 한다. | `index.html`이 바깥을 가리키는 심볼릭 링크일 수도 있어요. |
| 3-7 | 파일은 헤더를 먼저 보내고 64KB 지역 버퍼로 `read()` → `write_all()`을 반복해 보낸다. `sendfile()`은 쓰지 않는다. | 파일 크기와 상관없이 메모리가 일정해요. `sendfile()`은 리눅스 전용이라 C + POSIX 조건에 맞지 않아요. |
| 3-8 | `Content-Length`는 연 파일의 `fstat()` `st_size`로 정하고, 파일은 `read()`/`write()`로만 다룬다. | `strlen()`, `fgets()` 같은 문자열 함수는 `'\0'`이 섞인 바이너리를 깨뜨려요. |
