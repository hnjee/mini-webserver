# Step 2. HTTP 요청 파싱 + 고정 응답

## 목표

받은 바이트를 HTTP 요청으로 읽고, HTTP 형식에 맞춘 고정 응답을 보내요. 요구사항 ID는 R-02, R-03이에요.

- `curl -v http://localhost:8080/`에 `200 OK`와 HTML이 돌아와요.
- 요청이 여러 조각으로 나뉘어 와도 처리해요.
- 잘못된 요청은 400, 모르는 메서드는 501, 지원하지 않는 버전은 505로 응답해요.
- 파서는 소켓과 떨어진 모듈로 만들고 `make test`로 단위 테스트해요.

본문(POST)과 keep-alive는 아직 다루지 않아요. 응답 하나를 보내면 연결을 닫아요.

## 핵심 과제

요청 하나의 처리 흐름은 네 단계예요. Step 2는 ③을 빼고 만들어요.

```
① 헤더 받기 → ② 파싱 → ③ 본문 받기 → ④ 응답 보내기
                      (Step 4)
```

1. **요청 받기**: TCP는 메시지 경계를 모르니까, 연결별 버퍼에 쌓다가 `\r\n\r\n`이 보이면 멈춰요.
2. **파싱**: 버퍼 안의 요청 라인과 헤더를 조각내서 struct에 담아요.
3. **판정**: 형식, 메서드, 버전을 검사해서 400·501·505를 골라요.
4. **응답**: 상태 라인, 헤더, 본문을 함수 하나로 만들고 `Content-Length`를 본문 길이와 맞춰요.
5. **테스트**: 파서를 소켓 없이 문자열만으로 테스트해요.

## 질문과 정리

### 주제 1. 요청은 어디서 끝나나

**Q. `read()`로 요청을 한 번에 다 가져오면 안 되나?**

`read(fd, buf, 8192)`는 "요청 하나를 줘"가 아니라 "지금 커널 수신 버퍼에 와 있는 걸 최대 8192바이트까지 줘"예요. 요청이 네트워크에서 나뉘어 오면 `read()` 한 번에 `"GET / HT"`만 돌아올 수도 있어요. 서버는 요청이 몇 바이트인지 미리 모르니, 끝 표시를 찾을 때까지 반복해서 읽어요.

**Q. 그럼 요청은 어떤 순서로 읽나?**

두 단계예요. 헤더 길이는 정해져 있지 않으니 끝 표시(`\r\n\r\n`)로 찾고, 본문 길이는 헤더의 `Content-Length`를 파싱해야 알 수 있어요. 그래서 헤더를 먼저 다 읽고 파싱한 다음에 본문을 읽어요.

| 단계 | 언제 멈추나 |
| ---- | ---- |
| 헤더 읽기 | 버퍼에 `\r\n\r\n`이 보이면 |
| 본문 읽기 (Step 4) | `Content-Length`만큼 모이면 |

**Q. 요청 헤더가 8KB를 넘을 일이 있나?**

보통은 없어요. 일반 요청 헤더는 수백 바이트에서 1~2KB예요. 긴 쿠키, 긴 쿼리 문자열, 일부러 헤더를 끝없이 보내는 공격 정도예요. 그래서 실제 서버도 상한을 두고 넘으면 거절해요 (Apache 줄당 8190바이트, Node.js 전체 16KB). 늘어나는 버퍼를 써도 상한은 어차피 필요하니 고정 크기 배열이 단순해요.

**Q. 헤더가 너무 크면 400을 보내나?**

전용 코드 **431 Request Header Fields Too Large**가 있어요 (RFC 6585). 비슷한 414 URI Too Long도 있지만, 우리는 "버퍼가 찼다"는 것만 알고 원인을 따지지 않으니 431 하나로 충분해요. 431을 보낸 뒤에는 요청이 어디서 끝나는지 모르니 연결을 닫아요.

**Q. 헤더와 본문은 따로 저장하나?**

네트워크에서는 하나의 바이트 흐름으로 붙어 오지만, 서버 안에서는 따로 다뤄요. 헤더는 작은 텍스트라 조각내서 struct에 담고, 본문은 아무 바이트나 될 수 있고 클 수 있어서 해석하지 않고 따로 모아요. 8KB 버퍼는 헤더를 받는 용도예요.

**Q. `read()`는 수신 버퍼에서 복사해 오는 건가? 그럼 `\r\n\r\n` 뒤까지 읽어 버리면?**

네, `read()`는 커널 수신 버퍼에서 내 `buf`로 복사하고, 복사한 바이트는 커널 쪽에서 빠져요. 그래도 잃어버린 게 아니라 이제 내 `buf`에 있어요. 헤더 끝 위치(`end`)와 전체 길이(`len`)를 기억해 두면, `end` 뒤의 바이트(본문 앞부분이나 다음 요청)를 챙길 수 있어요. 요청 처리가 끝나면 남은 부분을 `buf` 맨 앞으로 당기고(`memmove`), 그 상태에서 다시 `\r\n\r\n`을 찾아요. Step 2는 응답 후 연결을 닫으니 그냥 버리고, 당기는 건 Step 4에서 만들어요.

1바이트씩 읽으면 딱 `\r\n\r\n`에서 멈출 수 있지만, `read()`는 시스템 콜이라 바이트마다 부르면 아주 느려요.

### 주제 2. 파싱 결과를 담을 struct

**Q. "복사 방식"과 "포인터 방식"은 어느 단계 이야기인가?**

"복사"가 두 단계에서 나와요.

```
[커널 수신 버퍼] ──① read()──▶ [buf 8KB] ──② 파싱──▶ [struct]
```

①은 선택지가 없어요. `read()`는 항상 복사해요. (A) 복사 / (B) 포인터 선택은 ②에서 struct에 무엇을 넣을지예요.

- (A) 복사: struct 안 배열(`method[16]`, `uri[2048]`...)에 글자를 한 번 더 복사해요. 필드마다 넘치는지 검사해야 해요.
- (B) 포인터: 버퍼 안의 공백과 `\r` 자리에 `'\0'`을 써 넣고, struct는 각 조각의 시작 위치만 가리켜요. 길이 검사는 버퍼 8KB 하나로 끝나요.

```
파싱 전: G E T ␣ / i n d e x . h t m l ␣ H T T P / 1 . 1 \r \n ...
파싱 후: G E T \0 / i n d e x . h t m l \0 H T T P / 1 . 1 \0 \n ...
         ↑            ↑                    ↑
     req.method    req.uri            req.version
```

(B)의 약점은 버퍼 내용이 바뀌면 struct가 엉뚱한 곳을 가리킨다는 거예요. 그래서 "요청 처리가 끝나기 전에는 버퍼를 다시 채우거나 당기지 않는다"는 규칙 하나만 지키면 돼요.

**Q. 요청을 처리 함수나 백엔드에 넘길 때도 포인터로 넘기나?**

같은 프로그램 안의 함수(Step 3 정적 파일 처리)에는 struct 주소를 넘겨요. 그 함수가 도는 동안 `buf`는 그대로라 안전해요. 다른 프로그램(Step 6 백엔드)에는 포인터를 넘길 수 없어요. 포인터는 내 프로그램 메모리의 위치일 뿐이라, HTTP 요청을 바이트로 다시 써서 백엔드 소켓에 `write()`해요. 백엔드는 그걸 자기 버퍼로 읽어 직접 파싱해요.

**Q. Spring이나 Express는 왜 요청을 복사하나?**

핸들러(요청을 처리하는 함수)는 프레임워크가 아니라 개발자가 써요. 프레임워크는 그 함수를 불러 줄 뿐이라, 함수가 `req`를 언제까지 쓸지 미리 알 수 없어요. 예를 들어 개발자가 이런 핸들러를 쓸 수 있어요 (Express).

```js
app.get('/a', (req, res) => {
  setTimeout(() => {
    res.send('요청한 주소: ' + req.url);   // 1초 뒤에 req.url을 읽어요
  }, 1000);
});                                       // 함수 자체는 바로 끝나요
```

프레임워크가 포인터 방식(B)이었다면 이렇게 돼요.

```
0.0초  요청 1 "GET /a" → buf에 담김, req.url → buf 안을 가리킴
       핸들러 호출 → 바로 끝남
0.1초  요청 2 "GET /zzz" → 같은 buf에 덮어씀
1.0초  핸들러가 req.url을 읽음 → 그 자리에는 이제 "/zzz"가 있음
       → 요청 1에게 "요청한 주소: /zzz"를 보냄
```

`req.url`이 가리키는 자리는 그대로인데 그 자리의 내용이 바뀐 거예요. DB 조회를 기다렸다 응답하는 것처럼 실제 서비스에서 흔한 패턴이라, 프레임워크는 안전하게 요청 내용을 복사해서 `req`를 만들어요.

우리 서버는 요청 하나를 "파싱 → 처리 → 응답"까지 한 흐름 안에서 끝내고, 그 뒤에는 아무도 그 요청을 다시 보지 않아요. `req`를 쓰는 기간이 `buf`가 그대로인 기간 안에 들어가니 (B)로 충분해요. C로 만든 nginx도 (B) 방식이에요. Step 5에서 동시성을 붙여도 연결마다 `buf`를 따로 가지면 섞이지 않아요.

### 주제 3. 에러 판정 (400 / 501 / 505)

**Q. 400, 501, 505는 어떻게 다른가?**

| 코드 | 뜻 | 한마디로 |
| ---- | ---- | ---- |
| 400 Bad Request | 형식이 틀렸어요 | "무슨 말인지 못 알아듣겠어" |
| 501 Not Implemented | 형식은 맞는데 그 메서드를 지원하지 않아요 | "알아는 듣겠는데 그건 안 해" |
| 505 HTTP Version Not Supported | 형식은 맞는데 그 버전을 지원하지 않아요 | "그 버전으로는 대화 못 해" |

형식이 틀렸으면 메서드나 버전을 따질 의미가 없어서 400을 먼저 검사해요.

| 요청 | 결과 | 이유 |
| ---- | ---- | ---- |
| `GET / HTTP/1.1` + `Host: x` | 200 | 정상 |
| `GET / HTTP/1.0` (Host 없음) | 200 | 1.0은 Host가 필수가 아니에요 |
| `GET / HTTP/1.1` (Host 없음) | 400 | 1.1은 Host가 필수예요 (RFC 9112) |
| `GET /` (버전 없음) | 400 | 요청 라인은 "메서드 공백 URI 공백 버전" 세 조각이에요 |
| `GET index.html HTTP/1.1` | 400 | URI는 `/`로 시작해야 해요 |
| `Host x` (콜론 없는 헤더 줄) | 400 | 헤더는 `이름: 값` 형식이에요 |
| `Content-Length: abc` | 400 | 숫자가 아니에요 |
| `BREW / HTTP/1.1` | 501 | 모르는 메서드예요 |
| `get / HTTP/1.1` | 501 | 메서드는 대소문자를 구분해요 |
| `GET / HTTP/2.0` | 505 | 1.0과 1.1만 지원해요 |
| `GET / HTTX/1.1` | 400 | `HTTP/`로 시작하지 않으면 버전이 아니라 틀린 형식이에요 |

### 주제 4. 응답 함수

**Q. 응답은 왜 함수 하나로 만드나?**

`curl`이나 브라우저는 HTTP 형식에 맞춘 응답만 알아들어요.

```
HTTP/1.1 200 OK\r\n                          ← 상태 라인
Date: Mon, 23 Nov 2026 05:00:00 GMT\r\n      ┐
Content-Type: text/html\r\n                  │ 헤더
Content-Length: 22\r\n                       │
Connection: close\r\n                        ┘
\r\n                                         ← 빈 줄 = 헤더 끝
<h1>Hello, world!</h1>                       ← 본문 (22바이트)
```

클라이언트는 `Content-Length`만큼 본문을 읽어요. 숫자가 크면 계속 기다리고, 작으면 본문이 잘려요. 호출하는 쪽이 본문과 길이만 넘기고 함수가 `Content-Length`를 직접 쓰면, 사람이 숫자를 잘못 적을 일이 없어요. 정상 응답과 에러 응답이 같은 함수를 쓰니 Step 3에서 404·403을 붙일 때도 그대로 써요.

### 주제 5. 파서 분리와 단위 테스트

**Q. 파서는 왜 따로 떼나?**

`nc`나 `curl`로만 테스트하면 매번 서버를 켜고 요청을 손으로 쳐야 해요. 파서가 소켓을 모르는 함수면 문자열을 넣고 결과만 확인하면 돼요. `make test` 한 번으로 위의 판정 표를 전부 확인할 수 있어요.

## 이 단계에서 정한 것

| #&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; | 결정 | 이유 |
| - | ---- | ---- |
| 2-1 | 연결마다 8KB(8192바이트) 고정 크기 버퍼에 이어 붙이고, `\r\n\r\n`이 나올 때까지 `read()`를 반복한다. | TCP는 메시지 경계를 몰라서 한 번의 `read()`로 다 온다고 가정할 수 없어요. (DESIGN.md 제안과 같음) 정상 요청 헤더는 8KB 안에 들어오고, 늘어나는 버퍼도 상한은 필요해서 고정 배열이 단순해요. |
| 2-2 | 버퍼가 가득 찼는데 `\r\n\r\n`이 없으면 431을 보내고 연결을 닫는다. | 431은 "헤더가 너무 크다"는 전용 코드라 400보다 원인이 분명해요. 요청 끝을 모르니 남은 바이트를 믿을 수 없어요. |
| 2-3 | 헤더가 끝나기 전에 `read()`가 0이면 응답 없이 연결을 닫는다. -1이면 `EINTR`은 다시 읽고 나머지는 연결을 닫는다. | 상대가 요청을 다 보내지 않고 끊었으니 응답할 대상이 없어요. 1-6의 `read()` 처리를 그대로 따라요. |
| 2-4 | `\r\n\r\n` 뒤에 딸려 온 바이트는 Step 2에서는 버린다. | Step 2는 응답 하나를 보내고 연결을 닫아요. 남은 바이트를 앞으로 당겨 다음 요청이나 본문으로 쓰는 건 Step 4에서 만들어요. |
| 2-5 | 파싱 결과는 버퍼 안을 가리키는 포인터로 struct에 담는다. 구분자 자리에 `'\0'`을 써 넣는다. 요청 처리가 끝나기 전에는 버퍼를 다시 채우거나 당기지 않는다. | 복사가 없고, 길이 검사가 버퍼 크기 하나로 끝나요. 요청 하나를 한 흐름 안에서 끝내는 구조라 버퍼가 바뀔 때 struct를 쓰고 있을 일이 없어요. |
| 2-6 | struct에는 `method`, `uri`, `version`, `host`, `content_length`, `connection`을 담는다. 그 밖의 헤더는 형식만 검사하고 버린다. 헤더 이름은 대소문자를 구분하지 않는다. | R-02가 요구하는 항목이에요. `Content-Length`와 `Connection`은 Step 4에서 써요. HTTP 헤더 이름은 대소문자를 구분하지 않아서 `host:`도 받아야 해요. |
| 2-7 | 지원 메서드는 `GET`, `POST`다. 그 밖의 메서드는 501이다. 메서드는 대소문자를 구분한다. | POST 본문은 Step 4에서 읽지만 아는 메서드로는 지금부터 인정해요. HTTP 메서드는 대소문자를 구분해요. |
| 2-8 | 지원 버전은 `HTTP/1.0`, `HTTP/1.1`이다. `HTTP/`로 시작하는 다른 버전은 505, `HTTP/`로 시작하지 않으면 400이다. | 형식이 맞는 다른 버전과 아예 틀린 형식을 구분해요. |
| 2-9 | 400 조건: 요청 라인이 세 조각이 아님, URI가 `/`로 시작하지 않음, 헤더 줄에 `:`가 없음, `Content-Length`가 0 이상의 정수가 아님, `HTTP/1.1`인데 `Host`가 없음. | 형식이 틀린 요청이에요. `HTTP/1.1`의 `Host` 필수는 RFC 9112 규칙이에요. |
| 2-10 | 판정 순서는 형식(400) → 메서드(501) → 버전(505)이다. | 형식이 틀렸으면 메서드나 버전을 따질 의미가 없어요. |
| 2-11 | Step 2는 모든 응답 뒤에 연결을 닫고, 응답에 `Connection: close`를 넣는다. | keep-alive는 Step 4에서 만들어요. 에러 뒤에는 남은 바이트를 믿을 수 없어서 Step 4에서도 닫아요. |
| 2-12 | 응답은 `send_response(fd, status, content_type, body, body_len)` 하나로 보낸다. `Content-Length`는 함수가 `body_len`으로 쓴다. | 본문 길이와 `Content-Length`가 어긋날 수 없어요. (DESIGN.md 제안과 같음) |
| 2-13 | 응답 헤더는 `Date`, `Content-Type`, `Content-Length`, `Connection`을 넣는다. | R-03의 표준 헤더예요. `Date`는 RFC 9110이 시계가 있는 서버는 보내라고 정했어요. |
| 2-14 | 헤더는 512바이트 지역 배열에 `snprintf()`로 만들고, `write_all()`로 헤더 → 본문 순서로 보낸다. | 헤더는 짧아서 작은 배열로 충분해요. 부분 `write()`는 1-7의 `write_all()`이 처리해요. |
| 2-15 | 정상 요청에는 URI와 상관없이 `text/html` 고정 본문 `<h1>Hello, world!</h1>`로 200을 보낸다. 에러에는 `text/plain`으로 `400 Bad Request`처럼 상태 줄과 같은 글자를 보낸다. | 파일 서빙은 Step 3이에요. 에러 본문이 있으면 `curl`로 볼 때 원인을 바로 알 수 있어요. |
| 2-16 | 파서는 `request.c`/`request.h`, 응답은 `response.c`/`response.h`로 나눈다. 파서는 소켓을 쓰지 않는다. `write_all()`은 `server.c`에서 `response.c`로 옮긴다. | 파서를 분리된 모듈로 만들어 단위 테스트해요. (DESIGN.md 제안과 같음) `write_all()`은 이제 응답을 보낼 때 써요. |
| 2-17 | 단위 테스트는 `tests/test_request.c`에 직접 만든 `CHECK` 매크로로 쓰고, `make test`로 빌드하고 실행한다. | C + POSIX만 쓰는 조건이라 외부 테스트 라이브러리를 쓰지 않아요. 실패하면 줄 번호를 출력하고 종료 코드로 알려줘요. |
| 2-18 | 요청마다 메서드, URI, 응답 코드를 `stdout`에 한 줄 출력한다. | 1-10의 연결 로그와 함께 보면 어떤 요청이 어떤 코드로 끝났는지 바로 확인할 수 있어요. |

## 만드는 파일과 함수

| 파일 | 내용 |
| ---- | ---- |
| `src/request.h` | `struct http_request` 정의, 파서 함수 선언 |
| `src/request.c` | 헤더 끝 찾기, 요청 라인·헤더 파싱, 400·501·505 판정. 소켓을 쓰지 않아요 |
| `src/response.h` | 응답 함수 선언 |
| `src/response.c` | `status_text()`, `send_response()`, `write_all()` |
| `src/server.c` | `handle_echo()`를 `handle_http()`로 바꿔요. `write_all()`은 `response.c`로 옮겨요 |
| `tests/test_request.c` | 파서 단위 테스트 |
| `Makefile` | `make test` 추가 |

```c
struct http_request {
    char *method;          /* "GET" */
    char *uri;             /* "/index.html" */
    char *version;         /* "HTTP/1.1" */
    char *host;            /* 없으면 NULL */
    long  content_length;  /* 없으면 -1 */
    char *connection;      /* 없으면 NULL */
};
```

`request.c`의 함수예요.

| 함수 | 하는 일 |
| ---- | ------- |
| `request_find_end(buf, len)` | `buf`의 `len`바이트에서 `\r\n\r\n`을 찾아, 그 바로 뒤 위치(헤더 길이)를 돌려줘요. 없으면 -1이에요. `buf`는 `'\0'`으로 끝나지 않아서 `strstr()`을 쓸 수 없고, `memmem()`은 POSIX가 아니라서 직접 찾아요 |
| `parse_request(buf, len, &req)` | 헤더 `len`바이트를 제자리에서 조각내 `req`를 채워요. 정상이면 0, 아니면 400·501·505를 돌려줘요 |

`response.c`의 함수예요.

| 함수 | 하는 일 |
| ---- | ------- |
| `status_text(status)` | 200 → `"OK"`, 404 → `"Not Found"`처럼 상태 문구를 돌려줘요 |
| `send_response(fd, status, content_type, body, body_len)` | 상태 라인과 헤더 4개를 만들고, 헤더 → 본문 순서로 끝까지 보내요. 성공하면 0, 실패하면 -1이에요 |
| `send_error(fd, status)` | `"400 Bad Request"` 같은 본문을 만들어 `send_response()`를 불러요 |
| `write_all(fd, buf, len)` | Step 1과 같아요. `server.c`에서 옮겨 와요 |

`server.c`의 `handle_http(client_fd)`는 이렇게 흘러가요.

```
char buf[8192]; len = 0
반복:
  end = request_find_end(buf, len)
  end를 찾았으면 → 빠져나가기
  len == 8192   → send_error(431), 닫기
  n = read(client_fd, buf + len, 8192 - len)
  n == 0 → 응답 없이 닫기 / n < 0 → EINTR이면 다시, 아니면 닫기
  len += n
status = parse_request(buf, end, &req)
0이면 고정 HTML로 200, 아니면 send_error(status)
로그 출력, close(client_fd)
```

## 완료 테스트

모든 명령은 컨테이너 안에서 실행해요. 터미널 A, B는 각각 Mac 터미널에서 `docker compose exec dev bash`로 연 컨테이너 셸이에요. 프롬프트가 `dev@xxxx:/app$`인지 먼저 확인해요 (문제가 생기면 STEP1.md 완료 테스트의 증상 표를 봐요).

서버는 터미널 A에서 켜 둬요.

```sh
# 터미널 A
make && ./webserver -p 8080 -r ./www
```

**1. 단위 테스트**

```sh
# 터미널 B
make test
# → 모든 CHECK 통과, echo $? 는 0
```

주제별 케이스: 정상 요청, `HTTP/1.0` Host 없음, 판정 표의 400·501·505 줄, 헤더 이름 대소문자(`host:`), `request_find_end()`가 `\r\n\r\n`이 없을 때 -1을 돌려주는지.

**2. 정상 요청** (완료 기준)

```sh
curl -v http://localhost:8080/
# → < HTTP/1.1 200 OK
# → < Content-Type: text/html
# → < Content-Length: 22
# → < Connection: close
# → <h1>Hello, world!</h1>
```

`curl`이 `Content-Length`와 실제 본문 길이가 다르면 경고를 내요. 경고 없이 끝나면 길이가 맞는 거예요.

**3. 나뉘어 온 요청** (완료 기준)

```sh
(printf 'GET / HTTP/1.1\r\n'; sleep 1; printf 'Host: x\r\n\r\n') | nc localhost 8080
# → 1초 뒤 HTTP/1.1 200 OK
```

**4. 에러 판정**

```sh
printf 'BREW / HTTP/1.1\r\nHost: x\r\n\r\n' | nc localhost 8080   # → 501 (완료 기준)
printf 'GET / HTTP/2.0\r\nHost: x\r\n\r\n'  | nc localhost 8080   # → 505
printf 'GET / HTTP/1.1\r\n\r\n'             | nc localhost 8080   # → 400 (Host 없음)
printf 'GET /\r\nHost: x\r\n\r\n'           | nc localhost 8080   # → 400 (버전 없음)
printf 'GET / HTTP/1.0\r\n\r\n'             | nc localhost 8080   # → 200
```

**5. 너무 긴 헤더**

```sh
{ printf 'GET / HTTP/1.1\r\nX: '; head -c 8173 /dev/zero | tr '\0' a; } | nc localhost 8080
# → 431 Request Header Fields Too Large
```

앞부분 19바이트와 `a` 8173개를 합쳐 정확히 8192바이트를 보내요. 더 많이 보내면 서버가 다 읽지 않은 채로 연결을 닫게 돼요. 그러면 커널이 RST를 보내고, 클라이언트가 431을 읽기 전에 `Connection reset`으로 끝날 수 있어요. 이 문제는 Step 7 엣지 케이스에서 다시 봐요.

**6. 중간에 끊긴 요청**

```sh
printf 'GET / HTTP/1.1\r\nHo' | nc -N localhost 8080
# → 응답 없음, 터미널 A에 closed 로그가 나오고 서버는 계속 돌아가요
```

`-N`은 입력이 끝나면 쓰기 방향을 닫아서, 서버의 `read()`가 0을 받게 해요.

**7. 메모리 검사**

```sh
# 터미널 A: 서버를 끄고 디버그 빌드로 다시 실행
make debug && ./webserver-debug -p 8080 -r ./www
# 터미널 B: 테스트 2~6을 다시 실행
# → 터미널 A에 ASan 에러가 나오지 않아요
```
